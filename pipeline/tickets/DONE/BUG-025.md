**Depends on:** None.

**Premise checked 2026-09-12:** `deploy_state_configmap_name` still did `Printf.sprintf "sol-deploy-state-%s" workspace` and `save_deployed_groups` still wrapped the apply in `ignore` — so a workspace like `ci_smoke` produced an invalid object and the failure was silent.

`Sol_cli_deployment_state.deploy_state_configmap_name` builds the deploy-state ConfigMap name as `"sol-deploy-state-" ^ workspace`. A workspace named `ci_smoke`, `my_app` or `Acme` contains characters Kubernetes forbids in an object name (`_`, uppercase), so `kubectl apply` rejects the ConfigMap — and `save_deployed_groups` wraps the apply in `ignore`, so the rejection is silent.

## Impact

`load_deployed_groups` reads that same never-written ConfigMap and gets `[]`, so `check_consumer_group_changes` can never warn that a consumer group has disappeared. On any workspace whose name has an underscore or uppercase letter — which includes CI's own `ci_smoke` and the common `my_app` — the drift check is dead code that looks alive: it runs, finds nothing to compare, and reports nothing.

FEAT-067 hit the same class of bug with its current-release pointer (its name embeds the workspace) and fixed it with `Sol_cli_release.sanitize_name`; the deploy state was not touched there because correcting it changes behaviour.

## Fix

- Name the ConfigMap through an RFC 1123 subdomain sanitizer (lowercase, `-`/`.`, start and end alphanumeric) rather than raw concatenation. `Sol_cli_release.sanitize_name` already does exactly this; either share it or move the helper somewhere neutral.
- Stop ignoring the apply result in `save_deployed_groups`. A state write that fails must be reported, because the drift check's correctness depends on the state actually being there.

## Acceptance criteria

- `sol up` / `sol deploy` write the deploy-state ConfigMap for a workspace named `ci_smoke` or `my_app`.
- A failed state write is reported, not swallowed.
- A test covers an underscore/uppercase workspace name for the ConfigMap name.

## Completion notes

Landed 2026-09-12.

- **One home for name sanitizing.** The RFC 1123 subdomain transform moved to
  `Sol_cli_kubernetes_name.sanitize_name` (the module that already owns k8s
  names and `sanitize_label_value`). `Sol_cli_deployment_state` uses it for
  `sol-deploy-state-<workspace>`, and `Sol_cli_release` now uses it too —
  removing the duplicate FEAT-067 had introduced for its pointer object. A name
  and a label value are genuinely different (`_` is legal in the latter only),
  so both sanitizers remain, each documented for its side.
- **The write is no longer silent.** `save_deployed_groups` matches the apply
  result and prints `warning: could not record deploy state (<name>): <reason>`
  instead of `ignore`. It stays non-fatal — a deploy that succeeded should not
  fail because the bookkeeping did — but a permanent failure is now visible.
- **Test:** `test_deployment_state` covers `ci_smoke` →
  `sol-deploy-state-ci-smoke`, `My_App` → `sol-deploy-state-my-app`, and an
  already-valid `pluto` unchanged.

**Intended behaviour change, recorded:** on underscore/uppercase workspaces the
state ConfigMap now actually gets written, so `check_consumer_group_changes`
starts seeing previous groups. First deploy still sees `[]` (no warning); a
later deploy that drops a consumer group now warns and requires
`--confirm-group-change`. That is the check working, not a regression — it had
simply never had data on those workspaces before.

Verified: `dune build`, full `cli/sol/test` suite, `dune fmt --preview` clean.
Demo/example coverage: no CLI surface change.
