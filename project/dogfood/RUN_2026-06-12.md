**Expected:** The URL printed by `sun up` points at `dogfood_2026_06_12`'s `charge-svc`.  
**Actual:** Port 8080 was still held by `kubectl port-forward -n dogfood-2026-06-11-payments svc/charge-svc 8080:80`. `sun up` exited 0 and printed `http://localhost:8080 (port-forward running in background)`, but requests initially hit the older workspace.  
**Time lost:** ~5 minutes to inspect process and pod state.  
**Workaround:** Identify and terminate the stale port-forward, then rerun `sun up` or start the correct port-forward.  
**Blocks two-minute claim?** yes  
**Suggested fix:** Use the existing `UX-002` remediation: detect the owner of a busy Sun-managed service port and either replace stale Sun port-forwards safely or report the owning namespace/service and exact kill command.

**Command:** Directly port-forwarded the new namespace with `kubectl port-forward -n dogfood-2026-06-12-payments svc/charge-svc 18080:80`, then called `/health`, `POST /charges`, and `/notifications`.

**Actual:** `/health` returned `ok` and `POST /charges` returned accepted, but `/notifications` remained `[]` for 20 seconds. Both generated workload Secrets contained `POSTGRES_URL: ""`.  
**Time lost:** ~10 minutes to isolate from the stale 8080 port-forward and inspect pod Secrets/logs.  
**Workaround:** Manually populate the workload Secrets with the in-cluster Postgres URL and restart pods, or export `POSTGRES_URL` before deploy if targeting a non-local context.  
**Blocks two-minute claim?** yes  
**Suggested fix:** Local `sun up` should populate a valid in-cluster dev Postgres URL, and generated workloads should not silently run storage-backed flows with `POSTGRES_URL=""`.
