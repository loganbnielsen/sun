## Friction Log

### FRIC-001: `sun up` prints port-forward success URL even when port is already occupied

**Step:** `sun up`
**Command:** `sun up` (from `dogfood_2026_06_10/`)
**Expected:** Either (a) takes ownership of port 8080, printing `→ http://localhost:8080`, or (b) detects port conflict and prints a clear error with the competing namespace/process.
**Actual:** Port 8080 was held by an earlier workspace's `kubectl port-forward -n dogfood-clean-c-payments svc/charge-svc 8080:80`. `sun up` launched a new `kubectl port-forward` process, which immediately failed (logged to `/tmp/sun-pf-charge-svc.log` as "bind: address already in use"), but printed `→  http://localhost:8080  (port-forward running in background)` anyway. The PID written to `.sun/pf-charge-svc.pid` (37566) was dead on arrival.
**Time lost:** Several minutes diagnosing — the URL line made the workspace appear healthy; `curl /health` returned `ok` from the old workspace, masking the failure.
**Workaround:** Kill the old port-forward process manually (`kill 31817`), then re-run `sun up` or manually start `kubectl port-forward -n dogfood-2026-06-10-payments svc/charge-svc 8080:80`.
**Blocks two-minute claim?** yes — on any substrate where a prior workspace's port-forward is still alive, `sun up` silently deploys but the user hits the wrong service. The engineer has no indication of the problem.
**Suggested fix:** After calling `start_port_forward`, sleep briefly and check if the PID from `.sun/pf-*.pid` is still alive. If not, read `/tmp/sun-pf-<name>.log`, print a warning with the conflict details, and suggest `sun down` or a `--force-port-forward` flag. Do not print the `→ http://localhost:8080` success line if the process is dead.

**Code location:** `/home/lbendtly/Code/sun/cli/sun/bin/cmd_up.ml` lines 194-197 — the URL is printed unconditionally after `start_port_forward` without a liveness check.

## Findings

**Kafka worker path confirmed.** `notify_worker` in `dogfood-2026-06-10-comms` consumed the `Charged` events published by the charge-svc (via `dogfood_2026_06_10-payments-charges` topic) and wrote notification rows to PostgreSQL. `GET /notifications` returned the correct rows. Consumer group isolation per workspace is correct (`group_id = "dogfood_2026_06_10-comms-notify-worker"`).

**Topic isolation is correct, DB isolation is not.** Each workspace uses a workspace-scoped Kafka topic (`dogfood_2026_06_10-payments-charges`). However, all workspaces share the same PostgreSQL URL (`postgresql://postgres:dev@postgresql.postgresql.svc.cluster.local:5432/dev`) and the same `notifications` table. With two workspaces deployed simultaneously, both workspaces' workers insert rows into the same table — `GET /notifications` returns rows from all workspaces. This is expected for a local dev substrate but is worth noting in the runbook.

**`kubectl logs` returns empty for `notify_worker`.** `kubectl logs -n dogfood-2026-06-10-comms deploy/notify-worker` returned no output even after the worker had clearly consumed events. The old workspace's worker showed `[obs-loki] Loki returned HTTP 400` errors (likely duplicate Loki stream labels), which at least proves log output goes to stdout. The new workspace's empty logs are unexplained — possibly the Loki push succeeds and stdout is consumed, or the OCaml runtime buffers are not flushed before each push. Not blocking — the Kafka path is confirmed by DB state. Worth investigating as a diagnostics gap.

**Port-forward duplicate guard is workspace-scoped, not port-scoped.** `cmd_up.ml`'s `port_forward_running` checks `.sun/pf-<name>.pid` in the current workspace directory. It correctly prevents duplicate forwards within the same workspace re-deploy. It does not detect a competing port-forward from a different workspace directory — which is the common multi-workspace scenario.

**`sun dev up` reconcile on existing cluster: 24s.** Helm upgrades on all four charts (Redpanda, PostgreSQL, Loki, Prometheus) each take 1-2s because all are already at the desired version. The 24s total is dominated by `helm repo update` (~5s) and waiting for each Helm release response. This is acceptable for an "already running" scenario but could be improved by checking chart versions before running `helm upgrade`.
