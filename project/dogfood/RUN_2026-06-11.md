### FRIC-002 (blocker): `sun secret set` targets wrong secret object for standard Deployment workloads

**Step:** After `sun up`, set POSTGRES_URL for worker and service
**Command:** `sun secret set --env local --value "postgresql://..." POSTGRES_URL`
**Expected:** POSTGRES_URL becomes available to pods in the workspace; re-deploy picks it up.
**Actual:** The command prints "secret set in 2 namespace(s)" but updates `sun-secrets` in each namespace. Standard Deployment pods mount `<service>-secrets` (e.g., `notify-worker-secrets`, `charge-svc-secrets`), not `sun-secrets`. After running `sun secret set` and `sun up`, all pods still see `POSTGRES_URL=""`. The worker handler falls through to `| None -> ack (); Ok ()` — every Charged event is silently acknowledged without writing to the DB. `GET /notifications` returns `[]` with no error.
**Time lost:** ~15 minutes diagnosing; required reading manifest code to identify the disconnect.
**Workaround:** Manually patch the per-service secrets with `kubectl patch secret notify-worker-secrets --type merge -p '...'`, then `kubectl rollout restart` each deployment.
**Blocks two-minute claim?** yes — the Kafka → DB write path is broken without POSTGRES_URL, and there is no working documented path to inject it.
**Suggested fix:** Option A: In `sun secret set`, patch each `<service>-secrets` object in the workspace (read from manifest or derive from namespace contents) instead of `sun-secrets`. Option B: Include `sun-secrets` as a second `secretRef` in standard `deployment_doc` alongside `<service>-secrets`, so `sun secret set` works as designed. Option A is simpler and requires no manifest change.

**Code locations:**
- `cli/sun/lib/sun_cli_secret.ml` line 84: applies to `Sun_cli_manifest.runtime_secret_name` = `"sun-secrets"`
- `cli/sun/lib/sun_cli_manifest.ml` line 303-304: deployment `envFrom` mounts `<name>-secrets`
- `cli/sun/lib/sun_cli_manifest.ml` line 408-409: rollout `envFrom` mounts `runtime_secret_name` = `"sun-secrets"` ← only rollouts work with `sun secret set`

### FRIC-003 (high): Port-forward dies after `kubectl rollout restart` and is not revived

**Step:** After `kubectl rollout restart` (required workaround for FRIC-002), the port-forward process started by `sun up` exits.
**Command:** `kubectl rollout restart deployment/charge-svc -n dogfood-2026-06-11-payments`
**Expected:** Either the port-forward reconnects to the new pod automatically (since it targets `svc/charge-svc`), or `sun up` revives dead port-forwards when re-run.
**Actual:** After `kubectl rollout restart`, the `kubectl port-forward` process (targeting `svc/charge-svc`) exits. `curl http://localhost:8080/health` returns connection refused. Running `sun up` does not restart dead port-forwards (it starts a new process, but the new process also fails if another process is already on the port — or succeeds if not). The user must manually restart the port-forward with `kubectl port-forward`.
**Time lost:** ~5 minutes.
**Workaround:** `kubectl port-forward -n <ns> svc/charge-svc 8080:80 &`
**Blocks two-minute claim?** no — only triggered by the FRIC-002 workaround, not the normal path
**Suggested fix:** `sun up` (and a new `sun pf` or `sun status --fix`) should check PID liveness for all registered port-forwards and restart any that are dead. Alternatively, wrap `kubectl port-forward` in a restart loop (e.g., `while true; do kubectl port-forward ...; done`) so it survives pod replacements automatically.

### Medium friction: `sun up` exits 1 when port-forward fails but deployment succeeded

**Step:** `sun up` with port 8080 already occupied by old workspace
**Actual:** Services build, push, and roll out successfully. The port-forward fails. `sun up` prints the correct conflict warning (FRIC-001 fix). But `sun up` exits with code 1. In a script, the engineer would `set -e` and see the deploy as failed even though services are healthy. The exit code conflates deployment failure (recoverable by retry) with infrastructure failure.
**Blocks two-minute claim?** no
**Suggested fix:** Exit 0 when deployment succeeded, even if port-forward failed. Use exit 2 (or a different non-zero code) specifically for port-forward failure, distinct from deployment failure (exit 1).

## Findings

**Kafka worker path confirmed** (with workaround for FRIC-002). After manually injecting `POSTGRES_URL` into `notify-worker-secrets` and restarting the pod, `notify_worker` in `dogfood-2026-06-11-comms` consumed the `Charged` event from topic `dogfood_2026_06_11-payments-charges` and wrote a notification row to PostgreSQL. `GET /notifications` returned `[{"charge_id":"ch_770445","customer_id":"cus_dogfood","amount_cents":999,"currency":"usd"}]`. Consumer group isolation per workspace is correct (`group_id = "dogfood_2026_06_11-comms-notify-worker"`).

**Empty pod logs persist.** `kubectl logs -n dogfood-2026-06-11-comms deploy/notify-worker` returns empty even when the worker is clearly consuming events and writing to DB. This was noted in the 2026-06-10 run as well. Logs go to Loki via the structured backend when LOKI_URL is set; stdout is not flushed separately. This is a diagnostics gap — engineers relying on `kubectl logs` for debugging will see nothing. This is the same Loki-vs-stdout log routing observation from the prior run.

**`sun migrate` uses a separate port-forward on port 15432.** The migrate command prints "Forwarding postgresql (cluster) → localhost:15432" and correctly avoids the 5432 port already in use. This is correct behavior but not documented — an engineer who runs `sun migrate` while something else holds 5432 would be surprised by the port-forward on 15432.

**FRIC-001 fix quality is good.** The port-forward conflict warning is informative and includes the exact `kill $(lsof -ti:8080) && sun up` remediation. No regression introduced.
