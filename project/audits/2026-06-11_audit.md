## Findings

### AUDIT-021 — `sun migrate rollback` is a non-functional stub

* **Category:** DX
* **Severity:** Medium
* **Location:** `cli/sun/bin/cmd_migrate.ml` lines 79–82
* **Description:** `run_rollback` unconditionally prints "not yet implemented" and exits 1. The command appears in `sun migrate --help` and was added to the Tutorial CLI reference in RELEASE-003, misleading users who attempt to roll back a migration.
* **Impact:** Users who run `sun migrate rollback` get a stub error instead of functionality. CI automation that calls `sun migrate rollback` on failure will produce a confusing failure.
* **Remediation:** Implement rollback in `migration.ml` — track each applied migration's SQL or require a companion down-migration file (e.g., `0001_notifications.down.sql`). Alternatively, document that rollback requires a manual down-migration and remove the stub subcommand from the public CLI surface.

---

### AUDIT-022 — `auto_forward_pg` uses ambient `Unix.sleepf 2.0` timing

* **Category:** DX
* **Severity:** Low
* **Location:** `cli/sun/bin/cmd_migrate.ml` line 17
* **Description:** When `POSTGRES_URL` is unset and a cluster postgres exists, `sun migrate` starts a background `kubectl port-forward` and then unconditionally sleeps 2 seconds. If the port-forward takes longer to establish (cold cluster, slow kubelet), the subsequent connection attempt fails.
* **Impact:** Flaky `sun migrate` on cold or loaded clusters; misleading "connection refused" error.
* **Remediation:** Replace `Unix.sleepf 2.0` with a short polling loop (e.g., retry `pg_isready` or TCP connect up to 10× at 0.5 s intervals).

---

### AUDIT-023 — `sun migrate` has no `--dry-run` flag

* **Category:** DX
* **Severity:** Low
* **Location:** `cli/sun/bin/cmd_migrate.ml`; `integrations/storage/sun-storage/lib/migration.ml`
* **Description:** The AUDIT.md runbook invariant states: "sun migrate --dry-run prints the SQL before touching the database." No such flag exists in the CLI or the underlying `Migration.apply` implementation.
* **Impact:** Operators cannot preview migration SQL before applying to a live database. This is particularly risky for production migrations with additive/destructive changes.
* **Remediation:** Add `--dry-run` flag to the `apply` subcommand that prints the pending SQL statements to stdout without executing them.

### AUDIT-024 — Migration tracking table is not workspace-prefixed

* **Category:** Data Integrity
* **Severity:** Medium
* **Location:** `cli/sun/bin/cmd_migrate.ml` line 92; `integrations/storage/sun-storage/lib/migration.ml`
* **Description:** The default tracking table is `sun_schema_migrations` for every workspace. Two workspaces sharing a local database (common in local dev with `sun dev up`) will share the same tracking table, causing workspace A's migrations to appear applied in workspace B.
* **Impact:** Silent migration skips when switching between workspaces that share a Postgres instance. `sun migrate status` reports incorrect applied/pending state.
* **Remediation:** Derive the default table name from the workspace name found in `dune-project` (`sun_<workspace>_schema_migrations`) or document that the `--table` flag must always be passed in multi-workspace setups. A warning when the default table name is used and migrations from a different workspace are detected would also help.

### AUDIT-025 — `default_on_decode_error` uses unstructured stderr; callback lacks raw bytes

* **Category:** Observability
* **Severity:** Low
* **Location:** `integrations/kafka/kafka-eio-service/lib/kafka_service.ml` lines 337–340; `kafka_service.mli` line 120
* **Description:** Two gaps in the decode-error observability contract: (1) `default_on_decode_error` uses `Printf.eprintf` instead of a structured log line via `Obs`, so decode errors are invisible in Loki when no custom handler is provided. (2) The `on_decode_error` callback receives only an error string, not the raw message bytes — users cannot forward the failing message to a dead-letter topic from this callback.
* **Impact:** Silent decode errors in Loki (visible only in pod stderr). No dead-letter forwarding option without re-implementing the decode/error pipeline outside the framework.
* **Remediation:** (1) Accept an optional `?ot:Obs.t` in `default_on_decode_error` and emit via `Obs.log_t` when available. (2) Change the callback signature to pass `raw_bytes:bytes` alongside the error string so users can forward the raw payload.

### AUDIT-026 — Generated Dockerfiles copy host-compiled binaries (non-hermetic)

* **Category:** Runtime Performance / Hermetic Build
* **Severity:** Medium
* **Location:** `cli/sun/lib/sun_cli_cmd_new.ml` (scaffold Dockerfile template); `examples/venus/`, `examples/pluto/` Dockerfiles
* **Description:** All generated and reference Dockerfiles copy a pre-compiled binary from `_build/default/` into an Ubuntu 24.04 base image. The binary is compiled on the host by `dune build` before `docker build`. If the host OCaml toolchain links against a different glibc than ubuntu:24.04 provides, the binary will crash with "GLIBC_X.XX not found" at startup.
* **Impact:** Images that appear to build successfully may fail to start in production if the host glibc version differs from the container base image. This is invisible until the container starts.
* **Remediation:** (a) Add a multi-stage Dockerfile template that compiles the binary inside the container (`FROM ocaml/opam:ubuntu-24.04-ocaml-5.4.1 AS build`), or (b) investigate static linking via musl/cross-compilation. Option (a) is more maintainable and is the standard practice for OCaml production containers.

### AUDIT-027 — Partition count reduction is not guarded at deploy time

* **Category:** Data Integrity
* **Severity:** High
* **Location:** `cli/sun/lib/sun_cli_deployment_plan.ml`; `integrations/kafka/kafka-eio-service/lib/kafka_service.ml`
* **Description:** The deployment pipeline has no pre-flight check for Kafka partition count reductions. A developer who reduces `partitions` in `config` and runs `sun deploy` will receive an opaque librdkafka error (`ERR__UNKNOWN_PARTITION` or `INVALID_REPLICATION_FACTOR`) without a user-friendly explanation.
* **Impact:** Silent or confusing deploy failures when partition counts are decreased. Partition count increases are safe and can be allowed; only reductions should be blocked.
* **Remediation:** In `kafka_service.ml` `register`, query the existing topic's partition count before calling `rd_kafka_CreateTopics`. If the new count is lower, return an `Error` naming the topic and both counts. Expose a `--force-partition-reduce` flag to override.

---

### AUDIT-028 — Consumer group ID changes are not detected before deploy

* **Category:** Data Integrity
* **Severity:** Medium
* **Location:** `cli/sun/lib/sun_cli_deployment_plan.ml` lines 207, 328
* **Description:** The deployment plan derives and records `consumer_groups` from the workspace structure but does not compare against the currently deployed group IDs. A typo or intentional rename of `group_id` in a worker causes the new group to start consuming from the latest offset, potentially skipping messages produced during the switchover.
* **Impact:** Silent message loss or double-processing on group ID changes. No warning is shown before or after deploy.
* **Remediation:** Add a pre-deploy step that reads deployed ConfigMaps/consumer group names from the cluster (or stores a `sun-deploy-state.json` in a ConfigMap) and emits a prominent warning when a group ID changes. Require a `--confirm-group-change` flag to proceed.
