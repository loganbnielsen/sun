## Findings

### [EXP-001] — Stage 1: No binary distribution; full OCaml toolchain required
* **Stage:** 1 Installation
* **Gate:** Docs + Reproduction
* **Severity:** Blocker
* **Description:** There is no pre-built `sun` binary. Getting the CLI requires: installing `opam`, setting up OCaml 5.4.1, installing `librdkafka-dev`, running `opam install . --deps-only`, and running `dune build cli/`. This is a multi-step OCaml toolchain setup that requires language-specific knowledge entirely unrelated to using the platform.
* **Impact:** A startup engineer who wants to evaluate Sun must become an OCaml environment expert before writing a single line of business logic. The install friction alone breaks the "zero to running service" promise. Engineers unfamiliar with opam will be blocked at step zero.
* **Remediation:** Publish prebuilt binaries (Linux x86_64, macOS arm64) via GitHub Releases. Add a one-liner install to the README: `curl -sSL https://github.com/sun/releases/latest/download/sun-linux-x86_64 -o /usr/local/bin/sun && chmod +x /usr/local/bin/sun`. OCaml and dune remain required for building workspace code, but the CLI itself should not need them.

### [EXP-002] — Stage 3: `sun dev run` command is missing
* **Stage:** 3 Local Development
* **Gate:** Docs + Reproduction
* **Severity:** Blocker
* **Description:** The UX promise in `UX_AUDIT.md` includes `sun dev run` as the command to start workspace services locally after `sun dev up`. This command does not exist. `sun dev` has three subcommands: `up`, `down`, `status`.
* **Impact:** After `sun dev up` starts infrastructure, the engineer has no Sun command to run their services locally. The only paths are: (a) run `sun up` to build Docker images and deploy to k3d, then forward ports manually; or (b) run `dune exec app/.../bin/main.exe` per service with manual env var injection. Both paths require knowledge the engineer shouldn't need.
* **Remediation:** Implement `sun dev run` to start all workspace binaries (using `dune exec`) in parallel, injecting the dev environment variables (KAFKA_BROKERS, POSTGRES_URL, LOKI_URL, etc.) from the addresses printed by `sun dev up`. Tail combined stdout/stderr to one terminal with per-service prefixes.

### [EXP-003] — Stage 2/3: Generated workspace README instructs manual bash scripts
* **Stage:** 2 Project Creation → 3 Local Development
* **Gate:** Reproduction
* **Severity:** Medium
* **Description:** The README template generated by `sun new workspace` (in `cmd_new.ml`, `tpl_readme`) contains a "Run locally" section that instructs: `bash <path-to-sun>/platform/local/scripts/ensure-broker.sh`. This requires the engineer to know the location of the Sun framework repo on disk. The generated README's CLI commands section does show `sun dev up`, but the "Run locally" section contradicts it with manual scripts.
* **Impact:** An engineer who reads their generated `README.md` (the natural first step) finds contradictory instructions: the "Run locally" section uses bash scripts while the "CLI commands" section shows `sun dev up`. Following the first section requires knowing where the Sun repo is, which is not stated.
* **Remediation:** Remove the "Run locally" bash-script section from `tpl_readme`. Replace it with a single `sun dev up` instruction. The generated README should never reference paths outside the workspace.

### [EXP-004] — Stage 4: `sun cloud init` command is missing
* **Stage:** 4 Cloud Setup
* **Gate:** Docs + Reproduction
* **Severity:** Blocker
* **Description:** `sun cloud init` does not exist. The Terraform modules in `platform/infra/aws/` and `platform/infra/gcp/` are present but have no documentation and require the engineer to run `terraform init && terraform apply` directly, knowing which variables to supply.
* **Impact:** After validating locally, an engineer wanting to deploy to a real cloud environment must learn Terraform, understand VPC networking, configure IAM credentials, and navigate provider-specific Terraform docs — all to accomplish what the platform promises to abstract. The gap between `sun dev up` (zero Terraform knowledge) and cloud provisioning (full Terraform knowledge) is unbridgeable with the current tooling.
* **Remediation:** Implement `sun cloud init --aws` / `sun cloud init --gcp` that wraps `terraform init && terraform apply` with the correct variable inputs, printing the provisioned endpoints at completion. As a first step, add documentation to README explaining the manual Terraform path with exact variable values.

### [EXP-005] — Stage 5: Service access requires manual `kubectl port-forward` after `sun up`
* **Stage:** 5 First Deploy
* **Gate:** Reproduction
* **Severity:** High
* **Description:** After `sun up` deploys services to the local cluster, the engineer must run `kubectl port-forward svc/<name> -n <ns> 8080:80` in a separate terminal to access the service. `sun up` prints this hint for `Svc` primitives. However, `sun status` (which the README suggests running after deploy) looks for `NodePort` services to print the same hint — but AUDIT-004 changed all services to `ClusterIP`, so the hint is never printed from `sun status`.
* **Impact:** An engineer following the Quickstart will run `sun status`, see running pods but no port-forward hint, and be stuck. They must know kubectl to reach their own service.
* **Remediation:** (a) Fix `cmd_status.ml` to query `ClusterIP` services rather than `NodePort` services for the port-forward hint, since AUDIT-004 eliminated NodePort. (b) Implement `sun dev forward <service>` or have `sun up` automatically start port-forwards (similar to how `sun dev up` starts infrastructure port-forwards) and print the localhost URL directly.

### [EXP-006] — Stage 5: `sun deploy` / `sun up` split is unexplained and confusing
* **Stage:** 5 First Deploy
* **Gate:** Docs
* **Severity:** Medium
* **Description:** Two deploy commands exist with overlapping names and distinct semantics: `sun up` builds images and deploys (for local use); `sun deploy` skips the build and deploys pre-built images (for CI). The UX promise in `UX_AUDIT.md` uses `sun deploy` to mean "ship it", but `sun deploy` requires images already in a registry — running it locally on a fresh workspace yields a confusing failure if images haven't been pushed.
* **Impact:** An engineer following the promise `sun deploy → I can ship` will run `sun deploy` locally and either get an error (images don't exist in a registry) or silently deploy a stale image. The README Quickstart uses `sun up`, but the UX promise and the generated GitHub Actions workflow use `sun deploy` — the distinction is never explained in user-facing docs.
* **Remediation:** Add a callout in README that distinguishes `sun up` (local dev, builds images) from `sun deploy` (CI, uses pre-built images). Long-term: consider merging these into `sun deploy` with an optional `--build` flag.

---

### [EXP-007] — Stage 6: `sun rollback` command is missing
* **Stage:** 6 Shipping a Change
* **Gate:** Docs + Reproduction
* **Severity:** High
* **Description:** `sun rollback` does not exist. The only rollback surface is `sun migrate rollback`, which prints "not yet implemented" and exits with code 1. There is no way to roll back a broken deploy using Sun commands.
* **Impact:** An engineer who ships a breaking change must know `kubectl rollout undo deployment/<name> -n <namespace>` to recover. Finding the right deployment name and namespace requires knowledge of Sun's naming conventions (`<workspace>-<domain>`, underscores converted to hyphens) that is not documented in the README or TUTORIAL.md.
* **Remediation:** Implement `sun rollback [<service>]` that runs `kubectl rollout undo deployment/<k8s-name> -n <workspace>-<domain>` for each service (or a specified one), using the same service-discovery logic already in `discover_services`.

---

### [EXP-008] — Stage 7: `sun logs <service>` command is missing
* **Stage:** 7 Day-2 Operations
* **Gate:** Docs + Reproduction
* **Severity:** High
* **Description:** `sun logs <service>` does not exist. The CLI has no command for streaming service logs. After deploying, an engineer who wants to see log output must know `kubectl logs -n <workspace>-<domain> deployment/<name> -f` or open Grafana/Loki.
* **Impact:** The "no kubectl required" promise breaks at the first production debugging session. Finding the right namespace requires knowledge of Sun's naming convention. An engineer who hasn't read the source will try `sun logs charge_svc`, see "unknown subcommand", and be stuck.
* **Remediation:** Implement `sun logs <service>` that resolves the k8s namespace from the workspace name and service name, then tails the pod logs. Use the same service-discovery logic as `sun status` and `discover_services`. Support `-f`/`--follow` flag.
