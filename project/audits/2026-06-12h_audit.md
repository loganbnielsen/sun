## Section Results

### §1 — Local Developer Loop

**Zero-Knowledge Onboarding:** PASS for code compilation path. Two new regressions found:

1. **Dockerfile template missing opam packages** (AUDIT-037): The generated Dockerfile at `tpl_dockerfile` (lines 430–433 of `sun_cli_cmd_new.ml`) installs `eio eio_main cohttp-eio yojson cmdliner base64 uri cstruct mtime tls-eio x509 domain-name caqti-eio caqti-driver-postgresql` but omits `otoml` and `ptime`. These packages are required at build time: `ptime` is a direct dependency of `kafka-eio-service/lib/kafka_service.ml` (used in `tls_authenticator` for TLS certificate validation), and `otoml` is a dependency of `cli/sun/lib/sun_cli_toml.ml` (used for `sun.toml` parsing). Both modules are in the vendored framework that gets compiled inside the Docker container. Docker builds of scaffolded workspaces will fail with `Library "ptime" not found` or `Library "otoml" not found`.

2. **Stale `ocaml/setup-ocaml@v2` in deploy CI template** (AUDIT-038): `tpl_github_deploy` uses `ocaml/setup-ocaml@v2` with `ocaml-compiler: "5.4"`, while the main `tpl_github_ci` template correctly uses `ocaml/setup-ocaml@v3` and `ocaml-compiler: "5.4.1"`. The v2 action was superseded by v3. Both templates are written to the workspace at `new_workspace`. The inconsistency means the deploy-only workflow may behave differently in GitHub Actions.

**Atomic CLI Transactions:** PASS. `cmd_up.ml` exits non-zero on all failure paths.

**Hermetic Test Harnesses:** PASS. No ambient sleeps.

## Findings

### AUDIT-037 — Dockerfile template missing `otoml` and `ptime` from opam install

* **Category:** DX
* **Severity:** High
* **Location:** `cli/sun/lib/sun_cli_cmd_new.ml` (lines 430–433, `tpl_dockerfile`)
* **Status:** Open
* **Description:** The `tpl_dockerfile` template's `RUN opam install` step does not include `otoml` or `ptime`. Both are required for the vendored framework source that is compiled inside the container:
  - `ptime` is a direct dependency of `kafka-eio-service/lib/kafka_service.ml` (used by `tls_authenticator` for certificate validity time checks).
  - `otoml` is a dependency of `cli/sun/lib/sun_cli_toml.ml`, which `sun-svc`, `sun-worker`, and `sun-fn` transitively link.
  Any Docker build of a scaffolded workspace will fail with `Error: Library "ptime" not found` or `Error: Library "otoml" not found` when `dune build` runs inside the container.
* **Impact:** Every workspace scaffolded by `sun new workspace` will produce Docker images that fail to build until the user manually edits the generated Dockerfile. This breaks the zero-knowledge onboarding guarantee.
* **Remediation:** Add `otoml ptime` to the `opam install` line in `tpl_dockerfile`:
  ```
  RUN opam install -y --no-self-upgrade \
      eio eio_main cohttp-eio yojson cmdliner base64 uri cstruct mtime \
      tls-eio x509 domain-name ptime otoml \
      caqti-eio caqti-driver-postgresql
  ```

### AUDIT-038 — `tpl_github_deploy` uses stale `ocaml/setup-ocaml@v2` and imprecise OCaml version pin

* **Category:** DX
* **Severity:** Medium
* **Location:** `cli/sun/lib/sun_cli_cmd_new.ml` (lines 357–359, `tpl_github_deploy`)
* **Status:** Open
* **Description:** The `tpl_github_deploy` CI template uses `ocaml/setup-ocaml@v2` with `ocaml-compiler: "5.4"`, while `tpl_github_ci` (the main CI template written to the same workspace) correctly uses `ocaml/setup-ocaml@v3` with `ocaml-compiler: "5.4.1"`. Both templates are emitted to `.github/workflows/` during `sun new workspace`. The `@v2` action is superseded and may behave inconsistently across GitHub runner environments; using `"5.4"` instead of `"5.4.1"` can resolve to a different patch release, causing a build mismatch between the two CI workflows.
* **Impact:** A workspace owner relying on the generated deploy workflow may see CI inconsistencies or build failures, eroding trust in Sun's generated CI setup.
* **Remediation:** Update `tpl_github_deploy` to use `ocaml/setup-ocaml@v3` and `ocaml-compiler: "5.4.1"` to match `tpl_github_ci`.
