## Findings

### EXP-017 — `sun dev run` implemented but undocumented in user-facing guides

* **Stage:** 3 Local Development
* **Gate:** Docs
* **Severity:** Medium
* **Status:** Open
* **Description:** `sun dev run` was implemented as part of EXP-002. It discovers services under `app/<domain>/<name>/`, builds them with `dune build`, and spawns each as a native process with the dev environment variables (KAFKA_BROKERS, POSTGRES_URL, LOKI_URL) injected. Output is multiplexed with `[domain/name]` prefixes and all children are killed on Ctrl-C. The command appears in the README.md Status table only as a parenthetical `(sun dev up/down/status/run)` with no explanation. It does not appear in the Quickstart, in TUTORIAL.md, or in any guide section that explains the local development loop.
* **Impact:** Engineers who discover `sun dev run` via `--help` have no context for when to use it vs `sun up` — the two commands serve different purposes (native process fast iteration vs containerised smoke test). Engineers who follow only the tutorial skip the fast inner dev loop entirely, rebuilding and re-deploying Docker images for every code change.
* **Remediation:**
  1. Add a "Local iteration" subsection to TUTORIAL.md Part 1 or Part 3 explaining `sun dev run`: what it does, when to use it (rapid code-change iteration without a Docker rebuild cycle), and how it differs from `sun up` (native processes vs containers, same infra via port-forwards).
  2. Add `sun dev run` to the README.md Quickstart sequence alongside `sun dev up` with a one-line explanation.
