## Findings

### DOGFOOD-010 — local deploy starts with empty database credentials and silently drops persistence

* **Category:** Local Developer Loop / Data Integrity
* **Severity:** High
* **Location:** `cli/sun/bin/cmd_up.ml` local-cluster credential exemption; `cli/sun/lib/sun_cli_deployment_plan.ml` Secret rendering; generated service/worker templates in `cli/sun/lib/sun_cli_cmd_new.ml`
* **Description:** `sun up` on a known local k3d context allows missing `POSTGRES_URL`, but the rendered workload Secrets contain `POSTGRES_URL: ""`. Generated workloads start anyway. The service accepts writes and the worker acks messages without a database pool, so the end-to-end path appears healthy while persistence is skipped.
* **Impact:** A new user can deploy a fresh local workspace, receive successful HTTP responses, and never see worker-written notifications. Kafka messages can be acknowledged without the expected DB side effect.
* **Ticket:** `project/tickets/READY_FOR_ENGINEERING/DOGFOOD-010.md`

The remaining non-dogfood production issue is the existing `AUDIT-026` non-hermetic Dockerfile ticket, which is already in review. The local dogfood pass also reproduced the stale port-forward behavior tracked by `UX-002`; that is recorded in `project/dogfood/RUN_2026-06-12.md` and appended to the existing ticket rather than duplicated.
