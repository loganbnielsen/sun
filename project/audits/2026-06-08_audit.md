## Findings

### [AUDIT-001] — Transactional Stubs Block the OCaml Domain Lock
* **Category:** Runtime Performance
* **Severity:** High
* **Status:** Resolved
* **Location:** `integrations/kafka/kafka-eio-core/lib/kafka_stubs.c` (Lines 600–704)
* **Description:** `init_transactions`, `begin_transaction`, `commit_transaction`, `abort_transaction`, and `send_offsets_to_transaction` called blocking librdkafka functions without releasing the OCaml domain lock, freezing the Eio scheduler for the duration of any broker round-trip.
* **Impact:** Periodic scheduler stalls during transaction commits; liveness probes would timeout under broker slowness. Bug is invisible in local dev and only manifests under production load.
* **Remediation:** Applied `caml_release_runtime_system()` / `caml_acquire_runtime_system()` to all five stubs, matching the pattern used by `flush`, `consumer_poll`, and `consumer_close`.

### [AUDIT-002] — `commit_message` Blocks the Domain Lock
* **Category:** Runtime Performance
* **Severity:** High
* **Status:** Resolved
* **Location:** `integrations/kafka/kafka-eio-core/lib/kafka_stubs.c` (Lines 562–595)
* **Description:** `ocaml_rd_kafka_commit_message` called synchronous `rd_kafka_commit` with the domain lock held. Every `ack()` call froze the scheduler for the broker's synchronous commit round-trip.
* **Impact:** Workers processing messages at any non-trivial rate experienced degraded throughput and scheduler latency spikes proportional to broker commit latency.
* **Remediation:** Added `caml_release_runtime_system()` before both `rd_kafka_commit` call sites and `caml_acquire_runtime_system()` after.

### [AUDIT-003] — Database Password in Plaintext ConfigMap
* **Category:** Security
* **Severity:** Critical
* **Status:** Resolved
* **Location:** `cli/sun/lib/sun_cli_manifest.ml`
* **Description:** `POSTGRES_URL` with an embedded password was placed in a Kubernetes `ConfigMap`, stored unencrypted in etcd and readable by any pod in the namespace with basic RBAC.
* **Impact:** Any compromised pod, CI pipeline, or misconfigured RBAC policy would expose the database password in plaintext. Fails PCI-DSS, SOC 2, and any security audit.
* **Remediation:** Added `secret_doc` generating a Kubernetes `Secret` with `stringData`. Credentials are sourced via `secretRef` in Deployment envFrom. `POSTGRES_URL` uses a `CHANGE_ME` placeholder to force explicit operator substitution before deploying.

### [AUDIT-004] — `NodePort` Exposed for All Production Services
* **Category:** Security
* **Severity:** High
* **Status:** Resolved
* **Location:** `cli/sun/lib/sun_cli_manifest.ml`
* **Description:** Generated `Service` resources used `type: NodePort`, binding a port on every cluster node's host interface. In cloud environments this typically opens that port to the internet and bypasses ingress-level TLS termination.
* **Impact:** Startups would unknowingly expose their HTTP API directly to the public internet on a random high port, bypassing their ingress controller's TLS and rate limiting.
* **Remediation:** Changed to `type: ClusterIP`. Added `ingress_doc` generating an `Ingress` resource with `nginx.ingress.kubernetes.io/ssl-redirect: "true"` for `Svc` primitives.

### [AUDIT-005] — Silent Offset Commit Gap: `ack()` Not Enforced
* **Category:** Data Integrity
* **Severity:** Medium
* **Status:** Resolved
* **Location:** `integrations/kafka/kafka-eio-consumer/lib/kafka_consumer.ml` (Lines 142–164)
* **Description:** A handler returning `Ok ()` without calling `ack()` would silently never commit offsets, causing unbounded message replay after every restart with no observable error.
* **Impact:** Workers appeared to work (messages processed, no errors logged) but replayed the entire message history after every deploy.
* **Remediation:** Added an `acked` ref in `consume` and `consume_partitioned`. Both emit a structured `eprintf` warning when a handler returns `Continue` or `Stop` without having called `ack()`.

### [AUDIT-006] — Shell Injection via Unquoted Temp Path
* **Category:** Security
* **Severity:** Medium
* **Status:** Resolved
* **Location:** `cli/sun/lib/sun_cli_manifest.ml` (Lines 375, 386, 390)
* **Description:** Temp file paths were interpolated into `Sys.command` strings without quoting. Paths containing spaces or shell metacharacters would split into multiple arguments or execute arbitrary shell code.
* **Impact:** Low probability in standard environments, but a shell injection pattern in the CLI that generates and applies production manifests violates the "secure by default" contract.
* **Remediation:** Wrapped all three `Sys.command` interpolations with `Filename.quote`.

### [AUDIT-007] — `fd_ptr` Memory Leak on Producer Init Failure
* **Category:** Runtime Performance
* **Severity:** Medium
* **Status:** Resolved
* **Location:** `integrations/kafka/kafka-eio-core/lib/kafka_stubs.c` (Lines 144–165)
* **Description:** When `rd_kafka_new` returned NULL (e.g., broker unreachable at startup), the heap-allocated `fd_ptr` opaque pointer was leaked. librdkafka destroys the conf but not the opaque.
* **Impact:** Transient broker unavailability during startup (common in `sun dev up` before Redpanda is ready) would leak a heap allocation on each failed attempt.
* **Remediation:** Added `free(fd_ptr)` before returning the error on `rd_kafka_new` failure. `free(NULL)` is a no-op so the consumer path is safe.

### [AUDIT-008] — No `NetworkPolicy` Generated
* **Category:** Security
* **Severity:** Low
* **Status:** Resolved
* **Location:** `cli/sun/lib/sun_cli_manifest.ml`
* **Description:** No `NetworkPolicy` was generated, leaving all pods with unrestricted ingress from any namespace and unrestricted egress to any endpoint.
* **Impact:** A compromised pod could reach any other service in the cluster, any cloud metadata API, or any external endpoint without restriction. Flagged by SOC 2 and cloud-provider security reviews.
* **Remediation:** Added `network_policy_doc` generating a `NetworkPolicy` for every workload. Ingress restricted to ingress-nginx and in-cluster pods; egress restricted to DNS + Redpanda, PostgreSQL, and monitoring namespaces.

### [AUDIT-009] — Missing `seccompProfile` in Pod Security Contexts
* **Category:** Security
* **Severity:** Low
* **Status:** Resolved
* **Location:** `cli/sun/lib/sun_cli_manifest.ml`
* **Description:** Pod security contexts correctly set `runAsNonRoot`, `runAsUser`, and `runAsGroup`, but `seccompProfile` was absent. Pods ran with the `Unconfined` profile, able to invoke any Linux syscall.
* **Impact:** Flagged as a finding by all major Kubernetes security scanners (Trivy, Falco, kube-bench). Would surface in any production security review.
* **Remediation:** Added `seccompProfile: type: RuntimeDefault` to the pod-level security context in both `deployment_doc` and `cronjob_doc`.

### [AUDIT-010] — Decode Errors Silently Acked With No Observable Signal
* **Category:** Data Integrity
* **Severity:** Low
* **Status:** Resolved
* **Location:** `integrations/kafka/kafka-eio-service/lib/kafka_service.ml` (Lines 333–336)
* **Description:** `default_on_decode_error` acked and discarded malformed messages with only a bare `eprintf` line. No Prometheus counter, no dead-letter topic, no alertable signal. A schema evolution mistake would silently drop messages in production with no dashboard visibility.
* **Impact:** A startup debugging a schema mismatch would have no observability into how many messages were dropped or when the divergence began.
* **Remediation (applied):** `default_on_decode_error` now emits a structured log line with error context.
* **Remaining gap:** No Prometheus counter for decode errors; `on_decode_error` callback receives only the error string, not the raw message bytes, so users cannot forward the payload to a dead-letter topic.

### [AUDIT-011] — Scaffolded Worker Templates Call `ack()` Before Business Logic
* **Category:** Data Integrity
* **Severity:** Critical
* **Status:** Open
* **Location:** `cli/sun/bin/cmd_new.ml` — `ws_worker_ml` (~line 364) and `worker_lib_ml` (~line 500)
* **Description:** Both generated worker templates call `ack()` as the first line of the handler, before the DB insert and any side effect. If the worker crashes between `ack()` and the DB write, the message is permanently lost. This is the "ack-before-processing" anti-pattern.
* **Impact:** Every workspace scaffolded by `sun new` ships with at-most-once semantics in the handler template, directly contradicting the framework's at-least-once guarantee. The developer must know to move `ack()` themselves — there is no compiler or runtime warning that the generated code is wrong.
* **Remediation:** Move `ack()` to after all side effects succeed:
  ```ocaml
  let handle (msg : Message.t) ~ack ~trace_ctx:_ =
    match Notification.insert pool ... with
    | Ok ()   -> ack (); Ok ()
    | Error e -> Error (Storage_error.to_string e)  (* don't ack: will retry *)
  ```

### [AUDIT-012] — `Retry_topics` Path Silently Drops Messages on Producer Failure
* **Category:** Data Integrity
* **Severity:** High
* **Status:** Open
* **Location:** `integrations/kafka/kafka-eio-service/lib/kafka_service.ml` (Lines 446–449, 504, 559–564)
* **Description:** `publish_raw` calls `ignore(Kafka_producer.produce_await ...)` and then unconditionally calls `ack()`. If the publish to the retry or DLQ topic fails (broker unavailable, queue full), the message is silently acked — not on the retry topic, not on the DLQ, permanently gone. No error is returned, no metric incremented.
* **Impact:** Under broker degradation — exactly when retry topics matter most — messages vanish instead of being retried. The failure is undetectable from dashboards.
* **Remediation:** Check the `produce_await` result before acking:
  ```ocaml
  (match Kafka_producer.produce_await svc.producer
           ~topic:target_topic ~value:raw_bytes ~headers:new_headers () with
  | Ok ()  -> ack ()
  | Error e ->
    Printf.eprintf "sun-worker: PUBLISH_FAILED target=%s error=%s — not acking\n%!"
      target_topic (Kafka_error.to_string e))
  ```

### [AUDIT-013] — Schema Registry HTTP Client Does Not Support TLS
* **Category:** Security / Reliability
* **Severity:** Medium
* **Status:** Open
* **Location:** `integrations/kafka/kafka-eio-service/lib/kafka_service.ml`, `parse_base_url` (Lines 38–47)
* **Description:** `parse_base_url` strips only the `http://` prefix. An `https://` URL is passed through unchanged, causing the entire URL string to be used as the hostname in the TCP connect call. The connection fails with a confusing DNS error.
* **Impact:** Every managed Kafka offering (Confluent Cloud, MSK, Redpanda Cloud) requires HTTPS for schema registry. This silently breaks in every real cloud deployment.
* **Remediation (short-term):** Detect `https://` at startup and fail with a clear message:
  ```ocaml
  if String.length url >= 8 && String.sub url 0 8 = "https://" then
    failwith "kafka_service: HTTPS schema registry not yet supported; \
              set SCHEMA_REGISTRY_URL to an http:// address"
  ```
  **Remediation (long-term):** Add TLS support via Eio's `Net.connect` with a TLS context.

### [AUDIT-014] — `pause_partition`/`resume_partition` Missing `CAMLparam`/`CAMLreturn`
* **Category:** Runtime Safety
* **Severity:** Low
* **Status:** Open
* **Location:** `integrations/kafka/kafka-eio-core/lib/kafka_stubs.c` (Lines 845–866)
* **Description:** `ocaml_rd_kafka_pause_partition` and `ocaml_rd_kafka_resume_partition` do not use `CAMLparam`/`CAMLreturn`. Safe today because neither makes any OCaml allocations. Any future addition of a diagnostic string or return value will silently introduce a GC safety bug.
* **Impact:** Latent correctness risk invisible until a future change triggers it. Every other stub in the file uses correct macro discipline; these two are the exception.
* **Remediation:**
  ```c
  value ocaml_rd_kafka_pause_partition(value handle_v, value topic_v, value part_v) {
    CAMLparam3(handle_v, topic_v, part_v);
    /* ... unchanged ... */
    CAMLreturn(Val_unit);
  }
  ```
