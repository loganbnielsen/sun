## Stage Results

**Stage 1 — Installation: PASS.** README.md Quickstart shows a single `curl | tar xz` install for binary users. Prerequisites listed clearly. `SUN_HOME` contributor path documented. No changes since previous audit. Both gates pass.

**Stage 2 — Project Creation: PASS.** EXP-018 is resolved: TUTORIAL.md now correctly states "26 files" and the generated workspace `README.md` (`tpl_readme`) now includes `test/`, `.dockerignore`, and `db/migrations/*.down.sql` in the Project layout section. The tree listing in TUTORIAL Part 2 matches the actual scaffold output. Both gates pass.

**Stage 3 — Local Development: FAIL.** Docs gate partially fails.

`sun dev up` and `sun dev run` are documented and work correctly (EXP-017 fix holds). However, the documentation for adding a new service via `sun new svc`, `sun new worker`, or `sun new fn` says the generated code "compiles immediately and integrates with the existing observability and deployment stack" — but the generated `bin/main.ml` for all three primitives contains **no observability wiring**:

- `sun new svc` generates `Service.run Handler.routes ~env ()` — no `~ot`, no Loki backend, no Prometheus
- `sun new worker` generates `W.run ~env ~config ()` — no `~ot`, no Loki, no Prometheus, no Kafka security config
- `sun new fn` generates `F.run ~env ()` — no `~pushgateway_url`, no observability

Contrast with the workspace scaffold (`sun new workspace`), which correctly wires `LOKI_URL`, `Obs_loki`, `Obs_prometheus`, `Kafka_service.config_of_env()`, and passes `~ot` to all three primitives. TUTORIAL.md Part 7 says each new component "integrates with the existing observability" but never shows the wiring steps that achieve this. The section "How observability wiring works" (after Part 7) shows the full pattern for the workspace svc, but there is no instruction to replicate it when adding a new service with `sun new`.

A startup engineer who follows TUTORIAL Part 7 to add a new worker will have a service that compiles and runs but produces no Loki logs and no `sun_worker_messages_total` metric — contradicting the claim that it "integrates with the existing observability stack."

**Stage 4 — Cloud Setup: FAIL.** Docs gate partially fails.

EXP-019 is resolved: TUTORIAL.md Part 8 now shows `sun cloud init --aws` / `sun cloud init --gcp` as the primary path. Both README and TUTORIAL document `sun cloud init` correctly.

However, a new gap remains: `sun cloud init` prints a `kubeconfig_command` output line (e.g. `aws eks update-kubeconfig --region us-east-1 --name acme-prod`) but **does not run it** and **provides no instruction to run it** before the next step. The text continues directly to "Install platform components" then to `sun deploy`. An engineer who does not notice the `kubeconfig_command` output and run it manually will find `sun status` and `sun deploy` failing because `kubectl` has no cluster context. This breaks the Stage 4 invariant: "After the command completes, `sun status` shows a reachable cluster with no manual kubeconfig setup."

The gap is minimal: one sentence of instruction and/or auto-running the kubeconfig command from `cmd_cloud.ml` would close it.

**Stage 5 — First Deploy: FAIL.** Reproduction gate fails on one invariant.

`sun deploy` is implemented and documented with all required flags (`--image-tag`, `--registry`, `--emit-to`, `--dry-run`). CI workflow examples exist. However, the Stage 5 invariant states: "The command prints the URL of the deployed service when it completes." `sun deploy` prints "Done. N service(s) deployed. Run 'sun status' to check pod health." — it does not print the service URL. The engineer must run a separate `sun status` to discover the endpoint. This is a minor but measurable gap against the invariant.

**Stage 6 — Shipping a Change: PASS.** EXP-020 is resolved: `sun rollback` now reads `sun.toml` per service and dispatches to `kubectl argo rollouts undo` for Argo Rollouts services, with a clear actionable error if the plugin is missing. Both gates pass.

**Stage 7 — Day-2 Operations: FAIL.** Reproduction gate partially fails.

`sun logs`, `sun migrate`, and `sun status` are all implemented and documented. However, two invariants are not met:

1. **`sun status` does not show version/image tag.** The invariant states "shows health, version, and endpoint for every deployed service." `sun status` runs `kubectl get pods -n <ns>` (which shows NAME/READY/STATUS/RESTARTS/AGE) plus a port-forward URL for HTTP services. It does not show the deployed image tag or version. A startup engineer cannot confirm which version is running without additional kubectl knowledge.

2. **`sun logs` fails for `fn` services.** `sun logs` checks for a `Deployment` resource (`kubectl get deployment/<name> -n <ns>`) before streaming. `fn` services are rendered as Kubernetes `CronJob` resources, not `Deployment` objects. `sun logs billing/invoice` will always fail with "Service not found in namespace…" even when the CronJob exists and has completed runs. Neither README, TUTORIAL, nor `sun logs --help` documents this limitation.

**Stage 8 — Domain Event Flow: PASS.** `sun new event` documented, generates stub under `events/<team>/`. Schema compatibility via `test/test_schemas.ml` documented in TUTORIAL Part 7. `sun new worker` flow documented. Both gates pass.

**Stage 9 — AI-Agent Working Surface: FAIL.** Docs gate partially fails.

The generated workspace (`sun new workspace`) has predictable edit points (`events/`, `app/`, `db/migrations/`, `lib/`), a good workspace `README.md`, and `test/test_schemas.ml` for schema gates. Framework-owned concerns are separated from business logic. This aspect remains strong.

However, the `examples/pluto/` reference workspace — which exists in the repo and would be read by any AI agent exploring the codebase — is **significantly out of sync** with the current `sun new workspace` output:

- Missing `dune-project` (workspace will not build without it)
- Missing `test/test_schemas.ml` and `test/dune` (schema compatibility gate)
- Missing `.dockerignore` and `.github/workflows/`
- Missing `db/migrations/0001_notifications.down.sql`
- `README.md` uses pre-CLI commands (`ensure-broker.sh`, raw `dune exec`) rather than `sun dev up` / `sun dev run`
- Missing `vendor/` symlinks documentation (the workspace only builds via `SUN_HOME` or tarball bundle)

An AI agent working in this repo that reads `examples/pluto/` as a reference for workspace conventions will produce structurally incomplete scaffolding and incorrect CLI usage guidance.

## Findings

### [EXP-021] — Stage 5 / `sun deploy` does not print the service URL on completion; Stage 7 / `sun status` does not show deployed image version

* **Stage:** 5 First Deploy / 7 Day-2 Operations
* **Gate:** Reproduction
* **Severity:** Low
* **Description:** Two related gaps. (1) `sun deploy` completes with "Done. N service(s) deployed. Run 'sun status' to check pod health." but does not print the service URL. The Stage 5 invariant requires the command to print the deployed service URL on completion. (2) `sun status` runs `kubectl get pods -n <ns>` (NAME/READY/STATUS/RESTARTS/AGE) but does not show the deployed image tag. The Stage 7 invariant requires "health, version, and endpoint for every deployed service."
* **Impact:** After `sun deploy`, the engineer must run a separate command to discover the endpoint. After `sun status`, they cannot confirm which version is live without kubectl knowledge — making it harder to verify a rollout completed correctly.
* **Remediation:** (1) In `cmd_deploy.ml`, after deploying, query `kubectl get svc -n <ns>` for each HTTP service and print its port-forward hint (same logic as `cmd_status.ml`). (2) In `cmd_status.ml`, use `kubectl get pods -n <ns> -o jsonpath='{.items[*].spec.containers[0].image}'` or add `-o wide` / `--output=custom-columns=NAME:.metadata.name,READY:.status.conditions[?(@.type==\"Ready\")].status,IMAGE:.spec.containers[0].image` to include the image tag in the status output.

### [EXP-022] — Stage 3 / `sun new svc/worker/fn` generates observability-dark entrypoints

* **Stage:** 3 Local Development
* **Gate:** Docs + Reproduction
* **Severity:** High
* **Description:** `sun new svc`, `sun new worker`, and `sun new fn` each generate a minimal `bin/main.ml` with no observability wiring: no `LOKI_URL` check, no `Obs_loki` backend, no `Obs_prometheus`, no `Kafka_service.config_of_env()`, and no `~ot` argument passed to the framework. The workspace scaffold (`sun new workspace`) wires all of these correctly, but new primitives added to an existing workspace via `sun new` do not. TUTORIAL.md Part 7 says these commands generate code that "integrates with the existing observability and deployment stack" but this claim is false for the generated entrypoints.
* **Impact:** A startup engineer who follows the tutorial to add a second service or worker will deploy a service that produces no Loki logs and no `sun_worker_messages_total` / `sun_svc_requests_total` metrics. The engineer will see nothing in Grafana for the new service, contradicting the promise that observability is "wired automatically." They will need to manually copy the observability wiring from the workspace svc, which requires understanding the pattern in advance.
* **Remediation:** (1) Update the generic templates for `svc_bin_ml`, `worker_bin_ml`, and `fn_bin_ml` in `sun_cli_cmd_new.ml` to include the same observability wiring pattern as `ws_svc_bin_ml` / `ws_worker_bin_ml`. Use `{{name}}`, `{{domain}}`, `{{lib}}` substitution variables to set the service label. For the worker template, also add `Kafka_service.config_of_env()` and `~ot`. For the fn template, add `~pushgateway_url:(Sys.getenv_opt "PUSHGATEWAY_URL")`. (2) Update TUTORIAL.md Part 7's descriptions of `sun new svc/worker/fn` to note what the engineer needs to add if they want full observability, until (1) is implemented.

### [EXP-023] — Stage 4 / `sun cloud init` output includes kubeconfig command but provides no instruction to run it

* **Stage:** 4 Cloud Setup
* **Gate:** Docs
* **Severity:** Medium
* **Description:** `sun cloud init` prints `kubeconfig_command` (e.g. `aws eks update-kubeconfig --region us-east-1 --name acme-prod`) as part of its Terraform output, but neither `cmd_cloud.ml` runs this command automatically nor do README.md or TUTORIAL.md provide explicit instruction to run it before proceeding to `sun deploy`. The text following the `sun cloud init` output block jumps directly to "Install platform components" (`terraform apply` for `platform/infra/base`). An engineer who misses the `kubeconfig_command` line will find `sun deploy`, `sun status`, and `sun migrate` failing because `kubectl` has no cluster context.
* **Impact:** The Stage 4 invariant "After the command completes, `sun status` shows a reachable cluster with no manual kubeconfig setup" is not met. The engineer must have noticed the `kubeconfig_command` output line and run it manually — knowledge not made explicit anywhere in the primary documentation path.
* **Remediation:** Two options, do one or both: (A) In `cmd_cloud.ml`, after printing the Terraform outputs, parse the `kubeconfig_command` output and run it automatically via `Sys.command`. Print a clear message like "Configuring kubectl…" before running it. (B) In README.md and TUTORIAL.md Part 8, add an explicit post-`sun cloud init` step: "Copy and run the `kubeconfig_command` from the output above to configure kubectl before deploying."

### [EXP-024] — Stage 7 / `sun logs` fails for `fn` (CronJob) services

* **Stage:** 7 Day-2 Operations
* **Gate:** Reproduction
* **Severity:** Medium
* **Description:** `sun logs` checks whether a `Deployment` resource named `<service>` exists in the target namespace before streaming (`kubectl get deployment/<name> -n <ns>`). Services generated by `sun new fn` are rendered as `CronJob` resources, not `Deployment` resources. Running `sun logs billing/invoice` for a deployed fn service will always fail with "Service billing/invoice not found in namespace…" even when the CronJob exists. Neither `sun logs --help`, README.md, nor TUTORIAL.md documents this limitation. The CLI reference table shows `sun logs <service>` generically, implying it works for all service types.
* **Impact:** An engineer who deploys a scheduled function with `sun new fn` and then follows the documented Day-2 operations path by running `sun logs billing/invoice` will receive a confusing "not found" error with no guidance. They must resort to `kubectl logs -n <ns> job/<name>-<hash>` directly, which the platform promise explicitly avoids.
* **Remediation:** Two options, do one or both: (A) Fix `cmd_logs.ml` to detect `fn` services by checking for a `CronJob` when `Deployment` is not found. For CronJobs, find the most recent `Job` pod via `kubectl get pods -n <ns> -l job-name=<name> --sort-by=.status.startTime` and tail its logs. (B) Until (A) is done, add a clear warning: if `kubectl get deployment/<name>` fails, check for a CronJob and print an actionable message: "billing/invoice is a scheduled function — logs are available via: kubectl logs -n <ns> job/<name>-<hash>". Also add a note to README.md §"Streaming logs" and the CLI reference table.
