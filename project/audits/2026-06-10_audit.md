## Findings

### [AUDIT-015] — `POSTGRES_URL` With Embedded Password Flows Into ConfigMap

* **Category:** Security
* **Severity:** High
* **Status:** Open
* **Location:** `cli/sun/lib/sun_cli_manifest.ml` (Lines 97–104, 135–144)
* **Description:** `POSTGRES_URL` with the embedded password `dev` is in `default_cluster_env`, which is written verbatim into the Kubernetes ConfigMap by `configmap_doc`. `secret_doc` was added in the 2026-06-08 fix cycle but is never called from `render` or `render_spec` — it is dead code. The ConfigMap is stored unencrypted in etcd and is readable by any pod in the namespace via `envFrom: configMapRef`.
* **Impact:** Any compromised pod or overly permissive RBAC policy exposes the database password in plaintext. Violates the `Credentials are never in ConfigMaps` invariant. The default password `dev` will be copy-pasted to staging/production by users who follow the scaffold without realising the credential is not production-ready and is in an insecure location.
* **Remediation:** Move `POSTGRES_URL` from `default_cluster_env` to `default_cluster_secrets`. Wire `secret_doc` into `render` and `render_spec` so a `Secret` resource is emitted alongside the `ConfigMap`. The `configmap_doc` should carry only non-sensitive config (brokers, URLs). Remove `POSTGRES_URL` from `render_env_block` in the ConfigMap path.

### [AUDIT-016] — `Secret` Resource Never Emitted; `secret_keys` Path Causes CrashLoopBackOff

* **Category:** Security / Runtime Correctness
* **Severity:** High
* **Status:** Open
* **Location:** `cli/sun/lib/sun_cli_manifest.ml` (Line 148: `secret_doc`), `cli/sun/lib/sun_cli_deployment_plan.ml` (Lines 246–256)
* **Description:** `secret_doc` is declared in `sun_cli_manifest.mli` and defined in `sun_cli_manifest.ml` but is never called from `render`, `render_spec`, or any executor. No `Secret` resource is emitted for any workload. `render_secret_key_refs` correctly generates individual `secretKeyRef` env entries referencing `sun-secrets`, but those entries will fail at pod startup because the Secret does not exist. A workspace operator who follows the documented escape hatch (`secrets = ["POSTGRES_URL"]` in `sun.toml`) will get pods in CrashLoopBackOff with a `secret "sun-secrets" not found` error.
* **Impact:** The secrets mechanism is non-functional. Users who attempt to use `sun.toml` secrets cannot deploy. The framework's security story is compromised because the secret escape hatch silently breaks deployments.
* **Remediation:** Call `secret_doc` from `render_spec` (and `render`) to emit the Secret resource alongside the workload resources. The Secret should be included in `workload_yaml` (or emitted separately). Secret values should be injected by the operator via environment at apply time or via `sun secret set`.

### [AUDIT-017] — Generic `sun new worker` Template Calls `ack()` Before Business Logic

* **Category:** Data Integrity
* **Severity:** Medium
* **Status:** Open
* **Location:** `cli/sun/lib/sun_cli_cmd_new.ml` (`worker_lib_ml` template, Lines 767–770)
* **Description:** The generic worker template used by `sun new worker <domain>/<name>` calls `ack()` as the second statement in the handler — before any side effect — followed directly by `Ok ()`. When a developer adds business logic after `ack()` (following the generated structure), they implement the ack-before-processing anti-pattern. The workspace-specific template (`ws_worker_ml`, used by `sun new workspace`) was correctly fixed: `ack()` is after `Notification.insert`. The generic template was not updated.
* **Impact:** Every service scaffolded with `sun new worker` ships with at-most-once semantics in the handler template. A crash after `ack()` but before the side effect completes permanently loses the message. There is no compiler or runtime warning.
* **Remediation:** Restructure `worker_lib_ml` to place `ack()` after the side effect:
  ```ocaml
  let handle (msg : Message.t) ~ack ~trace_ctx:_ =
    Printf.printf "[{{name}}-worker] received id=%s\n%!" msg.id;
    (* TODO: add side effects here; call ack() only after they succeed *)
    ack ();
    Ok ()
  ```
  Add a comment explaining why `ack()` must come after all side effects.

### [AUDIT-019] — `rollout_doc` References `<name>-secrets` But `secret_doc` Generates `sun-secrets`

* **Category:** Security / Runtime Correctness
* **Severity:** Medium
* **Status:** Open
* **Location:** `cli/sun/lib/sun_cli_manifest.ml` (`rollout_doc`, Line 351)
* **Description:** `rollout_doc` hardcodes `secretRef: name: %s-secrets` where `%s` is the service name (e.g., `charge-svc`), producing `charge-svc-secrets`. The shared secret name constant is `runtime_secret_name = "sun-secrets"`. `secret_doc` generates a Secret named `sun-secrets`. The name mismatch means Argo Rollout deployments will always fail to find their secrets even if `secret_doc` is later wired in. `deployment_doc` correctly uses `render_secret_key_refs` (which references `sun-secrets`), but `rollout_doc` bypasses that and uses a hardcoded different name.
* **Impact:** Argo Rollout workloads (canary and blue-green deployments) that have secrets configured will fail at pod startup with a `secret "<name>-secrets" not found` error. Because `secret_doc` is currently never called (AUDIT-016), this is not yet observable — but it will surface immediately when AUDIT-016 is fixed.
* **Remediation:** Replace the hardcoded `%s-secrets` in `rollout_doc` with `runtime_secret_name` = `"sun-secrets"`. Use `render_secret_key_refs` consistently in both `deployment_doc` and `rollout_doc` instead of the `secretRef: name:` block in `rollout_doc`.

### [AUDIT-020] — `namespace_of` Does Not Lowercase; Uppercase Workspace Names Produce Invalid Namespaces

* **Category:** DX / Runtime Correctness
* **Severity:** Medium
* **Status:** Open
* **Location:** `cli/sun/lib/sun_cli_deployment_plan.ml` (Lines 137–141)
* **Description:** `k8s_name_of` maps underscores to hyphens but does not lowercase. `namespace_of` calls `k8s_name_of` on both workspace and domain. Kubernetes namespace names must match the RFC-1123 DNS label pattern: lowercase alphanumeric + hyphens. A workspace directory named `MyApp` or `Acme_Corp` would produce a namespace like `MyApp-payments` which the Kubernetes API server rejects. The `sun new workspace` path normalizes names via `Sun_cli_scaffold.normalize` (which lowercases), but `workspace_name()` in `cmd_up.ml` uses `Filename.basename (Sys.getcwd ())` — the raw directory name without normalization. The `kubectl apply --dry-run=server` step catches this in the live path, but the GitOps emit path (`--emit-to`) silently writes invalid YAML.
* **Impact:** Users who create a workspace directory with mixed case will get a confusing `kubectl apply` failure without a clear error message from the `sun` side. The GitOps path silently emits invalid manifests that Argo CD will reject.
* **Remediation:** Apply `String.lowercase_ascii` inside `k8s_name_of`, or add a validation step in `cmd_up.ml` and `cmd_deploy.ml` that rejects workspace names with uppercase letters before generating manifests.
