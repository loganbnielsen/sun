## Stage Results

**Stage 1 — Installation: PASS.** README.md Quickstart shows a single `curl | tar xz` install for binary users. Prerequisites listed clearly. `SUN_HOME` contributor path documented. No changes since previous audit. Both gates pass.

**Stage 2 — Project Creation: FAIL.** Docs gate fails. `sun new workspace` now generates **26 files** (CLI prints "Done. 26 files generated.") but TUTORIAL.md line 133 states "This generates 22 files." and the tree listing that follows omits four generated files:

| File | Notes |
|---|---|
| `.dockerignore` | Docker build context exclusion |
| `db/migrations/0001_notifications.down.sql` | Companion rollback migration for `sun migrate rollback` |
| `test/test_schemas.ml` | Schema compatibility CI gate (generated by EXP-014 work) |
| `test/dune` | Build file for the schema test |

The `test/` directory is particularly important: TUTORIAL.md Part 7 documents `dune test test/` as the schema compatibility check and references `test/test_schemas.ml` by name, but the tree listing that precedes this (in Part 2) does not include the `test/` directory. An engineer following the tutorial in order encounters an undocumented directory without explanation. This is a regression from EXP-010 (which fixed 19→22), driven by three scaffold additions after that fix.

Additionally, the generated workspace `README.md` (from `tpl_readme` in `sun_cli_cmd_new.ml`) does not mention `test/`, `db/migrations/*.down.sql`, or `.dockerignore` in its Project layout section. An AI agent or new engineer who reads only the workspace README will not know these exist.

**Stage 3 — Local Development: PASS.** EXP-017 fix still holds. TUTORIAL.md has the full `sun dev run` subsection (Part 1, "Local iteration with `sun dev run`"). README.md Quickstart covers it. Both gates pass.

**Stage 4 — Cloud Setup: FAIL.** Docs gate fails.

`sun cloud init` is the documented high-level CLI for cloud provisioning (README.md §"Cloud Infrastructure — `sun cloud init`" is accurate and complete). However, **TUTORIAL.md Part 8 bypasses `sun cloud init` entirely**, showing raw `terraform init` + `terraform apply` invocations directly for both AWS and GCP. A new engineer following the tutorial would:

1. Run manual Terraform commands rather than the Sun CLI.
2. Encounter cloud-specific CLI references (`aws eks update-kubeconfig`, `gcloud container clusters get-credentials`) that `sun cloud init` does not emit or run automatically.
3. Never discover `sun cloud init` from the tutorial.

Additionally, neither the TUTORIAL CLI reference table (lines 459–485) nor the README CLI reference table lists `sun cloud init` or any `sun cloud` subcommands. The implementation in `cmd_cloud.ml` registers `init`, `deploy`, `releases`, and `logs` under `sun cloud`, but these are absent from both CLI reference tables.

Also: the UX audit Stage 4 invariant states "After the command completes, `sun status` shows a reachable cluster with no manual kubeconfig setup." This invariant is not met: `sun cloud init` prints a `kubeconfig_command` line (e.g. `aws eks update-kubeconfig ...`) but does not run it. The engineer must run the kubeconfig command manually before `sun status` will work. This is partially acknowledged in README (shows the manual command) but is not documented as a required manual step in the tutorial path.

**Stage 5 — First Deploy: PASS.** `sun deploy` flags (`--image-tag`, `--registry`, `--emit-to`, `--dry-run`) documented in README and TUTORIAL. CI workflow examples in `platform/infra/ci/`. Both gates pass.

**Stage 6 — Shipping a Change: FAIL.** Reproduction gate fails for services using progressive delivery.

`sun rollback` calls `kubectl rollout undo deployment/<name> -n <namespace>`. When a service has `[infra.rollout]` configured in `sun.toml`, `sun deploy` / `sun up` emits a `kind: Rollout` resource (Argo Rollouts) instead of a `kind: Deployment` (`sun_cli_manifest.ml` line 375). The standard Kubernetes `kubectl rollout undo deployment/X` command will fail with an error or silently no-op against a namespace that has a `Rollout` but no `Deployment` of that name.

No documentation in README, TUTORIAL, or the rollback command itself warns that `sun rollback` does not support services using `[infra.rollout]`. README Part 8 documents both `sun rollback` and `[infra.rollout]` as production-ready features in adjacent sections without noting the incompatibility. The rollback command's help text (`kubectl rollout undo`) likewise gives no indication of the limitation.

The change → deploy cycle (docs gate) passes. The rollback path (reproduction gate) fails for the documented `[infra.rollout]` use case.

**Stage 7 — Day-2 Operations: PASS.** `sun logs`, `sun migrate`, `sun status`, `sun new svc/worker/fn` all documented and implemented. `sun logs` prints Grafana URL before streaming. Both gates pass.

**Stage 8 — Domain Event Flow: PASS.** `sun new event` documented, generates stub under `events/<team>/`. Schema compatibility via `test/test_schemas.ml` documented in TUTORIAL Part 7. `sun new worker` + `sun up` flow documented. Both gates pass.

**Stage 9 — AI-Agent Working Surface: PASS.** Generated workspace has predictable edit points. `events/`, `app/`, `db/migrations/`, `lib/` are clearly separated. Framework concerns (lifecycle, Kafka plumbing, observability wiring) are in `vendor/` and `bin/main.ml`; business logic edit points are `lib/handler.ml` and `lib/notify_worker.ml`. One minor gap: the generated workspace `README.md` does not mention `test/` in its Project layout, so an agent that reads only the workspace README will not discover the schema compatibility gate.

## Findings

### [EXP-018] — Stage 2 / TUTORIAL scaffold tree and file count out of date

* **Stage:** 2 Project Creation
* **Gate:** Docs
* **Severity:** Low
* **Description:** TUTORIAL.md claims `sun new workspace` generates 22 files and shows a tree that omits 4 of the 26 actually-generated files: `.dockerignore`, `db/migrations/0001_notifications.down.sql`, `test/test_schemas.ml`, and `test/dune`. The generated workspace `README.md` (tpl_readme) also omits all four from its Project layout section.
* **Impact:** Minor trust erosion and discoverability gap. An engineer sees "Done. 26 files generated." but the tutorial says 22. The `test/` directory — containing the schema compatibility CI gate — appears unexplained and could be deleted or ignored. The `.down.sql` migration file goes unnoticed, leaving `sun migrate rollback` undiscoverable from the workspace README.
* **Remediation:** (1) Update TUTORIAL.md line 133 from "22 files" to "26 files". (2) Add the four missing files to the TUTORIAL tree listing with brief descriptions. (3) Update `tpl_readme` in `sun_cli_cmd_new.ml` to add `test/`, `.dockerignore`, and `db/migrations/*.down.sql` to the Project layout section.

### [EXP-019] — Stage 4 / TUTORIAL Part 8 bypasses `sun cloud init` and CLI reference tables omit all `sun cloud` subcommands

* **Stage:** 4 Cloud Setup
* **Gate:** Docs
* **Severity:** Medium
* **Description:** TUTORIAL.md Part 8 ("Production deployment") shows raw `terraform init` + `terraform apply` commands for AWS and GCP provisioning, completely bypassing `sun cloud init`. The `sun cloud init` command is implemented and documented in README.md but never mentioned in the tutorial. Neither the TUTORIAL CLI reference table (lines 459–485) nor the README CLI reference table lists `sun cloud init`, `sun cloud deploy`, `sun cloud releases`, or `sun cloud logs`.
* **Impact:** An engineer following the tutorial is directed to run Terraform manually rather than using Sun's CLI. This breaks the "without consulting external documentation" promise: the engineer needs Terraform knowledge, cloud-provider CLIs, and knowledge of where the Terraform modules live — all of which `sun cloud init` abstracts away. The four `sun cloud` subcommands are invisible from both primary reference surfaces.
* **Remediation:** (1) Update TUTORIAL.md Part 8 to show `sun cloud init --aws` / `sun cloud init --gcp` as the primary provisioning path, with the current Terraform section demoted to an "Advanced / manual override" note. (2) Add `sun cloud init`, `sun cloud deploy`, `sun cloud releases`, and `sun cloud logs` to the CLI reference tables in both TUTORIAL.md and README.md.

### [EXP-020] — Stage 6 / `sun rollback` silently fails for services using `[infra.rollout]`

* **Stage:** 6 Shipping a Change
* **Gate:** Reproduction
* **Severity:** High
* **Description:** `sun rollback` runs `kubectl rollout undo deployment/<name> -n <namespace>` for every discovered service. When a service has `[infra.rollout]` configured in `sun.toml`, the synthesized manifest emits a `kind: Rollout` resource (Argo Rollouts), not a `kind: Deployment`. The `kubectl rollout undo deployment/X` command will fail or no-op against a namespace with a `Rollout` but no matching `Deployment`. Neither `cmd_rollback.ml` nor any documentation warns of this incompatibility.
* **Impact:** During a production incident, an engineer who configured canary or blue-green delivery (a documented, recommended feature) and then runs `sun rollback` will get a kubectl error or a silent failure. The previous version is not restored. This is the highest-stakes gap in the current codebase: the rollback path — which is the safety net — is broken for services that use the progressive delivery feature.
* **Remediation:** Two options, do one or both: (A) Implement: `cmd_rollback.ml` should read `sun.toml` for each discovered service; if `progressive_delivery` is set, invoke `kubectl argo rollouts undo <name>` instead of `kubectl rollout undo deployment/<name>`. (B) Warn: until (A) is implemented, add a pre-flight check in `cmd_rollback.ml` that reads `sun.toml`, detects `[infra.rollout]`, and exits with a clear error message: "Service X uses Argo Rollouts — run: kubectl argo rollouts undo X -n NAMESPACE". Also add a note to README.md §"Shipping a Change" and TUTORIAL.md §"Day-2 operations" documenting the current limitation.
