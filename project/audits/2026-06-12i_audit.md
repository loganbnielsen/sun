## Findings

### AUDIT-039 — `rollout_doc` references `sun-secrets` instead of `<name>-secrets` in envFrom secretRef

* **Category:** Security / Runtime
* **Severity:** High
* **Location:** `cli/sun/lib/sun_cli_manifest.ml` (line 419, `rollout_doc`)
* **Status:** Open
* **Description:** `rollout_doc` renders the Argo Rollout resource for canary and blue-green progressive delivery. Its `envFrom.secretRef.name` is set to `runtime_secret_name` = `"sun-secrets"` (a hardcoded constant), whereas `secret_doc` creates the Secret as `<name>-secrets` (per-service). `deployment_doc` (the standard path) correctly uses `name` in its format string to produce `<name>-secrets`. The mismatch means any service using `[infra.rollout] strategy = "canary"` or `"blue-green"` will generate an Argo Rollout that references a non-existent Secret. Pods will fail to start with a Kubernetes `SecretNotFound` error, and `POSTGRES_URL` and any other secrets will not be injected.
* **Impact:** Progressive delivery is silently broken for all services that configure a rollout strategy. The generated YAML passes `kubectl apply` (the Secret reference is not validated until pod scheduling), so the failure is discovered only at runtime when the pod crashes.
* **Remediation:** In `rollout_doc`, change the `envFrom.secretRef` format specifier from the hardcoded `runtime_secret_name` to use the `name` argument, identical to `deployment_doc`. In the format string (line ~408):
  ```
  - secretRef:
      name: %s-secrets
  ```
  and update the positional argument list at line 419 to supply `name` for this slot instead of `runtime_secret_name`. Also review `render_secret_key_refs` (line 225): if per-key `secretKeyRef` entries are intended to reference `<name>-secrets` rather than a cluster-wide Secret, change `runtime_secret_name` there too.
