## Findings

### [EXP-014] — Stage 8: No documented schema compatibility check path

* **Stage:** 8 Adding a Domain Event Flow
* **Gate:** Docs
* **Severity:** High
* **Status:** Open
* **Description:** Tutorial Part 7 says "the compiler will find every place that needs updating" when a developer modifies an event type. This is true for OCaml structural changes but not for the `schema` JSON field in `val schema : string`. If the JSON schema breaks backward compatibility with already-registered schemas (e.g., removing a field, changing a type), the incompatibility is only discovered when the worker starts and calls `Kafka_service.register` — by which time the old consumer may already be running against the new schema in staging. `Kafka_service.Schema.check` and `Schema.check_all` exist in the API but are not referenced anywhere in user-facing docs, tutorials, or generated workspace files.
* **Impact:** A developer who changes an event contract schema string and deploys will not know they have a breaking schema change until runtime, potentially causing decode errors in workers. The schema compatibility check API (`Kafka_service.Schema.check_all`) is discoverable only by reading source code.
* **Remediation:** (1) Add a generated `test/test_schemas.ml` to new workspaces that calls `Kafka_service.Schema.check_all` against the local schema registry — compile/test failure catches breaking changes in CI. (2) Add a note to Tutorial Part 7 explaining that schema compatibility should be verified in CI using `Schema.check_all` before deploy. (3) Optionally: wire schema compatibility into `sun deploy --dry-run` as a pre-flight check.

---

### [EXP-015] — Stage 8: `sun new event` for existing team requires manual dune edit

* **Stage:** 8 Adding a Domain Event Flow
* **Gate:** Reproduction
* **Severity:** Medium
* **Status:** Open
* **Description:** When `sun new event <team>/<name>` is run for a team whose `events/<team>/dune` file already exists, the CLI generates `events/<team>/<name>.ml` and prints "Note: Add `<Mod>` to the (modules ...) list." It does not patch the dune file. An engineer unfamiliar with dune must manually locate the `(modules ...)` stanza and add the new module name.
* **Impact:** Adding a second event to an existing team requires dune knowledge not mentioned in the Tutorial. The edit is trivial for a dune user but is a gap for a startup engineer who is new to OCaml build conventions. A missing module entry causes a silent build error ("Unbound module X") rather than a clear scaffold failure.
* **Remediation:** In `sun_cli_cmd_new.ml` `new_event`, when `events/<team>/dune` already exists, read its content, find the `(modules ...)` stanza, and append the new module name. A simple regex-based patch is sufficient. Alternatively, use a dune stanza that auto-discovers all `.ml` files (using `(modules (:standard))`) so no patching is needed.
