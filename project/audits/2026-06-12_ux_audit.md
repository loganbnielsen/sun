## Findings

### UX-002 — stale service port-forward still misroutes the success URL

* **Stage:** 5 First Deploy
* **Gate:** Reproduction
* **Severity:** Medium
* **Status:** Existing open ticket
* **Description:** A stale `kubectl port-forward -n dogfood-2026-06-11-payments svc/charge-svc 8080:80` was still bound to port 8080. The fresh `dogfood_2026_06_12` run printed `http://localhost:8080 (port-forward running in background)` and exited 0, but `curl http://localhost:8080/notifications` initially returned data from the older workspace. The new workspace's service and worker pods were healthy, but the advertised local URL was not pointing at them.
* **Impact:** A release-user or new engineer can validate the wrong workspace and believe the new deploy is working. This is especially dangerous because the command output looks successful.
* **Ticket:** Existing `project/tickets/READY_FOR_ENGINEERING/UX-002.md` updated with this reproduction.

### DOGFOOD-010 — local deploy accepts writes with empty database credentials

* **Stage:** 5 First Deploy
* **Gate:** Reproduction
* **Severity:** High
* **Status:** New ticket
* **Description:** After bypassing the stale port 8080 by directly port-forwarding `dogfood-2026-06-12-payments/charge-svc` to localhost:18080, `/health` returned `ok` and `POST /charges` returned accepted. However, `/notifications` remained `[]` for 20 seconds. Both generated workload Secrets contained `POSTGRES_URL: ""`, so the generated app ran without a database pool.
* **Impact:** The first local deploy can look successful while the core cross-domain persistence demo is broken.
* **Ticket:** `project/tickets/READY_FOR_ENGINEERING/DOGFOOD-010.md`
