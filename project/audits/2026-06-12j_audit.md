### §2 — Infrastructure Synthesis

**Standard workloads (Deployment, CronJob):** Most passing. `deployment_doc` and `rollout_doc` both set `app: <name>` in pod template labels, and `network_policy_doc` uses `matchLabels: app: <name>` — they match.

**CronJob / `-fn` workloads:** FAIL — see AUDIT-040. `cronjob_doc` does not include a `labels:` section in the pod template, so pods spawned by CronJobs do not carry the `app: <name>` label. The `network_policy_doc` generated alongside every workload (including `Fn`) uses `podSelector.matchLabels.app: <name>`. For Deployment and Rollout workloads this selector works correctly. For CronJob workloads the selector matches no pods, rendering the generated NetworkPolicy entirely ineffective. The CronJob pods are unrestricted despite a NetworkPolicy appearing in the manifest.

**Progressive delivery workloads (Rollout):** PASS — AUDIT-039 resolved. `rollout_doc` now emits `name: %s-secrets` using the `name` argument, consistent with `deployment_doc` and `secret_doc`.

### §3 — Core Runtime

All passing. ### §4 — Observability & Data Integrity

**Schema registry TLS:** PASS. `kafka_service.ml` uses a lazy-initialised TLS authenticator and passes the https wrapper to `Cohttp_eio.Client.make`.

**Loki push backend TLS:** FAIL — see AUDIT-041. `obs_loki.ml` line 14: `Cohttp_eio.Client.make ~https:None net`. Passing `~https:None` instructs Cohttp_eio to refuse any `https://` URI with a `Failure` or connection-refused error. Cloud-hosted Loki endpoints (Grafana Cloud, hosted Loki) require HTTPS. Attempts to connect will raise an exception caught by the outer `try/with`, producing an `Error "Loki push: ..."` message on stderr but silently dropping all log lines.

**Prometheus Pushgateway TLS:** FAIL — same root cause. `obs_prometheus.ml` line 242: `Cohttp_eio.Client.make ~https:None net`. Hosted or self-hosted Pushgateway deployments behind TLS will silently drop all metrics pushes from `-fn` workloads.

`default_on_decode_error` emits structured log + counter. `traceparent` propagation is correct.

## Findings

### AUDIT-040 — `cronjob_doc` pod template missing `app: <name>` label — NetworkPolicy never matches `-fn` workload pods

* **Category:** Security / Infrastructure Synthesis
* **Severity:** Medium
* **Location:** `cli/sun/lib/sun_cli_manifest.ml` (`cronjob_doc`, lines 522–564)
* **Status:** Open
* **Description:** `cronjob_doc` renders the `spec.jobTemplate.spec.template` without a `labels:` section. Pods spawned by the CronJob therefore carry no labels. `network_policy_doc` (always included in `common` for all primitives including `Fn`) uses `podSelector: matchLabels: app: <name>`. Since no CronJob pod carries this label, the generated NetworkPolicy matches no pods and applies no traffic restrictions to the `-fn` workload. By contrast, `deployment_doc` and `rollout_doc` both set `app: <name>` in their pod template labels.
* **Impact:** A `-fn` workload that is expected to have network egress restricted to DNS + Redpanda + PostgreSQL + monitoring is in fact unrestricted. Exfiltration or unexpected outbound connections from a compromised function pod are not blocked by the generated policy. The manifest passes `kubectl apply` without error; the misconfiguration is invisible to the operator.
* **Remediation:** Add a `labels:` section to the `cronjob_doc` pod template matching the pattern used by `deployment_doc`:
  ```yaml
  spec:
    jobTemplate:
      spec:
        template:
          metadata:
            labels:
              app: %s
  ```
  Insert the `metadata:` / `labels:` block before the `spec:` line of the job pod template in the `cronjob_doc` format string (around line 535). Add `name` as the positional argument for the `%s` in this new line. Add a test in `cli/sun/test/test_manifest_render.ml` that asserts the rendered CronJob YAML contains `app: <service-name>` in the pod template labels section.

### AUDIT-041 — `obs_loki.ml` and `obs_prometheus.ml` pass `~https:None` — HTTPS Loki/Pushgateway endpoints silently drop all observability data

* **Category:** Observability / Data Integrity
* **Severity:** High
* **Location:** `integrations/observability/obs-eio-loki/lib/obs_loki.ml` (line 14) · `integrations/observability/obs-eio-prometheus/lib/obs_prometheus.ml` (line 242)
* **Status:** Open
* **Description:** Both backends construct their Cohttp_eio client with `~https:None`. When `~https:None` is passed, Cohttp_eio refuses HTTPS URIs at connection time — no TLS handshake is attempted. Cloud-hosted Loki endpoints (Grafana Cloud `logs-prod-*.grafana.net`, self-hosted Loki behind a TLS ingress) and Pushgateway endpoints use HTTPS URLs. The `http_post` / Pushgateway push functions catch all exceptions and return `Error (...)` which is logged to stderr and then discarded. The operator's `LOKI_URL=https://...` or `PUSHGATEWAY_URL=https://...` environment variable silently stops working; logs and metrics are dropped without any impact on the application process. By contrast, `kafka_service.ml` correctly builds an HTTPS wrapper using `tls-eio` and `x509` and passes it to Cohttp_eio.
* **Impact:** A startup connecting to a hosted Loki or Prometheus Pushgateway (the typical production path) receives no error at startup. All log lines and metrics from `-fn` workloads are silently lost. The only observable symptom is stderr noise and absent data in Grafana, which may be mistaken for a configuration or labelling issue. The schema registry client (AUDIT-029) was fixed with a TLS wrapper — the same fix was not applied to the observability backends.
* **Remediation:** Apply the same TLS pattern already used in `kafka_service.ml`:
  1. Copy or factor out the `tls_authenticator` lazy value and `make_https_wrapper` helper from `kafka_service.ml` into a shared `Sun_http_tls` module (or duplicate the pattern per-file).
  2. In `obs_loki.ml`, replace `Cohttp_eio.Client.make ~https:None net` with `Cohttp_eio.Client.make ~https:(Some (make_https_wrapper ())) net` so that `https://` URIs work. Plain `http://` URIs continue to work — Cohttp_eio only invokes the https wrapper for HTTPS scheme.
  3. Apply the same change in `obs_prometheus.ml`.
  4. Add tests that construct a client with an https wrapper and assert no exception is raised for an `https://` URI (can use a mock or skip-unless-network pattern).
  The required packages (`tls-eio`, `x509`, `domain-name`, `ptime`) are already in `dune-project` and the Dockerfile template opam install line.
