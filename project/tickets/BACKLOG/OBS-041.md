Decide: is distributed tracing (backend + dashboard) in scope, or does trace-id correlation in logs stay the whole story?

**Depends on:** None.

## Problem

`docs/architecture/observability-design.md`'s Identity section names
"trace" as one of the signal types that must carry the shared ownership
labels (`workspace`/`env`/`domain`/`service`/`primitive`/`release`) — but
there is no tracing backend, no trace dashboard, and no other mention of
tracing anywhere else in the doc. What actually exists today is narrower:
`~/Code/obs-eio`'s `Obs_trace` module provides W3C `traceparent`
propagation (generate/parse/inject/extract, header-based context passing
across service calls) and `obs-loki-eio`'s `Obs_loki` backend embeds
`trace_id`/`span_id` as logfmt fields in pushed log lines
(`~/Code/obs-loki-eio/lib/obs_loki.mli`). That gives cross-service log
*correlation* (find every log line for one trace_id across services in
Loki) but not a trace *visualization* — no span waterfall, no latency
breakdown across service hops, no backend that understands the W3C trace
model as a first-class object (e.g. Tempo, Jaeger).

## Decision Required

- Is a real tracing backend (e.g. Grafana Tempo, paired with the
  `Obs_trace` context Sun already propagates) worth building, or does
  logfmt-embedded `trace_id` correlation in Loki stay sufficient for the
  foreseeable future?
- If in scope: Tempo is the natural fit given Sun already standardizes on
  Grafana for the dashboard shell (same sidecar-ConfigMap dashboard-loading
  convention `OBS-011` established) — would need span *emission*, not just
  context *propagation*, added to `obs-eio`/`obs-loki-eio` or a new
  `obs-tempo-eio` backend package (matching this repo's existing
  extraction pattern for `obs-loki-eio`/`obs-prometheus-eio`).
- If out of scope for now: say so explicitly in `docs/architecture/
  observability-design.md` (e.g. move "trace" out of the Identity table's
  implied "these get dashboards" framing, or add a Non-Goals line), so a
  future audit doesn't keep re-flagging this as an unimplemented promise.

This ticket stays in `BACKLOG` — it's a scope call, not yet a spec `/work`
could act on.
