Decide: is alerting/SLO tooling in scope for Sun, or left to the user's own Prometheus/Grafana setup?

**Depends on:** None.

## Problem

`docs/architecture/observability-design.md` specs dashboards, log/metric
identity labels, and backend modes — but says nothing about alerting or
SLOs anywhere. This isn't a deferred-and-noted gap the way the dashboard
list was (`OBS-036`/`OBS-038`); it's simply absent from the design, which
means it's never been decided whether it's in scope at all.

Sun already provisions Prometheus (`platform/infra/base/main.tf`'s
`helm_release.prometheus`) with Alertmanager available as part of that
chart, unconfigured. A user could hand-write `PrometheusRule` CRDs and
Alertmanager routes against Sun's existing labels
(`workspace`/`env`/`domain`/`service`/`primitive`/`release`) today with zero
Sun-side work — the label taxonomy already makes that possible. The open
question is whether Sun should provide anything on top of "the labels
exist, bring your own rules": starter alert rules (error-rate, pod
restart-loop, deploy-failure), an SLO/burn-rate dashboard, or `sun`-CLI
surface for authoring/viewing alerts.

## Decision Required

- Is baseline alerting (e.g. a starter `PrometheusRule` set for common
  failure modes, using labels Sun already emits) something Sun ships, or
  does Sun stop at "the labels are there, configure your own
  Alertmanager"?
- If in scope: what's the smallest defensible v1 (a handful of starter
  alert rules bundled with `platform/infra/base`, vs. a `sun`-specific
  authoring surface, vs. just documentation showing how to write rules
  against Sun's labels)?
- If out of scope: say so explicitly in `docs/architecture/
  observability-design.md`'s Non-Goals section, so this doesn't get
  re-discovered as a "missing" feature by a future audit.

This ticket stays in `BACKLOG` — it's a scope call, not yet a spec `/work`
could act on.
