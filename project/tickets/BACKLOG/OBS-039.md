Replace the deprecated `loki-stack` Helm chart before relying on it in production

**Depends on:** None.

## Problem

`platform/infra/base/main.tf`'s `helm_release.loki` resource
(`repository = "https://grafana.github.io/helm-charts"`, `chart =
"loki-stack"`, `version = "2.10.2"`) uses Grafana Labs' `loki-stack` chart,
which upstream has deprecated in favor of split/maintained charts (the
`loki` chart for Loki itself, plus a separate Grafana chart and either
`promtail` or `grafana-agent` for log shipping). Sun currently depends on
several `loki-stack`-specific behaviors that a replacement needs to
preserve, not just chart-swap blindly:

- `promtail.enabled=true` scrapes every pod's stdout/stderr cluster-wide via
  a DaemonSet — this is load-bearing for `OBS-004`'s failure-visibility
  story (OOMKilled, CrashLoopBackOff, pre-log crashes that `obs-loki-eio`'s
  app-push logging structurally cannot see).
- Bundled Grafana (`grafana.enabled`) with sidecar ConfigMap-loading for
  both dashboards and datasources (`OBS-011`) — dashboards are provisioned
  today purely by labeling a ConfigMap, no chart-specific dashboard-loading
  code in Sun itself.
- `loki.persistence.enabled` toggles PVC-backed storage for the `local`
  profile (`docs/deployment/observability-backends.md`).

## Open Questions

- **Which replacement chart(s)?** Options include Grafana's newer `loki`
  chart (single-binary or simple-scalable-deployment mode) paired with a
  separate `grafana`/`kube-prometheus-stack`-style Grafana chart and
  `promtail` or `grafana-agent` chart, versus another maintained
  distribution. Needs a real evaluation of which combination keeps the
  sidecar ConfigMap dashboard/datasource auto-loading `OBS-011` depends on
  — that convention needs to survive the migration, not just Loki log
  ingestion.
- **Migration path for existing self-hosted-durable deployments**
  (`self_hosted_durable` mode's S3-backed Loki, `docs/deployment/
  observability-backends.md`) — does swapping the chart require a
  data-migration story for existing installs, or is this safe as a
  clean-cutover change given Sun's pre-alpha/no-backwards-compatibility
  policy (`~/Code/CLAUDE.md`)?

This ticket stays in `BACKLOG` until at least the chart choice is resolved
— `/work` should not create a worktree for an unresolved
evaluation-and-choice question.

## Non-goal

Migrating for its own sake ahead of any concrete forcing function (a real
upstream removal, a CVE only fixed in the new chart, etc.) — if
`loki-stack` keeps receiving security patches at its current major version,
this can stay backlog-priority rather than urgent.
