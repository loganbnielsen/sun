Close the remaining Dashboard Shape gaps: domain overview, dedicated service logs view, deploy/release timeline

**Depends on:** None.

## Problem

`docs/architecture/observability-design.md`'s Dashboard Shape section specs
five dashboards: workspace overview, domain overview, service dashboard,
service logs view, deploy/release timeline. OBS-011 (`docs/deployment/
observability-backends.md`) built two — a combined workspace overview and a
`$domain`/`$service`-parameterized service template that already embeds a
Loki logs panel. Three are still missing:

- **Domain overview** — no dashboard scoped to one domain across its
  services (today's workspace overview is workspace-wide; the service
  template is single-service).
- **Dedicated service logs view** — the service template's embedded Loki
  panel covers this in practice for most workflows; a standalone logs-only
  dashboard may be redundant rather than missing. Worth confirming this is
  actually still a gap before building it, not just assuming the design doc
  is ahead of what shipped.
- **Deploy/release timeline** — no dashboard shows deploy/release events
  over time at all. This one has a real prerequisite gap, not just a
  missing JSON file (see Decision Required below).

## Decision Required

**Deploy/release events aren't recorded anywhere queryable today.**
`sun deploy` prints to stdout and updates `Sun_cli_deployment_state`
locally (`cli/sun/lib/sun_cli_deployment_state.ml`) — nothing reaches
Grafana, Loki, or Prometheus. A timeline dashboard needs a real event
source first. Candidate approaches, roughly in order of how much new
surface each adds:

1. **Grafana annotation API** — `sun deploy` (non-dry-run, non-emit-to)
   POSTs an annotation (service, release/image tag, timestamp) to Grafana's
   `/api/annotations` after a successful apply. Grafana natively renders
   annotations as vertical markers on any time-series panel — no new
   dashboard panel type needed, just points already-shown panels. Requires
   Grafana API reachability + auth from wherever `sun deploy` runs (CI
   runner, GitOps controller), which the direct-deploy path already assumes
   for `kubectl` but the GitOps path (`--emit-to`) does not.
2. **Synthetic Prometheus metric** — e.g. a `sun_deploy_info{service,
   release} 1` gauge pushed to Pushgateway on every deploy (same ingestion
   path `-fn` already uses). Queryable as a table or `changes()` panel, but
   doesn't render as a timeline marker as naturally as an annotation does.
3. **Loki log line** — `sun deploy` pushes a structured log line via the
   same client pattern services use. Cheapest to add, but timeline-style
   visualization from log lines is clunkier in Grafana than annotations or
   a metric.

This ticket cannot move to `READY_FOR_ENGINEERING` until one of these (or
another approach) is chosen — the choice determines what `sun deploy`
needs to call, which credentials/config it needs, and whether GitOps mode
(no direct cluster/Grafana access from the CI runner) can support it at
all or needs a documented gap.

## Non-goal

Live verification that any of OBS-011's or this ticket's dashboards
actually render against a real Grafana instance — that's covered by
`DOGFOOD-010`, which needs real cluster/cloud access this ticket doesn't
require.
