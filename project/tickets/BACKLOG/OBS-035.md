sun-worker exposes no Prometheus metrics port, so workers never show up in Grafana

**Depends on:** None.

## Problem

`cli/sun/lib/sun_cli_manifest_yaml.ml`'s `prometheus_annotations` only adds
`prometheus.io/scrape`/`prometheus.io/port` for `Http_service` (`-svc`)
Deployments — already called out in its own comment as "Background_worker's
own metrics port isn't wired at the manifest level yet (separate,
pre-existing gap, not addressed here)" (OBS-011). The gap is deeper than the
manifest annotation: `framework/sun-worker/lib/` has no HTTP listener at all
today, so there's no `/metrics` endpoint for an annotation to even point at
— `-svc` already runs an HTTP server (routes + auth) that a metrics endpoint
piggybacks on; `-worker` is a pure Kafka consumer loop with nothing
listening.

Net effect: the OBS-011/030 Grafana "Service template" dashboard's
`$service` variable (populated from live Prometheus label values) will
never list a worker, and worker-side metrics `sun-worker` already computes
internally (ok/error counters, duration histogram — see
`framework/sun-worker/lib/`'s existing metrics, per this repo's CLAUDE.md)
never reach Prometheus at all in a real deployment.

## Goal

A deployed `-worker` service's metrics (message counts, error counts,
processing duration) are scrapeable by Prometheus and show up in the same
Grafana dashboards `-svc` already populates.

## Open Questions

- What should serve `/metrics` for a worker that otherwise has no HTTP
  listener? Options include: spin up a minimal Eio-based HTTP server in
  `sun-worker`'s lifecycle just for metrics exposition (new surface area,
  needs to coexist cleanly with the consumer loop and graceful shutdown);
  or push metrics to Pushgateway the way `-fn` already does instead of
  being scraped (simpler, but changes the metrics model for `-worker`
  specifically, and Pushgateway is designed for short-lived jobs, not a
  long-running consumer). Worth a deliberate choice before implementing,
  since it affects `sun-worker`'s public shape either way.
