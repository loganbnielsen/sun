`sun up`'s Docker build fails for any freshly scaffolded workspace with a Postgres-backed service

**Depends on:** None.

## Problem

Found running a real end-to-end local demo (scaffold → `dune build` → `sun
up`) as part of closing out the observability-readiness work, right after
fixing two unrelated scaffold-template bugs in PR #109 (`require_ok`
unused-value error, a schema-check type error) that had been silently
blocking `dune build` on any fresh scaffold. `sun new workspace` produces
`notify_worker`'s `bin/dune` depending on `pg-eio`, `caqti-eio`,
`caqti-eio.unix`, `caqti-driver-postgresql` — and `kafka_eio_service`,
`obs-eio`, `obs-loki-eio`, `obs-prometheus-eio`, `obs-tempo-eio` for both
services. None of these are vendored into `vendor/framework`/
`vendor/integrations` (all fully externalized per `~/Code/CLAUDE.md`'s
repo layout notes) and none are published to the public opam-repository —
`sun_cli_scaffold_templates.ml`'s `tpl_dockerfile` never pins any of them,
so the Docker build stage's plain `opam install` can never find them.

`docker build -f app/comms/notify_worker/Dockerfile .` on a fresh scaffold
fails immediately:

```
Error: Library "pg-eio" not found.
-> required by _build/default/app/comms/notify_worker/bin/main.exe
```

This is not a hypothetical — it means `sun up` cannot succeed for a
freshly scaffolded workspace today, for any workspace that includes a
Postgres-backed service (the default scaffold does).

## Attempted fix and why it's incomplete

Added the same `opam pin add <pkg> https://github.com/loganbnielsen/<pkg>.git#main -y`
steps this repo's own `.github/workflows/ci.yml` already uses successfully
(`https-eio`, `kafka-eio`, `obs-eio`, `obs-loki-eio`, `obs-prometheus-eio`,
`obs-tempo-eio`, `pg-eio`), placed *before* the existing `opam install`
line (pin order matters — pinning `https-eio` after a plain install
already resolved a lower `tls-eio` fails, since a pin alone doesn't
upgrade an already-installed package's already-installed dependencies).

This gets further but still fails: `https-eio`'s `#main` opam file
requires `tls-eio >= 2.1.0`, and pinning it inside the `ocaml/opam:
ubuntu-24.04-ocaml-5.4` Docker base image reports "no matching version"
for `tls-eio` — **even after** explicitly repointing the opam remote at
the real `https://opam.ocaml.org` (`opam repository set-url default
https://opam.ocaml.org && opam update`, which reported "no changes",
meaning the index itself is not the problem). A local dev machine's
ambient switch has `tls-eio.2.1.0` available and resolves fine (confirmed
via `opam show tls-eio --field=all-versions`), so the real constraint
conflict is with something else already installed in the *base image's*
default switch state before any of this repo's own steps run — not
investigated further; this needs someone with time to actually resolve
the opam solve, not more reactive pin-tweaking.

## Non-goal

CI itself is unaffected — `ocaml/setup-ocaml@v3` creates a fresh switch
per run and `.github/workflows/ci.yml`'s existing pin block already works
there (confirmed: PR #109's CI run passed). This is specifically about
`sun new workspace` + `sun up`'s Docker build stage, a currently-untested
path (no test in this repo builds a scaffolded workspace's actual Docker
image, only `dune build` — see PR #109's new `test_scaffold_compiles`,
which stops at library compilation, not image builds).

## Suggested next steps

1. Reproduce inside a plain `ocaml/opam:ubuntu-24.04-ocaml-5.4` container
   (no Sun scaffold involved) and run `opam pin add https-eio
   https://github.com/loganbnielsen/https-eio.git#main -y` alone, with
   `-v`/`--debug` for the full solver explanation of exactly which
   already-installed package conflicts with `tls-eio >= 2.1.0` — the
   error shown during this investigation only printed the top-level
   missing-dependency line, not the actual conflicting package.
2. Consider whether `tpl_dockerfile`'s base image
   (`ocaml/opam:ubuntu-24.04-ocaml-5.4`) needs a version bump, or whether
   the fix belongs in `https-eio`'s own `.opam` constraint (loosening
   `tls-eio >= 2.1.0` if a lower version genuinely still works, if that
   floor was set defensively rather than for a real feature dependency).
3. Once resolved, add a real (if slow) regression test that actually runs
   `docker build` against a freshly scaffolded workspace's Dockerfile —
   the same gap-closing move PR #109 made for `dune build`, applied one
   layer further down the deploy path. `sun up`'s Docker build has
   apparently never been build-tested by this repo's own test suite.

## Acceptance criteria

- `sun new workspace foo && cd foo && docker build -f
  app/comms/notify_worker/Dockerfile .` succeeds on a plain Docker
  install with no pre-existing local opam pins (i.e., reproducible from a
  genuinely fresh environment, not just "works on my machine" because the
  host switch already has everything pinned).
- Same for `app/payments/charge_svc/Dockerfile`.
- A real build-based regression test exists so this can't silently break
  again.
