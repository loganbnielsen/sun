parse_pod discards the whole pod list if one pod's JSON has no "status" key

**Depends on:** None.

## Problem

Found while reviewing OBS-026's CronJob-status parsing (PR #85), which had the
same class of bug: `Yojson.Safe.Util.member key` returns `` `Null `` for a key
absent from an object, but `member` called *on* `` `Null `` itself raises
`Type_error`.

`sun_cli_rollout_diagnosis.ml`'s `parse_pod` does:

```ocaml
let status = J.member "status" item in
let phase = J.member "phase" status |> to_string_opt |> Option.value ~default:"Unknown" in
```

If a pod's JSON genuinely has no `"status"` key at all, `status` is `` `Null ``
and the `J.member "phase" status` call raises. `parse_pod` doesn't catch this
itself, so it propagates up to `parse_pods_json`'s outer `try...with _ -> []`,
which discards *every* pod in the list, not just the one missing `status` —
`format_service_diagnosis` would then see an empty pod list and report the
whole Continuous service's rollout as failed on a single malformed/edge-case
pod entry, or worse (depending on how "empty" is otherwise distinguished from
"no pods scheduled").

In practice this is unlikely — a real pod object from `kubectl get pods -o
json` always carries `status` once the object exists — but the failure mode
(silently discarding all diagnosis rather than degrading just the one pod) is
a landmine worth removing since it's already been hit once in a sibling
function this same session (OBS-026's `parse_cronjob_status`).

## Goal

A pod with no `status` key parses to the same `Unknown_state`/`"Unknown"`
degraded-but-present entry that a pod with an empty `status: {}` already gets,
not an exception that wipes out the rest of the pod list.

## Suggested approach

Match on `` `Null `` from `J.member "status" item` the same way
`parse_cronjob_status` now does (see `sun_cli_rollout_diagnosis.ml`,
OBS-026), instead of passing it straight into further `J.member` calls.
