Nothing stops selecting self_hosted_durable observability against a GCP-provisioned cluster

**Depends on:** None.

## Problem

`docs/deployment/observability-backends.md` says plainly: "GCP is a
deliberate gap, not an oversight" for `self_hosted_durable` (it sets
`eks.amazonaws.com/role-arn` IRSA annotations, which only mean anything on
EKS). But `platform/infra/base/main.tf`'s
`terraform_data.observability_backend_validation` only checks that
`loki_irsa_role_arn`/`thanos_irsa_role_arn`/the two S3 bucket names are
non-empty strings — it has no cloud-provider awareness at all. Nothing
rejects applying `self_hosted_durable` against a GKE (or any non-EKS)
cluster; it would misconfigure silently (the IRSA annotation is simply
meaningless there) rather than fail fast with a clear error.

`platform/infra/base` is deliberately cluster-agnostic (works with any
Kubernetes cluster from any provisioning path), so it has no first-class
signal for "which cloud am I running on" to check against.

## Goal

Applying `self_hosted_durable` against a non-AWS cluster fails with a clear
error at `terraform apply` time, not a silent misconfiguration discovered
later when logs/metrics don't actually persist.

## Open Questions

- The shallow fix (validate `loki_irsa_role_arn`/`thanos_irsa_role_arn`
  actually look like AWS IAM role ARNs, e.g. `^arn:aws:iam::`) only catches
  a malformed/wrong-shape value — it can't catch a user who copies real AWS
  ARNs from a `platform/infra/aws` apply and then points `base` at a
  GCP-provisioned cluster (syntactically valid ARNs, wrong actual cluster).
  Is the format check worth doing on its own as a cheap partial guard, or
  does closing this properly require `base` to take an explicit
  `cloud_provider` variable (a bigger, more deliberate architectural change
  to a module that's currently intentionally cluster-agnostic)?
