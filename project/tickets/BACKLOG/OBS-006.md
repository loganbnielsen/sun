Make platform metrics durable and remotely accessible

**Depends on:** OBS-005.

## Problem

`prometheus_persistent_storage` (`platform/infra/base/variables.tf`) is a
local-PVC toggle, not durable storage — if the cluster's node/volume is lost,
metric history goes with it. There's also no `sun`-CLI equivalent of `sun
logs` for metrics: today the only way to see Prometheus data is a manual
port-forward to Prometheus or Grafana from a machine with cluster access.

## Goal

Give Sun-managed targets a durable metrics storage story and a query path
from any developer machine with permission — the same shape of problem
OBS-005 solves for logs, using whichever backend OBS-005 decides on (hosted
vendor bundles logs + metrics together; self-hosted means Prometheus
remote_write to a long-term-storage backend such as Thanos or Mimir).

## Acceptance criteria

- Production-like targets retain metric history beyond a single pod/PVC
  lifetime, via the backend chosen in OBS-005.
- Dev/smoke targets can still opt into ephemeral, local-only metrics.
- A developer on a different machine than the one that ran `sun deploy` can
  query current and historical metrics for a service (via Grafana, a
  `sun`-CLI command, or documented direct query access — pick one, don't
  require standing up your own tooling).
- The access model is documented: required credentials, network path, and
  retention behavior.
- Teardown behavior is explicit: destroying compute does not accidentally
  delete retained metrics unless the target config says to.
