sun logs never authenticates Loki reads, so external/hosted backends always fall back to kubectl

**Depends on:** None.

## Problem

`Sun_cli_loki.query` (`cli/sun/lib/sun_cli_loki.ml`) sends unauthenticated
HTTP requests. `docs/deployment/observability-backends.md` already
self-documents this: an `external` backend pointed at a hosted Loki (Grafana
Cloud, etc.) that requires an API key on reads will always fail the query and
fall through to `kubectl logs` — silently, since that fallback path already
exists for other failure modes (Loki down, no results) and doesn't
distinguish "wrong credentials" from those.

Sun already collects `external_loki_username`/`external_loki_password` for
the *write* path (promtail's client config in `platform/infra/base/main.tf`)
— those aren't currently plumbed through to the CLI's *read* path at all.

## Goal

`sun logs --no-follow` against an `external` (or authenticated
`self_hosted_durable`) Loki actually authenticates its queries, using the
same credentials already configured for the write side where applicable, so
log snapshots work end-to-end for a real hosted backend instead of always
degrading to `kubectl logs`.

## Open Questions

- Where should the CLI read the read-side credentials from at invocation
  time? Candidates: new `--loki-username`/`--loki-password` flags (mirrors
  `--loki-base-url`'s existing pattern, but one more pair of secrets to pass
  by hand every time); reading the same `sun.yml`/target config the
  Terraform variables come from (requires the CLI to parse Terraform
  variables or a synced copy of them, which it doesn't do today); or
  environment variables the operator sets once per shell. Depends partly on
  how OBS-031 resolves the URL question, since both are "how does the CLI
  reach a real backend" pieces of the same gap.
