Make platform logs durable and remotely accessible

**Depends on:** OBS-004.

## Problem

Self-hosted Loki with ephemeral storage is fine for throwaway smoke tests, but
it is not enough for real projects. If the cluster is destroyed, Loki is
rescheduled without persistent storage, or the developer is on another machine,
important deployment/runtime logs may be unavailable.

This ticket also makes the durable-observability-backend decision for
**metrics**, not just logs — see `## Decision Required` below. If the answer
is a hosted vendor, it's the same vendor for both (e.g. Grafana Cloud bundles
Loki + Mimir under one relationship); if it's self-hosted, it's the same
philosophy applied to two different backends (Loki→object storage,
Prometheus→Thanos/Mimir). The Prometheus-specific implementation is tracked
separately in OBS-006, which depends on the decision made here.

## Decision Required

Which durable observability backend, if any, right now:

| Option | Primary cost | Ops overhead | Trade-off |
|---|---|---|---|
| **1. Self-hosted (S3/GCS)** | ~$0.02–0.023/GB-mo storage + compute | High — Sun's own Terraform manages ingesters/queriers/compactors, scaling, upgrades | Cheapest per-GB; highest ongoing engineering burden. No new vendor. |
| **2. Hosted Grafana Cloud** | Roughly $0.55/GB ingested (process + write + retain, 30-day retention) + per-seat fees | Low — only Promtail/agent deployment to manage | ~20x the per-GB cost of raw object storage, and you pay for ingestion whether it's ever queried — real bill-shock risk from a noisy service. Bundles logs + metrics under one vendor. |
| **3. Defer** | $0 now | None | Right call until there's a concrete GB/day estimate and engineering capacity to commit either way. Blocks OBS-005/OBS-006 engineering pickup, not anything else. |

(Cost figures are order-of-magnitude estimates from public pricing pages, not verified quotes — confirm current rates before committing to a vendor.)

Move this ticket to `READY_FOR_ENGINEERING` once a direction is picked, with the choice recorded here.

## Goal

Give Sun-managed targets a durable log storage story and a clear access path
from any developer machine with permission.

## Acceptance criteria

- Production-like targets store Loki data in durable object storage or a
  persistent backend appropriate for the provider.
- Dev/smoke targets can still opt into ephemeral logs for cost/simplicity.
- `sun logs <svc>` can query the configured durable log backend from a different
  machine than the one that ran `sun deploy`.
- The access model is documented: required credentials, network path, and
  retention behavior.
- Teardown behavior is explicit: destroying compute does not accidentally delete
  retained logs unless the target config says to delete them.
- The design leaves room for a future Datadog-style provider swap without
  changing service code.
