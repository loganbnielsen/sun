Provision Grafana dashboards (workspace + service, templated)

**Depends on:** OBS-008.

## Problem

Grafana ships in `platform/infra/base` with no dashboards provisioned at
all — a user gets an empty Grafana and has to hand-build every panel.
`docs/architecture/observability-design.md` calls for a workspace overview
and per-service dashboards filtering by Sun's label taxonomy rather than
namespace/pod names.

This is also the least concretely specified part of the design doc —
expect to make real layout/panel decisions in this ticket, not just wire up
something already fully speced.

## Goal

Ship the lazy version: two dashboards total, not one per domain/service.
Grafana already supports template variables and repeating panels — use
those instead of generating a dashboard file per service.

- **Workspace overview** — one dashboard, all domains' request rate/error
  rate/pod health, no template variable needed (it shows everything at
  once).
- **Service dashboard template** — one dashboard parameterized by
  `$domain`/`$service` template variables (populated from Prometheus/Loki
  label values, not a static list Sun maintains); selecting values in the
  dropdown re-scopes every panel. This is what every service "has its own
  dashboard" without Sun ever generating or maintaining N dashboard files.

No per-service generated dashboard files. No domain-level dashboard
separate from the service template — a domain is just one filter value away
from a service in the same templated dashboard.

## Acceptance criteria

- Dashboards are provisioned via Grafana's sidecar ConfigMap-loading
  mechanism (`grafana.sidecar.dashboards`, already available in the
  `loki-stack` chart Sun uses) rather than manual import.
- Exactly two dashboard JSON definitions ship: workspace overview, service
  template. Adding a new service requires zero Sun-side dashboard changes.
- Both dashboards query Loki/Prometheus using the OBS-008 labels
  (`workspace`/`domain`/`service`/`primitive`), not raw namespace/pod names.
- The service template's `$domain`/`$service` variables are queried from
  Prometheus/Loki label values (`label_values(...)`), not hardcoded against
  Sun's own service-discovery scan — so it also shows up-to-date results if
  something outside `sun up`'s knowledge is running.
- Documented: service logs view and deploy/release timeline (mentioned in
  the design doc) are explicitly deferred, not silently dropped — say so.
- Verified against a real Grafana instance that both dashboards actually
  render and the template variables populate (a JSON dashboard definition
  Grafana rejects at load time is worse than none) — this one needs at
  least a local `sun dev up` check, unlike the AWS-only tickets earlier
  which stayed at static validation.
