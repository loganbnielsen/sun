Wire `obs-tempo-eio` into Sun: framework backend, Tempo deployment, trace-lookup link

**Depends on:** OBS-041.

## Problem

`OBS-041` builds `obs-tempo-eio` as a standalone, Sun-independent package.
Nothing in Sun actually uses it yet — no framework primitive emits real
spans to a running Tempo, no `platform/infra/base` Terraform deploys
Tempo, and there's no way to jump from a `trace_id` in a Loki log line to
its trace waterfall.

## Goal

1. **`sun-svc`/`sun-worker`/`sun-fn`**: wire in `obs-tempo-eio` as an
   additional backend alongside the existing Loki/Prometheus ones — same
   shape of config/plumbing decision those frameworks already make for
   backend selection (`framework/sun-svc/lib/`, `framework/sun-worker/lib/`,
   `framework/sun-fn/lib/` — check how they currently construct
   `Obs_eio.create ~backend:...` and thread a second/third backend in,
   likely via `Obs_eio`'s support for multiple backends if it exists, or a
   small fan-out wrapper if it doesn't — check `obs_eio.mli` for this
   before inventing a wrapper). Start with `-svc` only, matching how
   `-worker`'s metrics work landed service-by-service in `OBS-035`, not
   all three primitives at once.
2. **`platform/infra/base`**: deploy Tempo itself (a new `helm_release`,
   likely `grafana/tempo` chart) and wire a Grafana Tempo datasource via
   the same sidecar ConfigMap-loading convention `OBS-011` already
   established for the Prometheus datasource
   (`kubernetes_config_map.grafana_prometheus_datasource` in
   `platform/infra/base/main.tf` is the template to mirror).
3. **A minimal trace-lookup link** — a way to jump from a `trace_id` seen
   in a Loki log line to that trace's waterfall in Tempo (Grafana's
   built-in Loki-derived-fields-to-Tempo-link feature is the natural fit —
   the Loki datasource config gains a `derivedFields` entry matching the
   existing `trace_id=` logfmt pattern `obs-loki-eio` already emits). As of
   `OBS-039`, the Loki datasource is its own resource,
   `kubernetes_config_map.grafana_loki_datasource` in `platform/infra/base/
   main.tf` (Prometheus's sibling is `grafana_prometheus_datasource`,
   dashboards are `grafana_dashboards`) — no longer auto-provisioned by a
   bundled Grafana subchart, since Grafana is now its own standalone
   `helm_release`.

## Non-goal

- A dedicated trace-analysis dashboard beyond the minimal lookup link
  above — start with "can jump from a log line to its trace," not a full
  APM-style trace search UI.
- Retrofitting `-worker`/`-fn` in the same pass — follow-up tickets once
  `-svc` proves the pattern out, matching `OBS-035`'s own precedent of
  landing primitives one at a time.
- Alloy as a collector in front of Tempo (`OBS-039` scopes Alloy to log
  shipping only) — spans push directly to Tempo via `obs-tempo-eio`.

## Acceptance criteria

- `-svc` emits real spans to a running Tempo instance in local dev
  (`sun dev up`).
- Tempo is deployed by `platform/infra/base` with a working Grafana
  datasource, validated the same way `OBS-036`/`OBS-039` validate new
  chart/datasource wiring (`terraform validate`, `helm show values`).
- A `trace_id` visible in a Loki log line can be clicked through to its
  trace in Tempo from Grafana.
