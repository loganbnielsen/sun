Diagnose an actively-running Fn's pod health, not just its last completed run

**Depends on:** None.

## Problem

OBS-026's CronJob-status-based `Ephemeral` diagnosis (`sun_cli_rollout_diagnosis.ml`)
treats any currently-active run (`active_count > 0`) as healthy without
inspecting the run's own pod. A scheduled function stuck in `Pending`,
`ImagePullBackOff`, or crash-looping mid-run won't be flagged until it
actually terminates (bounded by `backoffLimit: 3`, so this is a real but
time-limited blind spot, not indefinite).

Flagged during review of PR #85 (OBS-026): "If this PR wants correct Fn
health, inspect active Job/pod state; otherwise rename the behavior as
'last completed run status' and file active-run diagnosis separately." The
latter was chosen for that PR — this ticket is the "file it separately"
half.

## Goal

`sun status`/`sun logs`'s Fn diagnosis also catches a currently-running
scheduled invocation that's actively broken, not only a completed one that
failed.

## Decision

Went with the approach the Open Question favored: `status.active[].name` on
the CronJob (now parsed as `cronjob_status.active_job_names`) names the
active Job directly, and its pods carry the `job-name=<name>` label
Kubernetes' Job controller sets — scoping the fetch to exactly this run's
pod(s), never a broader/historical list.

One correctness point found while implementing: an active run's pod
reaching `Succeeded` is the *expected* successful outcome, not a failure —
unlike a `Continuous` service's pod (where `Succeeded` is abnormal). Reusing
`format_service_diagnosis` as-is would have misreported a normally-completed
run as failed during the window between the pod finishing and the CronJob
controller clearing `status.active`. Added a dedicated
`format_active_run_diagnosis` (pass `is_healthy OR Succeeded`) instead of
reusing the `Continuous` formatter.
