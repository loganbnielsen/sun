OBS-024's zero-pods-is-degraded fix falsely flags idle scheduled functions

**Depends on:** None.

## Problem

`discover_services` includes `_fn` directories (CronJob-backed scheduled
functions), but `cmd_status.ml`'s `declared_services` drops the
`primitive` field, and `service_diagnoses_named` runs the same pod-based
diagnosis for every declared service regardless of primitive. After
OBS-024 (merged in PR #83), `format_service_diagnosis []` returns "No
pods found" instead of `None` — correct for a `Svc`/`Worker`
(Deployment/Rollout-backed, expected to have a continuously running pod),
but wrong for `Fn`: a scheduled function has no pod between runs *by
design*. Every idle scheduled function now reports `DEGRADED` in `sun
status`, which is worse than the bug OBS-024 fixed.

Note: this was originally caught and fixed as a same-PR follow-up commit
on OBS-024's branch, but the PR was merged (by the user) before that
follow-up landed, so it's being tracked and re-applied here as fresh work
against current `main` instead.

## Goal

Zero pods is a real finding for `Svc`/`Worker`, but not for `Fn`. An `Fn`
with an actively crash-looping pod (during a run) should still be flagged
— only the "no pod at all" case is expected/healthy for `Fn`.

## Acceptance criteria

- `Sun_cli_rollout_diagnosis.format_service_diagnosis`/
  `diagnose_service_live` take a way to distinguish "this primitive is
  expected to have a continuously running pod" from "this primitive is
  normally idle between runs" (e.g. `~expects_continuous_pods:bool`,
  defaulting to `true` to preserve today's behavior for existing callers
  that don't have primitive info readily available). When `false`, an
  empty pod list stays `None` (healthy), matching pre-OBS-024 behavior;
  unhealthy pods, when present, are still flagged either way.
- `cmd_status.ml`'s `declared_services` keeps the `primitive` alongside
  each service's name/k8s-name, and `service_diagnoses_named` passes
  `~expects_continuous_pods:false` for `Fn` services, `true` for
  `Svc`/`Worker`.
- `sun status <domain>` and `sun status <domain>/<fn-service>` report a
  healthy scheduled function as `healthy`, not `DEGRADED`, when it simply
  has no pod running at the moment.
- Tests cover: `format_service_diagnosis` with `~expects_continuous_pods:
  false` and an empty pod list returns `None`; with `true` (or the
  default) it still returns the "No pods found" diagnosis as OBS-024
  shipped; an `Fn` with actually-unhealthy pods present is still flagged
  either way.
