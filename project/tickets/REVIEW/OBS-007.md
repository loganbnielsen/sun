Durable metrics storage (self_managed_durable profile)

**Depends on:** OBS-005.

## Problem

OBS-005 defines an `observability_backend = "self_managed_durable"` profile
but leaves its implementation as a placeholder. For metrics, `Prometheus`
`prometheus_persistent_storage` is a local-PVC toggle — metric history is
lost if the volume goes with the node/cluster.

## Goal

Implement the `self_managed_durable` profile for metrics. Prometheus
durability has more architectural options than Loki's (Thanos, Mimir, plain
long-term remote_write); this ticket owns picking one for Sun's self-managed
path — that choice was deliberately left out of OBS-005 so it doesn't block
the interface from shipping.

## Acceptance criteria

- Pick and document the self-managed long-term-storage architecture (Thanos
  sidecar + object storage, or Mimir, or another documented option) and
  justify the choice briefly in the PR — this is an implementation decision
  for this ticket, not a repeat of OBS-005's interface work.
- When `observability_backend = "self_managed_durable"`, Prometheus retains
  metric history beyond a single pod/PVC lifetime via the chosen backend.
- A developer on a different machine than the one that ran `sun deploy` can
  query current and historical metrics for a service (via Grafana, a
  `sun`-CLI command, or documented direct query access — pick one, don't
  require standing up bespoke tooling per developer).
- Required IAM/credentials are provisioned by the same Terraform module that
  provisions the rest of the target's infra.
- Teardown behavior is explicit: destroying the cluster does not delete
  retained metrics unless the target config says to.
- Documented: what this profile costs to run and what it requires from the
  user's cloud account.
- **Scope:** AWS only (`platform/infra/aws` + `platform/infra/base`). GCP is a
  deliberate gap for now, not a missing requirement.
- **Verification:** `dune build`/`terraform validate` only — no live
  cluster/AWS smoke test in this pass.
