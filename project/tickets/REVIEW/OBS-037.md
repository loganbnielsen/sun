sun deploy pushes a structured release-event log line to Loki

**Depends on:** None.

## Problem

Deploy/release events aren't recorded anywhere queryable today. `sun deploy`
prints progress to stdout and updates local state via
`Sun_cli_deployment_state` (`cli/sun/lib/sun_cli_deployment_state.ml`) —
nothing reaches Grafana, Loki, or Prometheus. `docs/architecture/
observability-design.md`'s Dashboard Shape section specs a "deploy/release
timeline" dashboard (tracked in `OBS-038`), but no dashboard can show release
events until something actually emits one.

## Decision (resolved 2026-09-04)

Push one structured Loki log line per successful deploy — chosen over a
Grafana annotation API call or a synthetic Prometheus metric because it is
the only mechanism that works uniformly across all three observability
backend modes (`local`, `self_hosted_durable`, `external`):

- **Grafana annotations** require a self-hosted Grafana instance, which
  `external` mode explicitly does not run (`docs/deployment/
  observability-backends.md`) — the annotation approach would need a
  documented gap for that mode.
- **A Prometheus metric** (e.g. a Pushgateway gauge) doesn't render as a
  timeline marker as naturally as a log line does, and doesn't unlock
  anything a log line doesn't already give a timeline dashboard.
- **A Loki log line** works everywhere logs already go: `local`/
  `self_hosted_durable` push to Sun's in-cluster Loki; `external` ships to
  whatever Loki-compatible endpoint the user has configured, same as every
  application log line already does.

This does not preclude adding Grafana annotations later as a richer visual
layer specifically for `local`/`self_hosted_durable` (where Grafana already
exists) if `OBS-038`'s log-line-based timeline turns out to render poorly
once dogfooded — deliberately not building that now, per this repo's
YAGNI-first house rules.

## Goal

`sun deploy` (real apply, not `--dry-run`/`--emit-to` — see Non-goal) emits
one structured log line per service per successful deploy, containing at
minimum: `workspace`, `env`, `domain`, `service`, `primitive`, `release`
(matching the taxonomy label set `render_taxonomy_labels` already emits —
`cli/sun/lib/sun_cli_manifest_yaml.ml:173-189` — so the log line and the
manifest's labels describe the same release consistently) and a fixed
event-type field (e.g. `event=deploy`) that `OBS-038`'s dashboard query can
filter on without colliding with ordinary application log lines.

## Design notes for implementation

- **Reuse the existing push client, don't build a second one.** `~/Code/
  obs-loki-eio`'s `Obs_loki.create` + `Obs_eio` (see its `.mli` for the
  push-client shape: one HTTP POST per span/log line, no buffering) is the
  same mechanism application code already uses to reach Loki. `sun deploy`
  is a short-lived CLI process, not a long-running Eio service with spans —
  confirm whether the existing `Obs_eio`/`Obs_loki` API fits a single
  one-shot push cleanly, or whether it needs a minimal one-shot helper
  added to `obs-loki-eio` (edit there, re-pin, per this repo's usual
  `obs-*` workflow — see `.claude/CLAUDE.md`).
- **Loki push URL resolution is a new problem, not an existing one.**
  `cli/sun/lib/sun_cli_observability_url.ml`'s `resolve` function resolves
  Grafana *UI* URLs (`local` → `http://localhost:3000`, `self_hosted_durable`
  → `https://grafana.<base_domain>`), not a Loki *push* endpoint — and for
  `external` mode there is no generated URL at all today (`resolve` returns
  `No_url` deliberately). `sun deploy` needs its own resolution: for
  `local`/`self_hosted_durable`, the in-cluster Loki push address (not
  Ingress-exposed the way Grafana is — direct-deploy mode already runs
  `kubectl`/has cluster access, so port-forwarding or an in-cluster address
  is available; GitOps mode's CI runner does not have this by default, and
  that gap needs to be either solved or explicitly documented as
  unsupported for GitOps-mode release events). For `external`, reuse
  whatever Loki push URL the target's config already carries for
  application-level log shipping — check `Sun_cli_config`'s target fields
  for an existing one before adding a new config field.
- Failure to push the log line must never fail the deploy itself — same
  "backend errors don't propagate to application code" contract
  `obs-loki-eio` already documents for its span-close path. Print a
  warning and continue.

## Non-goal

- `--dry-run` and `--emit-to` (GitOps manifest emission without an apply)
  don't push anything — there's no real deploy event to record, matching
  the existing precedent of skipping the `POSTGRES_URL` check and the
  consumer-group-rename guard in those same modes (`cmd_deploy.ml`).
- Grafana annotations and the Prometheus metric approach (see Decision
  above) — explicitly not building either now.
