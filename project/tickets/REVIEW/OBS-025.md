sun logs --no-follow's actual Loki query is still not target-aware

**Depends on:** None.

## Problem

OBS-015 made `--target` resolve `observability_backend`/`base_domain` for
the printed Grafana URL, but `sun logs --no-follow`'s actual Loki
*snapshot query* still always uses `--loki-base-url`'s flag default
(`http://localhost:3100`), completely independent of `--target`. For a
`self_hosted_durable` or `external` target, `sun logs` queries the wrong
place (`localhost:3100`, which isn't running there), gets a connection
failure, and falls back to `kubectl logs` — silently doing the wrong thing
instead of skipping the Loki attempt cleanly. Same class of bug OBS-018
already fixed for `sun status`'s reachability checks.

## Goal

`sun logs --no-follow` only attempts a Loki query when it has a URL that's
actually meaningful: an explicit `--loki-base-url`, or the `Local`
backend's hardcoded default. Any other backend with no explicit URL skips
the Loki attempt entirely and goes straight to `kubectl logs`, instead of
querying `localhost` and pretending that was a real check.

## Acceptance criteria

- `--loki-base-url` becomes optional (no forced default), matching
  `sun status`'s existing `--loki-base-url`/`--prometheus-base-url` shape.
- When resolving the URL: an explicit `--loki-base-url` always wins;
  otherwise the `Local` backend's `http://localhost:3100` default is used;
  otherwise (any other backend, no explicit URL) the Loki query is skipped
  entirely — print something like "(Loki not checked for backend
  <backend>; showing Kubernetes logs)" and go straight to
  `exec_kubectl_logs`, rather than querying localhost.
- `sun logs` with no `--target`/`--observability-backend` (today's default
  usage) is unchanged: still queries `http://localhost:3100` by default.
- `follow` mode is unaffected either way (it already always uses
  `kubectl logs --follow`, never Loki).
