sun-worker exposes no Prometheus metrics port, so workers never show up in Grafana

**Depends on:** None.

## Problem

`cli/sun/lib/sun_cli_manifest_yaml.ml`'s `prometheus_annotations` only adds
`prometheus.io/scrape`/`prometheus.io/port` for `Http_service` (`-svc`)
Deployments — already called out in its own comment as "Background_worker's
own metrics port isn't wired at the manifest level yet (separate,
pre-existing gap, not addressed here)" (OBS-011). The gap is deeper than the
manifest annotation: `framework/sun-worker/lib/` has no HTTP listener at all
today, so there's no `/metrics` endpoint for an annotation to even point at
— `-svc` already runs an HTTP server (routes + auth) that a metrics endpoint
piggybacks on; `-worker` is a pure Kafka consumer loop with nothing
listening.

Net effect: the OBS-011/030 Grafana "Service template" dashboard's
`$service` variable (populated from live Prometheus label values) will
never list a worker, and worker-side metrics `sun-worker` already computes
internally (ok/error counters, duration histogram — see
`framework/sun-worker/lib/`'s existing metrics, per this repo's CLAUDE.md)
never reach Prometheus at all in a real deployment.

## Goal

A deployed `-worker` service's metrics (message counts, error counts,
processing duration) are scrapeable by Prometheus and show up in the same
Grafana dashboards `-svc` already populates.

## Decision

Scrape, not push — `Obs_prometheus.push` is documented as being for
short-lived jobs; a long-running consumer needs the renderer + scrape model
`-svc` already uses. Split the work along package boundaries instead of
building the HTTP listener inside `sun-worker` from scratch:

- **`obs-prometheus-eio`** (`~/Code/obs-prometheus-eio`): add the smallest
  primitive that does this, not a worker-aware metrics server. Something
  like `serve : sw:Eio.Switch.t -> net:_ Eio.Net.t -> Eio.Net.Sockaddr.stream
  -> (unit -> string) -> unit` — given a switch and an already-chosen socket
  address, bind and respond to `GET /metrics` with the renderer's output
  until the switch is cancelled. It owns none of: which port, when to
  start/stop, or how this fits into a worker's shutdown sequence — those
  stay call-site decisions. `cohttp-eio` is currently a test-only dependency
  there (see `obs-prometheus-eio.opam`); this promotes it to a real library
  dependency, which is fine (pre-alpha, no back-compat constraint). Edit in
  place, then re-pin into this switch per this repo's usual `obs-*`
  workflow.
- **`framework/sun-worker/lib/`**: owns lifecycle, port choice, cancellation,
  and docs — picks the default port (with an override), passes its own
  switch so shutdown ties into the consumer loop's, and calls the new
  primitive rather than wiring `Cohttp_eio` directly itself.
- **`cli/sun/lib/sun_cli_manifest_yaml.ml`**: extend `prometheus_annotations`
  to also cover `Background_worker` Deployments, pointing
  `prometheus.io/port` at the worker's new metrics port (closes the
  OBS-011 gap this ticket's Problem section references).
