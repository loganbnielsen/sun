The real `sun dev up` k3d cluster's Loki (Helm-deployed, not the local Docker test container) genuinely rejects reads and writes with "too many unhealthy instances in the ring" — BUG-006's original diagnosis, never actually applied.

**Depends on:** None.

## Problem

`platform/infra/base/main.tf`'s `helm_release "loki"` never set
`loki.commonConfig.replication_factor`, so it defaulted to the chart's own
recommended value of 3 — appropriate for a real multi-instance ingester
ring, wrong for this module's single `singleBinary.replicas = 1`. Every
write and most reads fail because the ring's quorum check needs 2 live
replicas and only 1 exists.

This is BUG-006's original diagnosis (`platform/infra/base/main.tf`'s
Helm release lacking the RF override) — that ticket was silently deleted
during a batch ticket-state operation on 2026-09-05 without the fix ever
being applied (see BUG-008's writeup for the full history of that loss;
BUG-008 itself turned out to be a *different*, unrelated bug — a local
`kubectl port-forward` shadowing a Docker test container's port — found
while investigating what looked like the same symptom. This ticket is
the real, original bug, confirmed live in the actual cluster this time).

Confirmed directly against Loki's own `/config` endpoint on a running
cluster: `common.replication_factor: 3`. Confirmed the fix works by
applying it live via `helm upgrade loki ... --set
loki.commonConfig.replication_factor=1` against the running cluster —
both push (`HTTP 204`, 3/3) and query (`query_range` returned the pushed
lines) succeeded immediately after the rollout, where they failed with
the ring error before.

## Goal

A fresh `sun dev up` cluster's Loki accepts writes and serves queries
immediately, with no manual `helm upgrade` needed.

## Remediation (done, verified live)

Added `set { name = "loki.commonConfig.replication_factor" value = "1" }`
to `helm_release "loki"` in `platform/infra/base/main.tf`, alongside the
existing `deploymentMode`/`singleBinary.replicas`/etc. overrides for the
single-binary local/self-hosted-durable profiles.

## Acceptance criteria

- `terraform plan`/`apply` (or an equivalent `helm upgrade` against an
  existing cluster) shows the new `replication_factor` value taking
  effect.
- A fresh `sun dev up` cluster's Loki accepts a push (`HTTP 204`)
  immediately after `/ready` reports true, with no "live replicas" error.
