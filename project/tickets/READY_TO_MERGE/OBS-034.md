Nothing stops selecting self_hosted_durable observability against a GCP-provisioned cluster

**Depends on:** None.

## Problem

`docs/deployment/observability-backends.md` says plainly: "GCP is a
deliberate gap, not an oversight" for `self_hosted_durable` (it sets
`eks.amazonaws.com/role-arn` IRSA annotations, which only mean anything on
EKS). But `platform/infra/base/main.tf`'s
`terraform_data.observability_backend_validation` only checks that
`loki_irsa_role_arn`/`thanos_irsa_role_arn`/the two S3 bucket names are
non-empty strings — it has no cloud-provider awareness at all. Nothing
rejects applying `self_hosted_durable` against a GKE (or any non-EKS)
cluster; it would misconfigure silently (the IRSA annotation is simply
meaningless there) rather than fail fast with a clear error.

`platform/infra/base` is deliberately cluster-agnostic (works with any
Kubernetes cluster from any provisioning path), so it has no first-class
signal for "which cloud am I running on" to check against.

## Goal

Applying `self_hosted_durable` against a non-AWS cluster fails with a clear
error at `terraform apply` time, not a silent misconfiguration discovered
later when logs/metrics don't actually persist.

## Decision

Add an explicit `cloud_provider` variable to `platform/infra/base` — a small
recognized-value fact, not a reversal of `base`'s cluster-agnostic design —
and gate `self_hosted_durable` on it:

```hcl
variable "cloud_provider" {
  type        = string
  description = "Cloud provider for provider-specific Kubernetes integrations."
  default     = "aws"
  validation {
    condition     = contains(["aws", "gcp"], var.cloud_provider)
    error_message = "cloud_provider must be one of: aws, gcp."
  }
}
```

Extend `terraform_data.observability_backend_validation`'s condition so
`self_hosted_durable` also requires `cloud_provider == "aws"`:

```hcl
condition     = var.observability_backend != "self_hosted_durable" || var.cloud_provider == "aws"
error_message = "observability_backend = \"self_hosted_durable\" is currently supported only on AWS/EKS because it uses IRSA. GCP support requires Workload Identity wiring."
```

`base` still does no provider-specific work itself — `gcp` is a recognized,
explicitly-unsupported-for-this-feature value, not an implementation. Catches
both the malformed-ARN case and the "real AWS ARNs pointed at a GCP cluster"
case the format-check-only approach couldn't.

Building the actual GCP adapter (GCS bucket + Workload Identity module,
mirroring `aws/`'s S3 + IRSA modules) is real, separate, larger scope —
deferred to INFRA-003 rather than built speculatively ahead of a concrete
GCP feature that needs it.
