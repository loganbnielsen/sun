Make `sun up` handle stale local service port-forwards cleanly.

**Depends on:** RELEASE-002.

**Problem:** During the alpha.6 release-user smoke test, `sun up` built,
pushed, and rolled out both services but exited nonzero because port `8080` was
held by an old `kubectl port-forward` for another workspace's `charge-svc`.
The CLI printed a useful warning and remediation command, but the first run
still failed even though the Kubernetes deployment was healthy.

**2026-06-12 reproduction:** A fresh `dogfood_2026_06_12` run hit the same
class of issue, but worse: port `8080` was still held by
`kubectl port-forward -n dogfood-2026-06-11-payments svc/charge-svc 8080:80`.
`sun up` exited 0 and printed `http://localhost:8080 (port-forward running in
background)`, while requests to that URL initially hit the older workspace.

**Goal:** Reduce confusion when multiple Sun workspaces reuse the same local
service port by detecting stale Sun-managed port-forwards and either replacing
them safely or reporting a more precise recovery path.

**Remediation:**

1. Inspect the current port-forward startup logic used by `sun up`.
2. Detect whether the process bound to the requested local port is a
   `kubectl port-forward` for a different Sun workspace/namespace.
3. Choose a conservative behavior:
   - replace only stale Sun-managed port-forwards when the target namespace or
     service does not match the current deploy, or
   - keep the existing failure behavior but print the owning namespace/service
     and an exact command to terminate only that stale process.
4. Add tests around stale port-forward detection and message formatting where
   feasible.

**Acceptance criteria:**

- `sun up` no longer leaves a release-user guessing which workspace owns a busy
  local port.
- Existing successful port-forward behavior is unchanged.
- The CLI does not kill unrelated user processes.
- The release smoke-test workaround is documented as this follow-up.
