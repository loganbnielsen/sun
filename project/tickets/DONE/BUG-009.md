Invalid — same root cause as BUG-008: a `kubectl port-forward` to the real k3d cluster's Tempo was shadowing the query port, not a real `obs-tempo-eio`/`https-eio` concurrency bug.

**Depends on:** None.

## What actually happened

Originally diagnosed as: two `Sun_obs.t` handles (`order-svc`,
`fulfillment-worker`) pushing spans to Tempo concurrently dropped 5 of 6
spans, with zero client-side errors. That diagnosis was wrong — see
BUG-008 for the full root-cause writeup. This session had a long-running
`kubectl port-forward -n monitoring svc/tempo 3200:3200` bound to
`127.0.0.1:3200`, while `ensure-tempo.sh`'s Docker container's query API
publishes `0.0.0.0:3200`. Every trace lookup this investigation made
against `http://localhost:3200/...` was silently answered by the **real
k3d cluster's Tempo**, not the container the demo's spans were actually
pushed to (OTLP push, on port 4318, had no competing forward and worked
correctly the whole time — only the *query* side was shadowed). The
`tempo_distributor_spans_received_total=1` metric read during the original
investigation reflected unrelated real traffic on the k3d cluster's Tempo,
not this demo's own spans landing anywhere.

Killing the two colliding port-forwards (Loki 3100, Tempo 3200) and
restarting the Docker containers made `examples/local-demo`'s Tempo
assertions pass reliably: 3 consecutive full runs, both Tempo assertions
(`order-svc` span, `fulfillment-worker` child span) passing every time,
alongside all other assertions (HTTP, both Prometheus metrics, Loki,
PostgreSQL). No code change was needed in `obs-tempo-eio`/`https-eio`
concurrency handling — there was nothing to fix there.

## Remediation

Covered by BUG-008's remediation (port-conflict detection in
`ensure-*.sh` scripts) — no separate action needed here. Closing this
ticket; if a genuine Tempo-under-concurrency issue resurfaces with a
clean, non-shadowed port, open a fresh ticket with that evidence rather
than reopening this one.
