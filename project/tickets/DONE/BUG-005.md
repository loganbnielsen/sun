`sun up`'s Docker build fails for any freshly scaffolded workspace with a Postgres-backed service

**Depends on:** None.

## Problem

Found running a real end-to-end local demo (scaffold → `dune build` → `sun
up`) as part of closing out the observability-readiness work, right after
fixing two unrelated scaffold-template bugs in PR #109 (`require_ok`
unused-value error, a schema-check type error) that had been silently
blocking `dune build` on any fresh scaffold. `sun new workspace` produces
`notify_worker`'s `bin/dune` depending on `pg-eio`, `caqti-eio`,
`caqti-eio.unix`, `caqti-driver-postgresql` — and `kafka_eio_service`,
`obs-eio`, `obs-loki-eio`, `obs-prometheus-eio`, `obs-tempo-eio` for both
services. None of these are vendored into `vendor/framework`/
`vendor/integrations` (all fully externalized per `~/Code/CLAUDE.md`'s
repo layout notes) and none are published to the public opam-repository —
`sun_cli_scaffold_templates.ml`'s `tpl_dockerfile` never pinned any of
them, so the Docker build stage's plain `opam install` could never find
them. This meant `sun up` could never succeed for a freshly scaffolded
workspace, for any workspace that includes a Postgres-backed service (the
default scaffold does).

## Resolution (PR #110)

Three compounding causes, all fixed in `tpl_dockerfile`:

1. **Missing opam pins.** Added the same `opam pin add <pkg>
   https://github.com/loganbnielsen/<pkg>.git#main -y` steps this repo's
   own `.github/workflows/ci.yml` already uses successfully (`https-eio`,
   `kafka-eio`, `obs-eio`, `obs-loki-eio`, `obs-prometheus-eio`,
   `obs-tempo-eio`, `pg-eio`), placed *before* the existing `opam install`
   line — pin order matters, since pinning `https-eio` after a plain
   install already resolved a lower `tls-eio` fails (a pin alone doesn't
   upgrade an already-installed package's already-installed
   dependencies).
2. **Stale base-image opam-repository.** `https-eio`'s `#main` opam file
   requires `tls-eio >= 2.1.0`; pinning it inside the `ocaml/opam:
   ubuntu-24.04-ocaml-5.4` base image reported "no matching version" even
   after `opam update`, because the base image's default remote is a
   local `git+file://` checkout with no upstream for `opam update` to
   fetch from. `opam repository set-url default https://opam.ocaml.org`
   before `opam update` resolves it.
3. **Missing plain opam packages.** `jose` and `http` —
   `framework/sun-svc/lib/dune`'s own real, published dependencies (HTTP
   server + JWT auth verification) — were missing from the base `opam
   install` line entirely, independent of the pin issue. This is why
   `notify_worker` (no auth dependency) built fine once the pins were
   fixed, while `charge_svc` kept failing with `Library "jose" not found`
   until this was found too.

Verified end-to-end, not just statically: `sun new workspace shopdemo`
followed by a real `sun up` built both generated services' real Docker
images, pushed them, and deployed them to a live local k3d cluster —
confirmed both pods `Running` (`shopdemo-payments/charge-svc`,
`shopdemo-comms/notify-worker`), and exercised the live `charge-svc` with
a real `curl` request through to a 202 response.

Deliberately did not add an automated `docker build` regression test — a
real Docker build is slow and network-dependent, and adding that cost to
the fast `dune test` suite every contributor runs many times a day wasn't
justified by this fix alone. The end-to-end manual verification above is
a stronger signal than a synthetic check would be; revisit as a
dedicated, separately-scoped CI job if this regresses.

## Acceptance criteria

- ✅ `sun new workspace foo && cd foo && sun up` succeeds end-to-end
  (build, push, deploy) for both generated services on a machine with no
  pre-existing local opam pins for these packages.
- ✅ Confirmed via real pods running in a live cluster, not a dry-run or
  static check.
