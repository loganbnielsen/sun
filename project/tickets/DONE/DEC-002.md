Decide the initial hosted runtime tenancy model.

**Question:** Should hosted runtime clusters be single-tenant, multi-tenant, or tier-dependent?

**Context:** Single-tenant clusters simplify isolation and enterprise trust but raise cost and provisioning complexity. Multi-tenant clusters improve unit economics and speed but require stronger isolation, quota, and noisy-neighbor controls. A tiered model may be right long term but can complicate the first implementation.

**Options:**

1. Single-tenant per customer.
2. Multi-tenant shared clusters.
3. Tier-dependent tenancy.

**Decision criteria:**

- Security and isolation expectations for early customers.
- Cost floor for small startup workloads.
- Operational complexity of the control plane.
- Impact on secrets, observability, domains, and billing design.

**Acceptance criteria:**

- A written decision chooses the first supported tenancy model.
- The decision identifies what changes, if anything, in the deployment plan.
- Follow-up implementation tickets are created if the answer requires substrate changes.

**Decision:**

The first Sun-hosted runtime is single-tenant per customer.

Each hosted customer gets an isolated runtime substrate rather than sharing a
cluster with unrelated customers. Multi-tenant and tier-dependent models remain
future options, but they are not part of the first hosted executor boundary.

**Implications:**

- FEAT-010 can assume the hosted executor submits a deployment plan to a
  customer-scoped environment.
- Deployment plans do not need per-service tenant-isolation fields beyond the
  existing workspace/environment identity.
- The hosted control plane eventually needs customer-to-environment ownership,
  release history, and substrate lifecycle records.
- The first hosted version prioritizes isolation and trust over the lowest
  possible cost floor.
- Multi-tenant concerns such as cross-customer quota enforcement, shared-cluster
  network isolation, and noisy-neighbor scheduling are deferred.
