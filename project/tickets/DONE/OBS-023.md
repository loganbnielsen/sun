Source dashboard domain/service variables from Loki, not Prometheus, so workers/functions are selectable

**Depends on:** None.

## Problem

`docs/architecture/observability-design.md`'s goal states "a domain,
service, worker, or function can be filtered without knowing Kubernetes
names," but `service-template.json`'s `$domain`/`$service` template
variables query `label_values(up{...}, domain|service)` — the Prometheus
`up` metric only exists for scraped HTTP services (`prometheus.io/scrape`
is only set on `Http_service` pods per OBS-011). A worker or function with
real Loki logs won't appear in either dropdown unless a same-named/same-
domain HTTP service happens to also be scraped. Workers/functions aren't
first-class in the one place meant to make them filterable without
Kubernetes knowledge.

## Goal

Domain/service selection in the dashboards includes every primitive that
has emitted any log line, not just scraped HTTP services — without
requiring new metrics instrumentation for workers/functions (out of scope
here).

## Acceptance criteria

- `service-template.json`'s `$domain`/`$service` (and
  `workspace-overview.json`'s `$workspace`) template variables query Loki
  (`label_values({...}, domain|service|workspace)`) instead of Prometheus,
  since Promtail's relabel config (OBS-008) already attaches
  `workspace`/`domain`/`service` labels to every primitive's log stream,
  not just scraped ones.
- The panel queries themselves (`sun_svc_requests_total`, `up{...}`, p95
  duration) stay on Prometheus unchanged — those inherently only apply to
  scraped HTTP services; only the variable *selection* source changes.
- A worker or function that has emitted at least one log line is now
  selectable in `$domain`/`$service`, and its Logs panel populates
  correctly when selected (its metrics panels legitimately stay empty —
  documented as a known, separate gap, not something this ticket fixes).
