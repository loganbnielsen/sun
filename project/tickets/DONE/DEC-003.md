Decide the secrets backend for Sun-hosted mode.

**Question:** Which secrets backend should hosted mode assume?

**Context:** Sun already keeps secret values out of deployment plan JSON and renders Kubernetes `Secret` references for local/customer-cloud paths. Hosted mode needs a real source of truth for secret storage, audit, rotation, and injection.

**Options:**

1. Kubernetes Secrets as the first backend.
2. Cloud-provider secret managers.
3. Vault or another dedicated secrets service.
4. A Sun-managed abstraction with pluggable backends later.

**Decision criteria:**

- Secret value never appears in deployment plan output.
- Rotation and audit story.
- Fit with hosted tenancy model.
- Implementation burden for the hosted executor spike versus production hosted mode.

**Acceptance criteria:**

- A written decision names the first hosted secrets backend.
- The decision defines how deployment plans refer to secrets.
- The decision states whether secret creation belongs to the CLI, hosted UI/API, or external CI.

**Decision:**

Sun exposes one secret-management UX across local, customer-cloud/self-hosted,
and Sun-hosted modes. Users should be able to create, update, list, and delete
environment secrets through Sun commands or APIs without needing support
intervention.

The product model is a Sun-managed secrets abstraction. For the first runtime
backend, secret values may be materialized as Kubernetes `Secret` objects in the
target environment. Hosted mode goes through the Sun control-plane API;
customer-cloud/self-hosted mode can write directly to the target cluster using
the active environment target.

Deployment plans reference secret keys only. Secret values never appear in plan
JSON, rendered manifests, logs, or review output.

**Implications:**

- A future feature ticket should add commands such as `sun secret set`,
  `sun secret list`, and `sun secret delete`.
- FEAT-010 should treat secrets as pre-existing environment inputs referenced by
  key, not values included in deployment submission.
- Hosted users self-serve through Sun CLI/API.
- Self-hosted users get the same Sun CLI experience out of the box, with direct
  Kubernetes editing left as an advanced/admin escape hatch.
- Vault, AWS Secrets Manager, and GCP Secret Manager remain possible future
  backends behind the same Sun secret abstraction.
