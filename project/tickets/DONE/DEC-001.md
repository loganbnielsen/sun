Decide how Sun-hosted builds receive source or artifacts.

**Question:** Should hosted builds pull directly from Git providers, receive artifacts from customer CI, or support both?

**Context:** Pulling from Git providers gives Sun a simple hosted experience, but requires repository integrations and build ownership. Receiving artifacts from customer CI keeps Sun out of source access and build secrets, but makes onboarding less seamless.

**Options:**

1. Git-connected hosted builds only.
2. Customer CI artifact handoff only.
3. Support both, with one path as the default.

**Decision criteria:**

- Fastest credible hosted onboarding.
- Minimum trust and security burden.
- Compatibility with the existing deployment plan model.
- Operational simplicity for the first hosted release.

**Acceptance criteria:**

- A written decision names the default path.
- The decision states whether the alternate path is unsupported, future, or supported immediately.
- FEAT-010 can implement its hosted executor spike without guessing this boundary.

**Decision:**

Sun-hosted deploys initially receive prebuilt image artifacts from customer CI.
The hosted executor accepts a deployment plan plus immutable registry/image refs.
Sun does not pull source code, run builds, or manage build secrets in the first
hosted version.

Git-connected hosted builds are a future option, not part of the first hosted
executor boundary. They should be considered only after hosted platform/deploy/release
orchestration is proven.

**Implications:**

- FEAT-010 should model hosted submission around a deployment plan and image refs.
- Customer CI remains responsible for compiling, testing, building, and pushing images.
- The first hosted control-plane API does not need Git provider OAuth, repo webhooks,
  build cache isolation, build logs, or customer build-secret handling.
- Docs should describe Sun-hosted deployment as "bring prebuilt images" until a
  hosted-build product exists.
