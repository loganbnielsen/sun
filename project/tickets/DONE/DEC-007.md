Decide whether GitOps is core to hosted mode or customer-cloud only.

**Question:** Does GitOps remain a core hosted mechanism or only a customer-cloud option?

**Context:** `sun deploy --emit-to` and Argo CD support make GitOps a strong customer-cloud story. Hosted mode could also use GitOps internally, but exposing that model to hosted users may add concepts the product is trying to hide.

**Options:**

1. GitOps is internal implementation only for hosted mode.
2. GitOps is a visible hosted feature.
3. GitOps is customer-cloud only.

**Decision criteria:**

- Simplicity of the default hosted user experience.
- Auditability and rollback needs.
- Compatibility with hosted release history.
- Whether users need direct manifest visibility in hosted mode.

**Acceptance criteria:**

- A written decision states where GitOps belongs.
- Hosted docs and customer-cloud docs use consistent language.
- FEAT-010 can model hosted submission without implying the wrong GitOps boundary.

**Decision:**

GitOps is a visible customer-cloud/self-hosted option, not the primary hosted
product surface.

Sun-hosted mode may use GitOps internally, but hosted users should interact with
release, deployment plan, status, logs, and rollback concepts rather than Argo CD
or GitOps repository mechanics. Users still need clear visibility into what is
happening: submitted plan, image refs, rendered resource summary, rollout status,
errors, and release history.

Hosted mode should also provide a read-only diagnostic escape hatch for users who
want more detail than the default release view. That escape hatch can expose
rendered manifests, reconciliation events, rollout resource names, Kubernetes
event summaries, and raw failure details. It should expose facts and diagnostics,
not direct ownership of the underlying hosted control plane.

**Implications:**

- FEAT-010 should model hosted submission as a release request and response, not
  as "write manifests to a GitOps repo".
- Hosted UX should expose inspectable deployment plans and release status.
- Customer-cloud docs can continue to present `sun deploy --emit-to` and Argo CD
  as the advanced GitOps path.
- Hosted docs should avoid requiring users to understand Argo CD, sync waves, or
  GitOps repo structure for the default flow.
- If hosted mode uses GitOps internally, that should remain an implementation
  detail unless advanced users explicitly request lower-level diagnostics.
- Hosted diagnostics should be read-only. Direct Argo/Kubernetes write access is
  not part of the default hosted product surface.
