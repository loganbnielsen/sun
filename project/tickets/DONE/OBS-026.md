OBS-024's zero-pods-is-degraded fix falsely flags idle scheduled functions

**Depends on:** None.

## Problem

`discover_services` includes `_fn` directories (CronJob-backed scheduled
functions), but `cmd_status.ml`'s `declared_services` drops the
`primitive` field, and `service_diagnoses_named` runs the same pod-based
diagnosis for every declared service regardless of primitive. After
OBS-024 (merged in PR #83), `format_service_diagnosis []` returns "No
pods found" instead of `None` — correct for a `Svc`/`Worker`
(Deployment/Rollout-backed, expected to have a continuously running pod),
but wrong for `Fn`: a scheduled function has no pod between runs *by
design*. Every idle scheduled function now reports `DEGRADED` in `sun
status`, which is worse than the bug OBS-024 fixed.

Note: this was originally caught and fixed as a same-PR follow-up commit
on OBS-024's branch, but the PR was merged (by the user) before that
follow-up landed, so it's being tracked and re-applied here as fresh work
against current `main` instead.

## Goal

Zero pods is a real finding for `Svc`/`Worker`, but not for `Fn`. An `Fn`
with an actively crash-looping pod (during a run) should still be flagged
— only the "no pod at all" case is expected/healthy for `Fn`.

## Acceptance criteria

- `Sun_cli_rollout_diagnosis.format_service_diagnosis`/
  `diagnose_service_live` take a way to distinguish "this primitive is
  expected to have a continuously running pod" from "this primitive is
  normally idle between runs and has no durable running state." When
  the latter, an empty pod list stays `None` (healthy); unhealthy pods
  that are actually active, when present, are still flagged either way.
- `cmd_status.ml`'s `declared_services` keeps the `primitive` alongside
  each service's name/k8s-name, and `service_diagnoses_named`/
  `print_service_status` pass the right health model for each primitive.
- `sun status <domain>` and `sun status <domain>/<fn-service>` report a
  healthy scheduled function as `healthy`, not `DEGRADED`, when it simply
  has no pod running at the moment, and also when its most recent
  pod(s) finished (successfully or not) rather than being actively
  broken right now.
- Tests cover: the idle (zero-pod) case; a successfully completed pod;
  an old *failed* but terminal pod (kubectl can return several
  historical run pods at once via successfulJobsHistoryLimit/
  failedJobsHistoryLimit, so a stale failure must not keep a
  since-succeeded service looking degraded); and an actively unhealthy
  pod is still flagged regardless of primitive.

### Shipped design (updated across review rounds — see PR #85 for the full history)

The mechanism converged on a `Sun_cli_rollout_diagnosis.pod_expectation`
enum (`Continuous | Ephemeral`), not the originally-proposed
`~expects_continuous_pods:bool` — self-documenting, and it's `required`
on `diagnose_service_live` (no default), since the whole bug came from a
caller applying the wrong model implicitly. `Sun_cli_status.
pod_expectation_of_primitive` translates from `Sun_cli_manifest.primitive`
(kept local to the diagnosis module, not coupled to manifest concepts)
and is directly unit-tested.

`Ephemeral` does not diagnose from pod state at all — multiple
historical run-pods can coexist with no reliable way to tell which is
"latest" from pod state alone. Instead it reads the CronJob's own status
(`lastScheduleTime`/`lastSuccessfulTime`/`active`): a currently-active
run is never flagged (that gap is real but bounded by `backoffLimit`,
tracked separately as OBS-028); idle between runs, the most recently
scheduled run must have a later-or-equal recorded success (compared via
parsed `Ptime` values, not raw RFC3339 strings) or it's a finding. A
`Missing` CronJob (confirmed via kubectl's NotFound) is always a
finding; an `Unavailable` fetch (transient failure) stays silent.
