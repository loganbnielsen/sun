**Depends on:** None.

## Problem

`sun_cli_manifest_yaml.ml`'s `network_policy_doc` emits a `NetworkPolicy`
for every service, for every target — local (`sun up`) and real cloud
(`sun deploy`) alike. BUG-012 fixed that policy to allow Prometheus
ingress from the `monitoring` namespace, and it was verified live against
the local k3d cluster.

That verification doesn't carry over to the AWS profile. `platform/infra/aws/main.tf`'s
`module "eks"` (`terraform-aws-modules/eks/aws`) sets no `cluster_addons`
block at all, so it gets the default `vpc-cni` addon with no
configuration. The default AWS VPC CNI does not enforce Kubernetes
`NetworkPolicy` resources unless network policy enforcement is
explicitly turned on (`ENABLE_NETWORK_POLICY` / the addon's
`enableNetworkPolicy` configuration value, available since VPC CNI
v1.14). Without it, every `NetworkPolicy` sun generates — including the
BUG-012 fix — is silently a no-op on a stock EKS cluster: pods are never
actually isolated, and Prometheus ingress "working" there proves nothing
about whether the policy is enforced at all.

k3d's default CNI (Flannel + kube-router here) does enforce
`NetworkPolicy`, which is why local verification didn't catch this — the
policy has always been non-functional on the one profile most likely to
run it in front of real traffic.

## Goal

An EKS cluster provisioned by `platform/infra/aws` enforces the
`NetworkPolicy` resources sun's manifest renderer generates, the same as
the local k3d cluster does.

## Remediation

In `platform/infra/aws/main.tf`'s `module "eks"` block, add a
`cluster_addons` block for `vpc-cni` that sets
`configuration_values = jsonencode({ enableNetworkPolicy = "true" })`
(pin `most_recent = true` for that addon so the network-policy-agent
ships). Confirm no other addon block was implicitly relying on old
defaults.

`NetworkPolicy` by default and cannot be disabled — GCP does not have
this gap, no follow-up needed there.
