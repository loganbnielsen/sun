sun status/logs/open (and sun up/deploy) are not deterministic from any directory

**Depends on:** None.

## Problem

`docs/architecture/observability-design.md` promises `sun status` "is
deterministic from any directory inside the workspace. The current working
directory is only used to find the workspace root." That's not true today:
`cmd_status.ml`, `cmd_logs.ml`, and `cmd_open.ml` all derive the workspace
name via `Filename.basename (Sys.getcwd ())` and scan a literal `app/`
relative to cwd (`Sun_cli_manifest.discover_services` does the same). Run
`sun status` from `app/payments/charge_svc` and the workspace becomes
`"charge_svc"` and no domains are found. The same assumption is baked into
`sun up`/`sun deploy` too — this isn't new to the observability commands,
but they're the ones that explicitly promised otherwise.

## Goal

Any `sun` command that discovers `app/`-relative state should first resolve
the real workspace root by walking up from cwd looking for a directory
containing an `app/` subdirectory, and operate from there — regardless of
which subdirectory the user invoked `sun` from.

## Acceptance criteria

- A single ancestor-walk helper (e.g. in `Sun_cli_workspace`) finds the
  nearest ancestor directory (including cwd itself) containing an `app/`
  subdirectory; returns `None` when no such ancestor exists (e.g. before
  `sun new`'s first scaffold), leaving today's behavior unchanged in that
  case.
- `main.ml` resolves the workspace root once at startup and `chdir`s there
  before dispatching to any subcommand, so every existing `Sys.getcwd ()`
  /relative-`"app"` call site downstream works correctly without being
  individually rewritten.
- `sun status`, `sun logs`, and `sun open` produce identical output whether
  invoked from the workspace root or from any subdirectory inside it
  (e.g. `app/payments/charge_svc`).
- Tests cover the ancestor-walk helper directly (finds root from a nested
  dir, returns `None` outside any workspace) without needing to invoke the
  `main` executable.
