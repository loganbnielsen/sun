**Depends on:** None.

## Problem

Local platform components (Loki, Grafana, Alloy, Tempo, Prometheus, etc.)
are not provisioned through `platform/infra/base`'s Terraform — `sun dev
up` (`cli/sun/bin/cmd_dev.ml`) is a separate, hand-written OCaml
implementation that shells out to `helm install` directly, with its own
independently-typed values for each chart. The file's own comments say
this is deliberate ("Dev mirrors prod exactly" — same charts/values as
`platform/infra/base/main.tf`, by convention, not by sharing code or
state) but there's no mechanism enforcing that mirror.

BUG-013 fixed exactly this kind of drift once already: `platform/infra/base/main.tf`'s
`helm_release "loki"` was missing `loki.commonConfig.replication_factor
= 1`, defaulting to the chart's RF=3, which fails outright against a
single `singleBinary` replica ("too many unhealthy instances in the
ring"). That fix was applied only to `platform/infra/base/main.tf`.
`cmd_dev.ml`'s own Loki `helm_install` call (~line 155) sets
`singleBinary.replicas: 1` but has no `commonConfig.replication_factor`
override at all — confirmed by grep, nothing sets it anywhere in
`cmd_dev.ml` or the shared `Sun_cli_helm` module. A fresh `sun dev up`
today provisions a Loki that should fail the same ring-quorum check
BUG-013 diagnosed.

This wasn't caught because BUG-013's live verification was done via a
manual `helm upgrade --set ...` against an already-running cluster, not
by tearing down and re-running `sun dev up` from scratch — so the fix
was verified against a *patched* live release, never against what
`cmd_dev.ml` actually generates on its own.

## Goal

A fresh `sun dev up` (torn-down cluster, clean run) produces a Loki that
accepts writes and serves queries immediately, matching what `platform/infra/base`
now produces for real clusters — and going forward, drift between these
two independently-maintained Helm-value sets is either eliminated or at
least easy to catch mechanically instead of by manual review.

## Remediation

At minimum: add `("loki.commonConfig.replication_factor", Float 1.)` (or
that config's `Sun_cli_helm` equivalent) to the Loki `helm_install` call
in `cmd_dev.ml`, and verify with a full `sun dev down --cluster && sun
dev up` cycle that Loki accepts a push immediately.

Worth considering as a follow-up (not required to close this ticket):
whether `cmd_dev.ml` and `platform/infra/base/main.tf` should share a
single source of Helm values per chart instead of two hand-maintained
copies, to prevent this exact class of bug recurring for the next chart
value that changes in one place and not the other.

## Acceptance criteria

- `cmd_dev.ml`'s Loki `helm_install` call sets `commonConfig.replication_factor`
  to `1`, matching `platform/infra/base/main.tf`.
- A `sun dev down --cluster` followed by a fresh `sun dev up` produces a
  Loki that accepts a push (`HTTP 204`) immediately after `/ready`
  reports true, with no "unhealthy instances in the ring" error.
