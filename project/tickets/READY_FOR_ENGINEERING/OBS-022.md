sun status <domain>/<service> should verify the service is declared before reporting health

**Depends on:** None.

## Problem

`cmd_status.ml`'s service scope validates the domain, normalizes the
service string to a k8s name, and queries Kubernetes directly — it never
checks whether that service is actually declared under that domain in
`app/`. If the namespace exists but the service name is bogus (typo, wrong
domain, never scaffolded) or has no matching pods,
`Sun_cli_rollout_diagnosis.format_service_diagnosis` returns `None` for an
empty pod list (vacuously "no unhealthy pods"), which `rollup_domain_status`
then reports as `healthy` — actively misleading for a service that doesn't
exist.

## Goal

`sun status <domain>/<service>` only reports a health status for services
that are actually declared in that domain; anything else is a clear error,
matching how an unknown domain is already handled.

## Acceptance criteria

- Before running diagnosis, `sun status <domain>/<service>` checks that
  `service` (by its k8s name) matches one of `Sun_cli_manifest
  .discover_services`'s services for that domain.
- If it doesn't match, print a clear error (e.g. "Service '<service>' not
  found in domain '<domain>'.") and exit 1 — the same failure shape as
  today's unknown-domain error — rather than proceeding to report a
  possibly-misleading health status.
- `sun open`/`sun logs` are unaffected (they intentionally don't require
  the target to already be running); this check is specific to `sun
  status`'s health-reporting contract.
- Tests cover: a declared service still reports its real health as before;
  an undeclared service name under a real domain errors instead of
  reporting "healthy".
