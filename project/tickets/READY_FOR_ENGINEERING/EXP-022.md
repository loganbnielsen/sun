`sun new svc/worker/fn` generates observability-dark entrypoints with no Loki, Prometheus, or Kafka security wiring

**Description:** `sun new svc`, `sun new worker`, and `sun new fn` each generate a minimal `bin/main.ml` with no observability wiring: no `LOKI_URL` check, no `Obs_loki` backend, no `Obs_prometheus`, no `Kafka_service.config_of_env()`, and no `~ot` argument passed to the framework. The workspace scaffold (`sun new workspace`) wires all of these correctly in `ws_svc_bin_ml`, `ws_worker_bin_ml`, and the framework fn template, but the generic primitives added via `sun new` do not. TUTORIAL.md Part 7 says these commands generate code that "integrates with the existing observability and deployment stack" — this claim is false for the generated entrypoints in `svc_bin_ml`, `worker_bin_ml`, and `fn_bin_ml` in `sun_cli_cmd_new.ml`.

**Impact:** A startup engineer who follows the tutorial to add a second service or worker will deploy a service that produces no Loki logs and no `sun_worker_messages_total` / `sun_svc_requests_total` metrics. The engineer will see nothing in Grafana for the new service, contradicting the promise that observability is "wired automatically." They need to manually copy the observability wiring pattern from the workspace svc, which requires prior knowledge of the pattern.

**Remediation:** (1) Update the generic templates `svc_bin_ml`, `worker_bin_ml`, and `fn_bin_ml` in `cli/sun/lib/sun_cli_cmd_new.ml` to include the same observability wiring pattern as `ws_svc_bin_ml` / `ws_worker_bin_ml`. Use `{{name}}`, `{{domain}}`, `{{lib}}` substitution variables to set the service label. For the worker template, also add `Kafka_service.config_of_env()` and `~ot`. For the fn template, add `~pushgateway_url:(Sys.getenv_opt "PUSHGATEWAY_URL")`. Update the corresponding dune templates to include `obs_eio obs_eio_loki obs_eio_prometheus` in libraries. (2) Update TUTORIAL.md Part 7's descriptions of `sun new svc/worker/fn` to note what wiring is needed until (1) is implemented.
