Local Loki deployment sets `replication_factor: 3` with only one replica running — reads fail with "too many unhealthy instances in the ring".

**Depends on:** None.

## Problem

`platform/infra/base/main.tf`'s `helm_release.loki` leaves the chart's default `loki.commonConfig.replication_factor: 3` in place while the actual topology (both `sun dev up`'s local k3d cluster and, per `docs/architecture/observability-design.md`, single-replica production) runs exactly one Loki pod (`loki-0`, a single-member StatefulSet). Loki's ring requires `replication_factor` distinct healthy instances to be found for reads/writes; with one real pod and RF=3, the ring can never reach quorum.

Confirmed live on a running local cluster:

```
$ curl http://localhost:3100/loki/api/v1/labels
too many unhealthy instances in the ring
```

Restarting the pod (`kubectl delete pod loki-0`) does not fix it — it recovers only long enough to serve a handful of queries before returning to the same error, since the underlying replica count never changes.

`loki-0`'s own logs on startup show the memberlist ring failing to reach even its own single node in time (`loki-memberlist.monitoring.svc.cluster.local` DNS not yet resolvable, `required_nodes=1` not met), then treating that as a genuinely unhealthy ring rather than a normal single-instance ring — consistent with RF=3 configured against a 1-pod deployment.

This directly breaks the tutorial's "Observe logs" walkthrough (`docs/guides/TUTORIAL.md` Part 6): `{service=~"pluto-.*"} | logfmt` in Grafana Explore → Loki returns no results, and any handler's `Obs_eio.log_standalone`/span-attached log call fails with `Loki returned HTTP 500: at least 2 live replicas required, could only find 1` (observed directly from a live `-svc` pod's stderr).

## Goal

A single-replica local/dev Loki deployment has a ring configuration that actually works with one pod, so log ingestion and queries succeed reliably without manual pod restarts.

## Remediation

1. In `platform/infra/base/main.tf`'s `helm_release.loki` values, set `loki.commonConfig.replication_factor: 1` (matching the actual single-replica topology) rather than leaving the chart's multi-replica default in place.
2. Confirm the same applies wherever this module is applied against a genuinely single-replica Loki (local k3d dev). If a production profile ever runs multiple Loki replicas, gate the value on replica count rather than hardcoding — check `docs/architecture/observability-design.md` for whether multi-replica Loki is in scope anywhere today (per this investigation, it is not).
3. Validate: fresh `sun dev up`, then `curl http://localhost:3100/loki/api/v1/labels` and a `-svc` request that calls `Obs_eio.with_span`/`log_standalone` both succeed without a pod restart, immediately after the stack comes up and again after leaving the cluster idle for a while (the ring issue appeared after the cluster had been running for several hours).

## Acceptance criteria

- A freshly provisioned local cluster's Loki answers `/loki/api/v1/labels` and query requests without "too many unhealthy instances in the ring".
- A `-svc`/`-worker` log/span call that pushes to Loki succeeds (no `at least 2 live replicas required` error) under normal operation, including after the cluster has been idle for hours.
- `terraform validate`/`terraform fmt -check` pass.
