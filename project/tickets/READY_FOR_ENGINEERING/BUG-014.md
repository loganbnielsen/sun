Every Kafka consumer in this repo (any `-worker`, plus `sun-fn`'s consumer paths) silently left its consumer group every `max.poll.interval.ms` regardless of actual message throughput — root-caused and fixed upstream in `kafka-eio`; this ticket threads the resulting API change through `sun`.

**Depends on:** None.

## Problem

`kafka-eio`'s consumer read messages via a raw `rd_kafka_consume_queue`
call on the consumer queue, bypassing the consumer-group housekeeping
`rd_kafka_consumer_poll` performs (heartbeats, rebalance callbacks, and
critically resetting the `max.poll.interval.ms` watchdog). Compounding
that, librdkafka's routine heartbeat traffic is handled entirely inside
its own background thread and never lands on the app-visible consumer
queue, so the event-driven fd wakeup this consumer relied on never fired
at all during genuine idle periods — no poll call of *any* kind happened,
regardless of which function it would have used.

Confirmed live against the real multi-service demo deployed to a k3d
cluster: `notify-worker` left its consumer group on an exact ~304-305s
cadence (just over librdkafka's 300000ms default), forever, independent
of message volume or the unrelated Loki outage (BUG-013) investigated
alongside it in the same session. No data loss (the consumer always
caught up after rejoining), but constant unnecessary rebalancing.

Fixed upstream in [kafka-eio#22](https://github.com/loganbnielsen/kafka-eio/pull/22)
(merged): swapped to the existing `consumer_poll` binding (reads the same
queue, so the fd-wakeup fast path is unaffected, but now drives the
correct housekeeping) and added a periodic keepalive (an idle timeout
race on the wake-fd read, every 3s) so the poll loop runs on a fixed
cadence even with zero message/rebalance traffic. `Kafka.Consumer.create`
now takes a required `~clock` to drive that keepalive — a real, if small,
public API change, landing in a pre-1.0 unpublished package with no
external consumers besides this repo (see `~/Code/CLAUDE.md`'s pre-alpha
policy).

## Goal

`sun`'s own `Kafka_service.consume`/`consume_partitioned` (and every
generated `-worker` that goes through them) build against the new
`kafka-eio` API and no longer exhibit the rebalance churn.

## Remediation (done)

- Re-pinned `kafka-eio` to the merged `#main` commit.
- Threaded `~clock` through `Kafka_service.consume` (previously lacked
  it entirely) and its two internal `Kafka.Consumer.create` call sites,
  and `Kafka_service_retry_topics.consume`'s two call sites (already had
  `~clock` in scope from its own signature).
- Updated the two test call sites in
  `kafka-eio-service/test/test_kafka_service_integration.ml`.

## Acceptance criteria

- `dune build`/`dune test` (including the real-broker integration suite)
  pass against the re-pinned `kafka-eio`.
- A freshly-deployed `-worker` no longer emits `MAXPOLL`/"leaving group"
  log lines during idle periods — verified live by redeploying
  `notify-worker` in the real multi-service demo cluster and watching its
  logs for a clean interval well past 300s with no traffic.

## Related

- Separately noticed while verifying this fix: `sun up`'s Docker build
  caches the `opam pin add kafka-eio ...#main` layer by command text, so
  a fresh upstream commit on `#main` doesn't actually get pulled into a
  rebuild unless the cache is busted (`docker build --no-cache`, or some
  other cache-invalidating change). `sun up` has no flag for this. Worth
  its own small ticket if this becomes a recurring source of "why isn't
  my fix showing up" confusion — not fixed here.
