Replace the deprecated `loki-stack` chart with `loki` + `grafana` + `alloy` — promtail is already past EOL

**Depends on:** None.

## Problem

`platform/infra/base/main.tf`'s `helm_release.loki` resource uses Grafana
Labs' `loki-stack` chart (`repository = "https://grafana.github.io/
helm-charts"`, `chart = "loki-stack"`, `version = "2.10.2"`). Grafana Labs'
own chart README states: *"This chart is deprecated and will no longer
receive updates or support."*

**This is not a someday risk.** `loki-stack` defaults to Promtail as its log
shipper, and Sun explicitly turns it on (`promtail.enabled = true`,
load-bearing for `OBS-004`'s failure-visibility story — OOMKilled,
CrashLoopBackOff, and pre-log crashes that `obs-loki-eio`'s app-push
logging structurally cannot see). **Promtail itself reached end-of-life in
March 2026** (six months before this ticket) — no further updates, ever,
regardless of what happens to `loki-stack`.

## Decision (resolved 2026-09-04)

Migrate to the split, currently-maintained chart set Grafana Labs
recommends:

- **Loki**: the community-maintained `loki` chart
  (`grafana-community/helm-charts`) — Loki-only, no bundled Grafana.
- **Grafana**: becomes its own standalone `helm_release` using the
  `grafana/grafana` chart directly (previously a subchart of `loki-stack`).
  The sidecar ConfigMap dashboard/datasource auto-loading convention
  `OBS-011`/`OBS-036`/`OBS-038` all depend on
  (`grafana_dashboard=1`/`grafana_datasource=1` labels) is a feature of the
  **Grafana chart itself**, not `loki-stack` — it survives the migration
  unchanged in behavior, but its Terraform `set` blocks move from the
  nested `grafana.sidecar.dashboards.enabled` (today's `loki-stack`
  passthrough naming) to the standalone chart's top-level
  `sidecar.dashboards.enabled` / `sidecar.datasources.enabled`.
- **Log shipping**: **Grafana Alloy**, not a promtail-shaped replacement.
  Alloy is Grafana's unified OTel-based collector (logs, metrics, and
  traces in one binary) and is the officially documented promtail
  successor (`alloy convert --source-format=promtail` migrates existing
  config mechanically). Using Alloy here is deliberately scoped to *log
  shipping only* in this ticket — its metrics/traces capability is a
  future connection point for `OBS-041`'s tracing work, not something to
  build out now.

Sources: Grafana's `loki-stack` chart README (deprecation notice), the
`grafana-community/helm-charts` `loki` chart, and Grafana's official
Promtail-to-Alloy migration docs — cite these in the PR description if a
reviewer wants to verify the claims independently.

## Remediation

1. Replace `helm_release.loki`'s `chart = "loki-stack"` with the community
   `loki` chart. Preserve `loki.persistence.enabled` (→
   `local.loki_install_local`/`var.loki_persistent_storage`, same
   `local`-profile PVC toggle it is today) and the existing
   `self_hosted_durable` S3 object-storage wiring
   (`local.loki_object_storage_config`, applied today via `values =
   concat(..., var.observability_backend == "self_hosted_durable" ?
   [yamlencode(local.loki_object_storage_config)] : [])`) — confirm the new
   chart's values schema for object storage config and adjust the
   `yamlencode` shape if it differs from `loki-stack`'s.
2. Add a new standalone `helm_release.grafana` (chart `grafana/grafana`),
   gated the same way today's bundled Grafana is
   (`count = local.loki_install_local ? 1 : 0` equivalent — no local
   Grafana when shipping to an `external` backend, matching
   `kubernetes_ingress_v1.grafana`'s existing gate). Move
   `grafana.adminPassword` → `adminPassword`, and the sidecar `set` blocks
   to their new top-level names.
3. Add a new `helm_release.alloy` (or equivalent Alloy chart resource)
   replacing the `promtail.enabled`/`loki_promtail_clients`/
   `loki_promtail_taxonomy_relabel_configs` locals' worth of config — same
   cluster-wide pod stdout/stderr scraping via DaemonSet, same taxonomy
   label relabeling (`local.loki_promtail_taxonomy_relabel_configs`), same
   `external`-mode client target (`local.loki_promtail_clients`). Use
   `alloy convert --source-format=promtail` against the current effective
   promtail config as a starting point, not a from-scratch rewrite.
4. Update `docs/deployment/observability-backends.md` and any other doc
   referencing the old chart/resource names.
5. Validate with `terraform validate`/`terraform fmt -check` (network
   access permitting `terraform init`, per `OBS-036`'s precedent) and
   `helm show values` against the new charts to confirm every `set` block
   still targets a real value path.

## Migration path for existing `self_hosted_durable` installs

Given this repo's pre-alpha/no-backwards-compatibility policy (`~/Code/
CLAUDE.md`), treat this as a clean-cutover Terraform change, not a
data-preserving migration — there are no real production installs to
preserve today. If a real `self_hosted_durable` deployment exists by the
time this lands, note in the PR that a `terraform apply` will replace the
Loki/Grafana resources (new Helm releases, likely new resource addresses)
and confirm whether the S3 bucket contents themselves (Loki's chunk/index
data) survive the resource replacement — they should, since the bucket is
a separate `aws-eio`/Terraform-AWS resource with `prevent_destroy`, not
something the Helm release itself owns.

## Non-goal

Building out Alloy's metrics/traces collection capability — this ticket
scopes Alloy to log shipping only, matching what promtail did. `OBS-041`
covers tracing separately.
