Add a Tempo tracing backend: `obs-tempo-eio` package + platform deployment

**Depends on:** None.

## Problem

`docs/architecture/observability-design.md`'s Identity section names
"trace" as a signal type that must carry the shared ownership labels — but
there is no tracing backend and no trace dashboard. What exists today is
narrower: `~/Code/obs-eio`'s `Obs_trace` module provides W3C `traceparent`
context propagation (generate/parse/inject/extract), and `obs-loki-eio`'s
`Obs_loki` backend embeds `trace_id`/`span_id` as logfmt fields in pushed
log lines. That gives cross-service log *correlation* by trace_id, not a
trace *visualization* (span waterfall, latency breakdown across service
hops).

## Decision (resolved 2026-09-04)

Build a real Tempo backend, following the exact extraction pattern
`obs-loki-eio`/`obs-prometheus-eio` already established — a new standalone
package, not code living inside `sun`'s own tree, and not Sun-specific in
any way:

- **`obs-tempo-eio`** implements `Obs_eio.backend`'s `emit_span` field
  (`~/Code/obs-eio/lib/obs_eio.mli:110`) by exporting `span_event`s
  (`trace_ctx : Obs_trace.t`, `name`, `service`, `start_ns`/`end_ns`,
  `status`, `log_entries`, `context` — see `obs_eio.mli:56-71`; entirely
  generic, no Sun-specific fields) to Tempo over OTLP, Tempo's native
  ingestion protocol. This is the same shape of work as `obs-loki-eio`'s
  `emit_span` doing one HTTP POST per span-close to Loki's push API — the
  backend interface, the "every field called synchronously inline on the
  calling fiber, no queue" contract (`obs_eio.mli:122-129`), and the
  "backend owns whether to block or hand off to a queue itself"
  responsibility for network calls all carry over unchanged.
- Package location: `~/Code/obs-tempo-eio`, own git repo, findlib name
  `obs-tempo-eio`, opam-pinned into this switch — mirror
  `obs-loki-eio`/`obs-prometheus-eio`'s repo layout, `.mli`-first design,
  and spec-doc convention exactly (see their `README.md`s as the template).

Sun-specific work is smaller and separate from the package itself:

1. **`sun-svc`/`sun-worker`/`sun-fn`**: wire in `obs-tempo-eio` as an
   additional backend alongside the existing Loki/Prometheus ones — same
   shape of config/plumbing decision those frameworks already make for
   backend selection (`framework/sun-svc/lib/`, `framework/sun-worker/lib/`,
   `framework/sun-fn/lib/` — check how they currently construct
   `Obs_eio.create ~backend:...` and thread a second/third backend in,
   likely via `Obs_eio`'s support for multiple backends if it exists, or a
   small fan-out wrapper if it doesn't — check `obs_eio.mli` for this
   before inventing a wrapper).
2. **`platform/infra/base`**: deploy Tempo itself (a new `helm_release`,
   likely `grafana/tempo` chart) and wire a Grafana Tempo datasource via
   the same sidecar ConfigMap-loading convention `OBS-011` already
   established for the Prometheus datasource
   (`kubernetes_config_map.grafana_prometheus_datasource` in
   `platform/infra/base/main.tf` is the template to mirror).
3. **A minimal trace-lookup dashboard/link** — at minimum, a way to jump
   from a `trace_id` seen in a Loki log line to that trace's waterfall in
   Tempo (Grafana's built-in Loki-derived-fields-to-Tempo-link feature is
   the natural fit — the Loki datasource config gains a `derivedFields`
   entry matching the existing `trace_id=` logfmt pattern
   `obs-loki-eio` already emits).

## Non-goal (this ticket)

- A dedicated trace-analysis dashboard beyond the minimal lookup link
  above — start with "can jump from a log line to its trace," not a full
  APM-style trace search UI.
- Retrofitting every existing span-producing call site to guarantee
  100% capture — sampling policy and coverage completeness are follow-up
  concerns once the backend exists and is dogfooded.
- Alloy's tracing/OTel-collector capability (`OBS-039` scopes Alloy to log
  shipping only) — a future ticket can revisit whether spans should route
  through Alloy as a collector in front of Tempo, rather than
  `obs-tempo-eio` pushing directly; don't build that indirection
  speculatively now.

## Acceptance criteria

- `obs-tempo-eio` exists as a standalone, opam-pinned package with its own
  README/spec doc, implementing `Obs_eio.backend`.
- At least one Sun framework primitive (`-svc` is the natural first choice,
  matching how `-worker`'s metrics work landed service-by-service in
  `OBS-035`) emits real spans to a running Tempo instance in local dev.
- Tempo is deployed by `platform/infra/base` with a working Grafana
  datasource, validated the same way `OBS-036`/`OBS-039` validate new
  chart/datasource wiring (`terraform validate`, `helm show values`).
- A `trace_id` visible in a Loki log line can be clicked through to its
  trace in Tempo from Grafana.
