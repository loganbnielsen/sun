Every service's auto-generated NetworkPolicy blocks Prometheus from ever scraping it — the "dashboards work out of the box" story is broken for every freshly deployed service.

**Depends on:** None.

## Problem

`network_policy_doc` in `cli/sun/lib/sun_cli_manifest_yaml.ml` generates an
`ingress` rule allowing traffic only from `ingress-nginx` and same-namespace
pods. `egress` already explicitly allows the `monitoring` namespace (so the
service can push logs/traces out), but nothing in `ingress` allows
`monitoring` in — so Prometheus, which lives in `monitoring` and needs to
scrape *into* each service pod, is silently blocked.

Confirmed live against a real `sun dev up` k3d cluster: `wget` from
Prometheus's own pod directly to a freshly-deployed `charge-svc` pod's IP
got `connection refused` on the exact port kubelet's own readiness probe
and a `kubectl port-forward` could both reach fine — the NetworkPolicy,
not the app, was the blocker. Prometheus's own target list confirmed
`up=0` with `lastError: connection refused` for every freshly-deployed
service in the cluster.

This is a real, load-bearing bug: `platform/infra/base/dashboards/
service-template.json`'s whole "zero-config" story (Grafana template
variables backed by live Prometheus label values, see
`cli/sun/lib/sun_cli_manifest_yaml.ml`'s design) depends on Prometheus
actually being able to reach every service — with this bug, metrics
panels (and any dashboard variable keyed off metric labels) stay empty
for every service, forever, with no error visible anywhere except deep in
Prometheus's own target-status page.

## Goal

Prometheus can scrape every scaffolded service's `/metrics` endpoint
without weakening the NetworkPolicy's other restrictions (still only
`ingress-nginx` + same-namespace + now `monitoring` — never open to the
whole cluster).

## Remediation (done)

Added a `monitoring` namespace `namespaceSelector` to `network_policy_doc`'s
`ingress.from` list, matching the pattern the `egress` block already uses.

Added `test_svc_networkpolicy_allows_monitoring_ingress` (regression test
in `cli/sun/test/test_manifest_render.ml` — the NetworkPolicy block had
**zero** test coverage before this).

## Acceptance criteria

- A freshly-deployed service's NetworkPolicy ingress rule includes the
  `monitoring` namespace.
- Prometheus's own `/api/v1/targets` reports `up=1` (not `up=0`,
  `connection refused`) for a freshly-deployed service, verified live.
