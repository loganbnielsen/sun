Local Loki container (`grafana/loki:3.0.0`, `ensure-loki.sh`) rejects every write with "at least 2 live replicas required, could only find 1" even though `common.replication_factor: 1` is set.

**Depends on:** None.

## Problem

This is the same failure mode BUG-006 described (that ticket was lost — deleted
by a batch ticket-state operation on 2026-09-05 without being fixed or moved to
DONE; see `project/tickets/DONE/` has no trace of it). BUG-006 diagnosed it
against `platform/infra/base/main.tf`'s Terraform Helm release; this instance is
the separate plain-Docker Loki container `ensure-loki.sh` starts for local
dev/tests/demo (`docker run grafana/loki:3.0.0 -config.file=/etc/loki/local-config.yaml`),
which never goes through that Terraform module at all — a different code path
with the same symptom.

Confirmed live:

```
$ curl -X POST http://localhost:3100/loki/api/v1/push -d '{"streams":[...]}
at least 2 live replicas required, could only find 1
HTTP 500
```

Investigation so far: the bundled `local-config.yaml` sets `common.replication_factor: 1`,
but `GET /config` shows `common.ring.replication_factor` (a *separate* field —
the generic ring struct embedded under `common:`, not the same as the
`common.replication_factor` convenience shortcut) defaults to 3 and is not
overridden by the shortcut. Mounting a corrected config with
`common.ring.replication_factor: 1` explicitly set (verified via `GET /config`
that the value actually changed to 1) did **not** fix the write failure —
the same "at least 2 live replicas" error persists with every relevant
`replication_factor` in the full `/config` dump reading 1 (only the unrelated
`query_scheduler.scheduler_ring` at 2, and the unused `storage_config.cassandra`
default at 3, remain non-1). This means the actual quorum check that's failing
is not reading any of the config fields inspected so far — something else
(possibly hardcoded, possibly a ring the write path consults that isn't
reachable via `/config`, possibly a real upstream Loki 3.0.0 bug) is still
enforcing effective RF=2+ on the write path.

## Goal

A fresh `ensure-loki.sh` container accepts pushes and serves queries
immediately (no manual pod/container restart, no flaky first-N-requests
window) so demo/tutorial/e2e runs that depend on `LOKI_URL` are reliable.

## Remediation

1. Reproduce directly against a stock `docker run grafana/loki:3.0.0` with
   *only* the bundled `local-config.yaml` (no local override) and confirm
   whether this is a genuine upstream regression in this exact image tag —
   check the Loki 3.0.0 changelog/issues for "at least 2 live replicas".
2. If it's a real upstream bug: try a newer/older `grafana/loki` tag known to
   work correctly in single-binary mode with `replication_factor: 1`, or find
   the actual field/flag it responds to (start by instrumenting/tracing which
   ring `pkg/distributor` consults for the write-path quorum check in this
   version — it is evidently not `common.ring` nor `ingester.lifecycler.ring`,
   both already confirmed at RF=1 via `/config` with no effect).
3. `platform/local/config/loki-config.yaml` + `ensure-loki.sh`'s mount already
   exist from this investigation (sets `common.ring.replication_factor: 1`)
   — keep, extend, or replace them once the real fix is found; they are not
   sufficient alone.
4. Validate: fresh container, immediate `curl -X POST .../loki/api/v1/push`
   succeeds (HTTP 204) with no retry/wait needed, and `examples/local-demo`'s
   Loki assertion passes end-to-end.

## Acceptance criteria

- A freshly started `ensure-loki.sh` container accepts a push immediately
  after `/ready` reports true, with no "live replicas" error.
- `examples/local-demo`'s "Loki: logs received" assertion passes reliably.
- `dune test` (or `run_tests.sh`'s e2e suite) passes its Loki assertion
  without a flake/retry loop worked around at the test level.
