`ensure-loki.sh`/`ensure-tempo.sh`/`ensure-grafana.sh` silently get shadowed by a `kubectl port-forward` to the real `sun dev up` k3d cluster on the same port, producing confusing errors (a fake "at least 2 live replicas required" for Loki; a real login screen with unknown credentials for Grafana) that look like real bugs but aren't.

**Depends on:** None.

## Root cause (found)

Not a Loki bug, not a config issue, not a version/networking/timing issue —
every one of those was tried and ruled out in the original investigation
below before the real cause was found. The actual cause: this session had
a long-running `kubectl port-forward -n monitoring svc/loki 3100:3100`
(started earlier for unrelated `sun dev up` observability work) bound to
`127.0.0.1:3100`, while `ensure-loki.sh`'s Docker container publishes
`0.0.0.0:3100`. On Linux, a listener on a specific address
(`127.0.0.1:PORT`) takes precedence over one on the wildcard address
(`0.0.0.0:PORT`) for connections to `localhost`/`127.0.0.1` — so every
`curl localhost:3100` and every `LOKI_URL=http://localhost:3100` test run
was silently talking to the **real k3d cluster's Loki** the whole time,
never the lightweight test/demo container `ensure-loki.sh` starts. The
same pattern hit Tempo's query port too
(`kubectl port-forward -n monitoring svc/tempo 3200:3200` vs. `ensure-
tempo.sh`'s `0.0.0.0:3200`) — see BUG-009, same root cause, separate
ticket only because it was diagnosed as a separate symptom before the two
were connected.

Confirmed by instrumenting `vendor/github.com/grafana/dskit/ring/
replication_strategy.go`'s `Filter` function in a locally-built
`grafana/loki:3.0.0` binary (cloned `github.com/grafana/loki` at tag
`v3.0.0`, added `fmt.Printf` tracing, rebuilt with
`golang:1.21.9`/`-mod=vendor`, ran it in place of the stock binary): when
reached on a port with no competing listener, `Filter` printed exactly the
expected `inputRF=1 len(instances)=1 minSuccess=1`, all healthy, and the
push succeeded (`HTTP 204`) immediately. Reproducing on port 3100 with the
`kubectl port-forward` still active produced the `HTTP 500` error with
**zero** `Filter` log lines — proving the request never reached the Docker
container's Loki process at all. Killing the two colliding port-forwards
(`kubectl port-forward ... svc/loki 3100:3100`,
`kubectl port-forward ... svc/tempo 3200:3200`) and restarting the Docker
containers made both push and query succeed reliably (5/5 pushes, full
`examples/local-demo` run with all 7 assertions passing, including the two
Tempo ones — see FEAT-030/BUG-009).

The same pattern hit a third port during a live walkthrough:
`kubectl port-forward -n monitoring svc/grafana 3000:80` shadowed
`ensure-grafana.sh`'s container identically — every login/anonymous-auth
attempt against `localhost:3000` was hitting the real k3d cluster's
Grafana (which has its own real auth requirements), not the local
container. Recreating the container with different auth configs (and even
trying a different Grafana version, `13.2.1` vs `11.3.0`, after the
newer build's `latest` tag showed an unrelated `auth.anonymous.org_role`
deprecation warning that turned out to be a red herring) never mattered —
killing the port-forward and restarting the container fixed it
immediately. `ensure-grafana.sh` should get the same preflight check.

The original BUG-006 diagnosis (a genuine `replication_factor` gap in
`platform/infra/base/main.tf`'s Helm release, defaulting to the chart's
RF=3) may still be a real, separate issue in the actual k3d-deployed Loki
— it was never actually verified fixed, and this investigation didn't
touch the Terraform module. That's still open; see Remediation.

## Goal

`ensure-loki.sh`/`ensure-tempo.sh`/`ensure-grafana.sh` (and any other `ensure-*.sh` script
that binds a well-known local port) should not silently produce a
misleading downstream error when something else already occupies that
port — a developer running `sun dev up` (which port-forwards the same
conventional ports) alongside local tests/demo will hit this exact trap
with no signal pointing at the real cause.

## Remediation

1. Add a preflight check to `ensure-loki.sh`/`ensure-tempo.sh`/`ensure-grafana.sh` (and ideally
   a shared helper other `ensure-*.sh` scripts can reuse): before starting
   the container, check whether the target port already has a listener
   that isn't the container's own health check succeeding for the right
   service (e.g. via `curl`'s response shape/version, or simply detecting
   a `kubectl port-forward` process bound to that port via `/proc/<pid>/
   cmdline` on Linux) — warn loudly and name the conflicting process
   rather than silently starting a container that will never be reached.
2. Separately (not verified by this investigation): check whether
   `platform/infra/base/main.tf`'s `helm_release "loki"` still lacks an
   explicit `loki.commonConfig.replication_factor` override for the
   non-`self_hosted_durable` (single-replica) path — BUG-006's original
   remediation. If the k3d cluster's real Loki has never actually had this
   fixed, a developer relying on `sun dev up`'s Loki directly (not through
   `ensure-loki.sh`) would still hit a real RF=3-on-1-replica issue.

3. `ensure-grafana.sh` pins no version at all (`grafana/grafana:latest`),
   unlike `ensure-loki.sh`/`ensure-tempo.sh`. Pin it to a known-good
   release (e.g. `11.3.0`, verified working with the anonymous-admin
   config this session used to unblock a live walkthrough) — a floating
   tag on infrastructure other scripts assume is stable is the same class
   of fragility as the port-shadowing issue above, just triggered by time
   instead of environment state.

## Acceptance criteria

- Starting `ensure-loki.sh` (or `ensure-tempo.sh`) while a conflicting
  `kubectl port-forward` already holds the same port prints a clear
  warning naming the conflict, instead of silently starting a container
  nothing will ever reach.
- `platform/infra/base/main.tf`'s Loki Helm release is confirmed to set
  (or already sets) `replication_factor: 1` for the single-replica path.
- `ensure-grafana.sh` pins a specific Grafana version instead of `latest`.
