Let `sun.yml` scale override `sun.toml` replicas when both exist, by service name; `sun.toml` stays the default.

**Depends on:** FEAT-025.

## Problem

Replica scale is declared in two places with nothing reconciling them:

- `Sun_cli_toml.t.replicas` (`cli/sun/lib/sun_cli_toml.mli:34`, type `t`
  — not `service_config`, corrected from an earlier draft of this ticket
  — `[infra.scale] replicas`) — **the live one**: manifest generation
  reads it directly (`sun_cli_deployment_plan.ml:303`,
  `sun_cli_manifest_yaml.ml:562`).
- `Sun_cli_config.service.scale_min`/`scale_max` (`sun_cli_config.ml:27-28`,
  `sun.yml`'s `services.<name>.scale.min/max`) — parsed and merged, but
  the only reader is `cmd_plan.ml:45`'s printout.

An earlier draft of this ticket proposed making `sun.yml` the sole source
of truth and removing `sun.toml`'s field, matching
`docs/planning/LIVE_DEV_DEPLOY_ROADMAP.md` line 114's listing of "service
scale" as a target-file-owned field. That's not actually implementable as
a straight swap, for two concrete reasons checked against the code:

1. **`sun new workspace` does not scaffold a `sun.yml` at all** — grepped
   `sun_cli_scaffold_templates.ml`/`sun_cli_cmd_new.ml`, no hit. Only
   `examples/pluto` has a hand-written one. Removing `sun.toml`'s field
   would leave every freshly scaffolded workspace with no way to set
   replica count.
2. **`sun up` has no target and never calls `load_for_target`**
   (`cmd_up.ml`, confirmed no `Sun_cli_config` usage) — it's local-only by
   design (see `FEAT-026`'s non-goal). There's no `sun.yml` overlay to read
   from on that path even when one exists.

## Goal

`sun.yml` scale (when present, matched by service name, and only reachable
because a target resolved — i.e. `sun deploy`/`sun cloud` paths) overrides
`sun.toml`'s `replicas` as a per-service default. `sun.toml`'s field is
**not removed** — it stays the base default everywhere, including `sun
up`, where no target-resolved `sun.yml` is ever in play. This is
deliberately a "layered override," not a migration: the "sun.yml wins"
framing from the earlier draft assumed sun.yml was universally available,
which it isn't yet.

The lookup this needs is narrow — "does a resolved `Sun_cli_config` have a
`service` entry whose `name` matches this discovered service, and does it
set `scale_max`/`scale_min`?" — a name-equality check, not the broader
`sun.yml`-vs-filesystem-discovery service-identity reconciliation
`FEAT-026` explicitly declines to do. No match, or no resolved config at
all (e.g. `sun up`): fall back to `sun.toml`'s `replicas` unchanged.

No `HorizontalPodAutoscaler` is emitted anywhere today, so `scale_min`/
`scale_max` (a range) and `replicas` (a fixed count) still aren't the same
shape — this ticket does not add HPA support. When `sun.yml` scale
overrides, use `scale_max` (falling back to `scale_min`) as the interim
fixed count.

## Remediation

1. Where `sun_cli_deployment_plan.ml:303`/`sun_cli_manifest_yaml.ml:562`
   currently read `Sun_cli_toml.t.replicas` directly, thread through an
   optional resolved `Sun_cli_config.t` (present on the `sun
   deploy`/`FEAT-026` path, absent on `sun up`) and look up a
   name-matching service's scale first; fall back to `Sun_cli_toml`'s
   `replicas` when there's no resolved config, no matching service, or no
   scale set on it.
2. Do **not** remove `Sun_cli_toml.t.replicas` or its `[infra.scale]`
   parsing — it remains load-bearing for `sun up` and every workspace
   without a `sun.yml`.
3. Blast radius of documenting `[infra.scale]` as still-live (an earlier
   draft's "remove the field" framing would have needed these; this
   ticket's "keep it as the base default" framing does not require editing
   them, but check each is still accurate): `docs/planning/ROADMAP.md`'s
   `sun.toml` fields table, `docs/deployment/escape-hatches.md` (the
   full config table, ~lines 56–63, 215, 235, 255), `README.md:429`,
   `docs/audits/STYLE_AUDIT.md:38`, and
   `sun_cli_scaffold_templates.ml` (~lines 78–79, 99 — emits `[infra.scale]`
   into every scaffolded `sun.toml`). None of these need edits under this
   ticket's layered design — confirm that during implementation rather
   than assuming; if any turn out to claim `sun.toml` is the *only* way to
   set scale, add a line noting `sun.yml` can override it.
4. Tests: a service with `sun.yml` scale set and a resolved target gets
   the `sun.yml` value; the same service via `sun up` (no resolved config)
   gets `sun.toml`'s value; a service with no `sun.yml` entry at all (the
   common case — most workspaces have no `sun.yml`) gets `sun.toml`'s
   value on every path.

## Acceptance criteria

- `sun.toml`'s `[infra.scale] replicas` continues to work unchanged for
  every workspace that has no `sun.yml`, and for every `sun up` deploy
  regardless of `sun.yml`.
- A workspace with both a `sun.yml` service scale entry and a
  `sun.toml` `replicas` value, deployed via a resolved target, uses the
  `sun.yml` value.
- `dune build`/`dune test` pass.
