`obs-tempo-eio`/`https-eio` silently drop spans when two `Obs_eio.t` handles push to the same Tempo endpoint concurrently — only 1 of 6 concurrent spans landed, with zero client-side errors.

**Depends on:** None.

## Problem

`examples/local-demo` was updated (CODE_LAYER-003 dogfooding) so both
`order-svc` and `fulfillment-worker` get tracing through their own
`Sun_obs.t` (each built by a separate `Sun_obs.of_env` call, so each holds
its own `Obs_tempo.create` backend instance pointed at the same
`TEMPO_URL`). Previously only `order-svc` pushed to Tempo, serially, and
that path was reliable. With both services pushing concurrently (svc
handling new orders while the worker fulfills previous ones, both under
independent Eio fibers), a 3-order demo run that should produce 6
`with_span` calls (3 `receive_order` + 3 `fulfill_order`, the latter as
child spans of the former via W3C trace-context propagation over Kafka)
resulted in Tempo's own `tempo_distributor_spans_received_total` /
`tempo_ingester_traces_created_total` metrics reading **1**, reproduced
across two independent fresh-container runs.

Critically: `Obs_eio.compose`'s `compose_call` catches and reports each
backend's exception independently (see `obs_eio.ml`'s `compose`/
`report_backend_error`), and no `Obs_eio: backend_error op=emit_span`
lines referencing Tempo/`Https_eio` were printed for any of the 6 calls —
every `Obs_tempo.create`'s `emit_span` call returned `Ok` (no exception)
from the client's perspective. So the drop is not a client-visible error
being swallowed; either the HTTP requests never actually reached Tempo's
distributor intact, or Tempo silently accepted and then dropped them
(e.g. a live-store/ring race under concurrent single-tenant writes).

Not yet isolated to `https-eio`'s HTTP/1.1 client (e.g. a connection-reuse
bug corrupting interleaved concurrent writes on a shared connection) vs.
`obs-tempo-eio`'s request construction vs. Tempo server-side behavior under
this specific concurrency pattern.

## Goal

Two (or more) independent `Obs_eio.t`/`Sun_obs.t` handles pushing spans to
the same Tempo endpoint concurrently should reliably land every span —
this is the normal production shape (every `-svc`/`-worker`/`-fn` process
gets its own `Sun_obs.t`, and multiple processes/replicas push to the same
shared Tempo endpoint simultaneously in any real deployment).

## Remediation

1. Write a focused repro in `obs-tempo-eio`'s test suite: N concurrent
   `Eio.Fiber.fork`s, each holding its own `Obs_tempo.create` backend (or
   its own `Obs_eio.t`), each emitting one span at the same instant against
   a single mock/real Tempo instance — confirm all N are received.
2. If `https-eio`'s client has connection-pooling/reuse, verify it is safe
   under concurrent use from multiple fibers/domains (a fresh connection
   per request, or a properly synchronized pool) — compare against the
   "TLS RNG seeding" and FFI-domain-lock precedents already documented for
   this codebase's other concurrency-sensitive client code.
3. If the client side is clean, escalate to a Tempo-side investigation
   (version-specific live-store/ingester behavior under concurrent
   single-tenant pushes).
4. Validate: `examples/local-demo`'s Tempo assertion (currently the
   `svc`-only historical version, now covering both services) passes
   reliably across repeated runs, not just once.

## Acceptance criteria

- A repro test in `obs-tempo-eio` demonstrates N-for-N concurrent spans
  landing in Tempo.
- `examples/local-demo`'s Tempo trace-lookup assertion passes reliably
  (multiple consecutive runs, not a one-off).
