Implement production JWT verification with a maintained JOSE library (not hand-rolled HMAC)

**Depends on:** None.

## Summary

`framework/sun-svc/lib/auth.ml` (`validate_jwt`, lines 173–180) fails closed today:
`Verified_signature_required` returns `` `Not_implemented `` and only
`Unverified_dev_only` actually validates a token, decoding the payload and checking
`exp`/scopes without ever checking the signature. This is safe (no route can silently
accept a forged token) but means Sun services cannot use JWT auth in production at all.

This is a second attempt. AUDIT-056 (`project/tickets/DONE/AUDIT-056.md`) implemented
HS256 verification by hand — base64url-decoding the JWT, computing an HMAC-SHA256 over
the signing input with `digestif`, and comparing it constant-time against the provided
signature, with the secret coming from config or `SUN_JWT_SECRET`. It merged
(`e3bbfff`) and was reverted in the same session (`b4a9a5f`, 2026-06-15) with no
recorded reason in the commit message. Confirmed with the person who made that call:
the revert was deliberate — hand-implementing signature comparison directly against a
crypto primitive is the wrong shape for this, and HS256-only (a single shared secret)
doesn't fit a real identity provider (Auth0, Cognito, Okta, etc.), which issue RS256/ES256
tokens verified against a rotating JWKS, not a static shared secret.

## Remediation

1. Use a maintained JOSE/JWT OCaml library for the actual verification — `jose` (already
   confirmed available in this switch's opam repo, mirage-crypto-backed, matching the
   rest of this codebase's crypto stack) is the leading candidate. Do not reimplement
   signature comparison against `digestif` or any other raw primitive directly in
   `auth.ml` — that's the shape that got reverted last time.
2. Support RS256/ES256 (asymmetric, JWKS-based) verification, not just HS256. A real
   config needs: issuer, audience, algorithm allowlist, and either a static JWKS
   document/key or a JWKS URL to fetch and cache (with rotation — don't cache forever,
   don't refetch every request).
3. Decide and document whether HS256 (shared-secret) support is kept at all alongside
   JWKS — plenty of real deployments are HS256-only — but if so it must go through the
   chosen library's verification path, not a hand-rolled comparison.
4. Keep `Unverified_dev_only` as the explicit, clearly-named local-dev-only escape
   hatch it already is; don't let `Verified_signature_required` silently fall back to it.
5. Tests: valid signed tokens (both HS256 and RS256 if both are supported), invalid/
   tampered signatures, wrong issuer/audience, expired tokens, missing scopes, and a
   JWKS-fetch-failure case (should fail closed, not fall back to unverified).

## Acceptance criteria

- `Auth.validate` can verify signed JWTs end-to-end with `Verified_signature_required`,
  without falling back to `Unverified_dev_only` behavior.
- Verification is delegated to a maintained library — no hand-rolled HMAC/signature
  comparison in `auth.ml`.
- Invalid signatures are rejected even when payload claims look valid.
- Existing `Public`/`Api_key`/`Unverified_dev_only` auth tests continue to pass.
- `framework/sun-svc/sun-svc.md` is updated to describe the verified-JWT configuration
  (issuer/audience/algorithm/JWKS), not just the `Unverified_dev_only` v1 path.
