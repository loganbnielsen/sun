Ship a starter alerting rule set on top of Sun's existing Prometheus/Alertmanager

**Depends on:** None.

## Problem

`docs/architecture/observability-design.md` specs dashboards, log/metric
identity labels, and backend modes — but says nothing about alerting.
`platform/infra/base/main.tf`'s `helm_release.prometheus` explicitly
disables Alertmanager (`alertmanager.enabled = false`) and ships no rule
files at all. A user gets Sun's label taxonomy
(`workspace`/`env`/`domain`/`service`/`primitive`/`release`) and nothing to
alert on it with.

## Decision (resolved 2026-09-04)

Ship a small starter rule set, not a full alerting product. Sun already
uses the plain `prometheus-community/prometheus` chart (`server` +
`alertmanager` subcharts) — **not** the Prometheus Operator
(`kube-prometheus-stack`) — so this chart has no `PrometheusRule` CRD to
target. The real mechanism is the chart's own file-based config:
`serverFiles.alerting_rules.yml` (Prometheus alerting rules) and
`alertmanagerFiles.alertmanager.yml` (Alertmanager routing), both already
plumbed through this chart's `values` the same way
`local.prometheus_remote_write`/`local.prometheus_thanos_server_fields`
are today.

## Goal

A small set of starter alert rules, using labels Sun already emits, that a
user gets by default and can extend or override:

1. **Error-rate spike** — HTTP 5xx rate above a threshold for a
   `domain`/`service` over a rolling window (source: `-svc`'s existing
   auto-metrics, per this repo's CLAUDE.md).
2. **Pod restart-loop** — a pod for a given `workspace`/`domain`/`service`
   restarting repeatedly (`kube_pod_container_status_restarts_total`
   rate, standard kube-state-metrics signal — confirm kube-state-metrics
   is actually scraped today; `platform/infra/base`'s Prometheus chart
   bundles it per its own subchart defaults, per the Helm output seen in
   `platform/infra/base/terraform.tfstate`'s notes).
3. **Deploy failure** — no automatic detection exists yet for this one
   without `OBS-037`'s release-event log line as a signal; scope this
   alert as "if OBS-037 has landed, alert on absence of an expected
   post-deploy healthy signal within N minutes" — otherwise skip it for
   v1 and note the dependency explicitly rather than block this ticket on
   it.

Ship with **no notification receiver configured** by default (no Slack
webhook, no PagerDuty key, nothing Sun doesn't know) — rules fire and are
visible in Alertmanager's own UI/API; wiring a receiver is a per-user
config decision, not something to default.

## Remediation

1. Enable `alertmanager.enabled = true` in `helm_release.prometheus`
   (`platform/infra/base/main.tf`).
2. Add a `values` entry for `serverFiles.alerting_rules.yml` with the
   starter rules above, using PromQL expressions scoped by Sun's existing
   labels — do not hardcode a specific `domain`/`service`, use label
   matchers/`by (...)` grouping so rules apply workspace-wide by default.
3. Add a minimal `alertmanagerFiles.alertmanager.yml` with a default
   route and a `null`/no-op receiver (or the chart's own default receiver
   if one exists) — document in `docs/deployment/observability-backends.md`
   exactly how a user points it at their own Slack/PagerDuty/email.
4. Document the starter rule set and override mechanism in
   `docs/deployment/observability-backends.md`.
5. Validate with `terraform validate`/`terraform fmt -check` and
   `helm show values prometheus-community/prometheus` to confirm the
   values keys are correct for the pinned chart version (`25.20.1`).

## Non-goal

- A full SLO/burn-rate dashboard or multi-window multi-burn-rate alerting
  — that's a meaningfully bigger design (needs explicit SLO targets per
  service, which Sun has no concept of today). Start with simple
  threshold rules; revisit multi-window burn-rate alerting only if the
  simple rules prove insufficient in practice.
- Migrating to the Prometheus Operator / `PrometheusRule` CRDs — that's a
  bigger architecture change than "add starter rules" and isn't justified
  by this ticket alone.
- Notification receiver integrations (Slack, PagerDuty, email) — document
  the extension point, don't build specific integrations speculatively.
