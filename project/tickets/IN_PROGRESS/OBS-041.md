`obs-tempo-eio`: a standalone Tempo backend package implementing `Obs_eio.backend`

**Depends on:** None.

## Problem

`docs/architecture/observability-design.md`'s Identity section names
"trace" as a signal type that must carry the shared ownership labels — but
there is no tracing backend and no trace dashboard. What exists today is
narrower: `~/Code/obs-eio`'s `Obs_trace` module provides W3C `traceparent`
context propagation (generate/parse/inject/extract), and `obs-loki-eio`'s
`Obs_loki` backend embeds `trace_id`/`span_id` as logfmt fields in pushed
log lines. That gives cross-service log *correlation* by trace_id, not a
trace *visualization* (span waterfall, latency breakdown across service
hops).

## Decision (resolved 2026-09-04)

Build a real Tempo backend, following the exact extraction pattern
`obs-loki-eio`/`obs-prometheus-eio` already established — a new standalone
package, not code living inside `sun`'s own tree, and not Sun-specific in
any way. **This ticket is the package only** — split out from a larger
combined ticket because the package is independently buildable and
testable with zero Sun dependency, unlike the Sun-side wiring (`OBS-042`,
depends on this ticket).

`obs-tempo-eio` implements `Obs_eio.backend`'s `emit_span` field
(`~/Code/obs-eio/lib/obs_eio.mli:110`) by exporting `span_event`s
(`trace_ctx : Obs_trace.t`, `name`, `service`, `start_ns`/`end_ns`,
`status`, `log_entries`, `context` — see `obs_eio.mli:56-71`; entirely
generic, no Sun-specific fields) to Tempo over OTLP, Tempo's native
ingestion protocol. This is the same shape of work as `obs-loki-eio`'s
`emit_span` doing one HTTP POST per span-close to Loki's push API — the
backend interface, the "every field called synchronously inline on the
calling fiber, no queue" contract (`obs_eio.mli:122-129`), and the
"backend owns whether to block or hand off to a queue itself"
responsibility for network calls all carry over unchanged.

## Remediation

1. New repo at `~/Code/obs-tempo-eio` — mirror `obs-loki-eio`'s repo
   layout (`lib/`, `test/`, `.mli`-first design, `README.md` spec doc,
   opam file) exactly. Findlib name `obs-tempo-eio`.
2. Implement `create : net:_ Eio.Net.t -> clock:_ Eio.Time.clock ->
   url:string -> ?timeout:float -> ?headers:(string * string) list ->
   unit -> Obs_eio.backend` (or the closest analogue — match
   `obs_loki.mli`'s `create` signature shape unless OTLP's transport
   genuinely requires something different; don't invent a different shape
   for its own sake).
3. Serialize `span_event` to OTLP (protobuf-over-HTTP or gRPC — pick
   whichever has better OCaml ecosystem support; check for an existing
   OCaml OTLP/protobuf library before hand-rolling wire encoding).
4. `emit_metric`/`declare_metric` can be no-ops for this backend (Tempo is
   trace-only) — don't build metric forwarding here, that's
   `obs-prometheus-eio`'s job.
5. Tests: unit tests for span → OTLP payload construction; an integration
   test pushing to a real local Tempo instance if one can be started
   cheaply (check if `platform/local/scripts/` needs a new
   `ensure-tempo.sh`-style helper for this, matching `ensure-loki.sh`'s
   pattern — that helper belongs in this ticket since the test needs it,
   even though deploying Tempo to `platform/infra/base` for production is
   `OBS-042`'s job).
6. `README.md` spec doc following `obs-loki-eio`'s/`obs-prometheus-eio`'s
   documentation conventions.

## Non-goal (this ticket)

- Any Sun-side integration (framework wiring, Terraform Tempo deployment,
  Grafana dashboard/datasource, trace-lookup link) — all of that is
  `OBS-042`.
- A dedicated trace-analysis dashboard or APM-style search UI.
- Retrofitting every span-producing call site for 100% capture — sampling
  policy is a consumer-side concern, not this package's.
- Alloy as a collector in front of Tempo (`OBS-039` scopes Alloy to log
  shipping only) — this package pushes directly to Tempo; routing through
  a collector is a future call, not built speculatively now.

## Acceptance criteria

- `obs-tempo-eio` exists as a standalone, opam-pinned package with its own
  README/spec doc, implementing `Obs_eio.backend`.
- Unit tests cover span → OTLP payload construction.
- At least one integration test pushes a real span to a locally-run Tempo
  instance and confirms it's queryable back out.
