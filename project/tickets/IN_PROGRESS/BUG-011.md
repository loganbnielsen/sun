`sun new fn` scaffolds fail to build (both locally and in Docker) with two separate, real dependency gaps — recovers the previously-lost BUG-007 plus a second, newly-found one.

**Depends on:** None.

## Problem

**Gap 1 (BUG-007, recovered — that ticket was silently deleted during
PR #115's branch-merge conflict resolution, a variant of the same
mistake that briefly lost CODE_LAYER-003 earlier the same day; never
actually fixed):** `fn_lib_dune` in `cli/sun/lib/sun_cli_scaffold_templates.ml`
had no `(libraries ...)` stanza at all, even though the sibling `fn_lib_ml`
template it pairs with references `Fn.Cron`/`Fn.FN` (the `sun_fn` package's
public modules). A bare `sun new fn` scaffold fails immediately with
`Error: Unbound module Fn`.

**Gap 2 (new, found while building a real multi-service demo — svc +
worker + fn across three domains — to populate the Grafana starter
dashboard from FEAT-031):** even after fixing Gap 1, the generated
Dockerfile fails: `framework/sun-fn/lib/dune` depends on `lambda-eio`
(an unpublished, git-pinned package per `~/Code/CLAUDE.md`'s repo list —
used for the `Fn.Lambda` trigger type), but the shared `tpl_dockerfile`
template's opam-pin block (`cli/sun/lib/sun_cli_scaffold_templates.ml`)
never pinned it — only `https-eio`/`kafka-eio`/`obs-eio`/`obs-loki-eio`/
`obs-prometheus-eio`/`obs-tempo-eio`/`pg-eio` were listed. This repo's own
`.github/workflows/ci.yml`/`release.yml` already pin `lambda-eio` (and
`aws-eio`/`s3-eio`/`dynamodb-eio`) for testing/publishing `sun` itself —
the scaffold template generating *other people's* Dockerfiles was simply
never updated to match when `sun_fn` picked up the `lambda-eio` dependency.

Confirmed live: a fresh `sun new workspace`, `sun new fn <domain>/<name>`,
then `sun up` reproduces both failures in sequence (Gap 1 blocks local
`dune build` entirely; fixing that alone still fails the Docker build on
Gap 2). Both are fixed in this pass; the full chain — `dune build` locally,
then a real `docker build` via `sun up`'s own `rsync --copy-links`
build-context construction — now succeeds end-to-end (verified, not just
inferred: image built and exported).

## Goal

`sun new fn <domain>/<name>` followed by `sun up` succeeds with no manual
fixes, matching `sun new svc`/`sun new worker`.

## Remediation (done)

1. `fn_lib_dune`: added `(libraries sun_fn)`.
2. `tpl_dockerfile`'s opam-pin block: added
   `opam pin add lambda-eio https://github.com/loganbnielsen/lambda-eio.git#main -y`,
   matching the existing pattern for the other unpublished packages.

## Acceptance criteria

- `sun new fn <domain>/<name>` followed by `dune build` (no other
  primitive scaffolded alongside it) succeeds with no errors.
- The generated Dockerfile builds successfully via `sun up`'s real
  `rsync --copy-links` build-context path (not just a same-machine
  `dune build`, which can mask missing-pin issues the way it masked this
  one before).
